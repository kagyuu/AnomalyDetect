# システム詳細設計

## 目的

* システム詳細設計書を作成して、バックエンドの仕様を確定する。

## インプット文書

* `docs/P001-requirement.md`
* `docs/P002-frontend-spec.md`
* `docs/ADR.md` (既存のADRがあれば)
* `docs/P901-cr-direction/CR-NNN.md` (Refactorステップからの再入時。対応中の変更要求の本文。対象CRの特定には状態の台帳 `docs/CR.md` を見る)

## アウトプット文書

* `docs/P003-backend-spec.md`

### アウトプットの記載内容

* `docs/P001-requirement.md` のAPI一覧にある全エンドポイントの完全な内部仕様
  * `docs/P002-frontend-spec.md` で明らかにしたAPIとデータモデルを使ってどのように外部仕様を成り立たせるか
  * 状態を保持する場合は、そのスコープ (システム、アプリケーション、ユーザセッションなど)と実現方法 (メモリ、KVS、RDBなど)を明らかにすること
* ユーザインタフェースに現れないデータがある場合は、データモデルを追加する: ER図 + テーブル定義書(主要カラム・型・制約・リレーション)
* ユーザインタフェースから使うデータモデルを修正する場合は、その旨を `docs/P002-frontend-spec.md` に追記する。修正内容と理由を明記すること。
* データモデルを定義する際は、**スキーマの適用方式(マイグレーション方式)を必ず明記する**。具体的には次の3点を記載する。
  * 適用のタイミングと方式(例: アプリ起動時に `migrations/*.sql` を全件再実行する、適用済みバージョンを管理テーブルで記録して差分のみ適用する、外部のマイグレーションツールを使う、など)。
  * その方式が**冪等かどうか**(同じマイグレーションが2回以上実行されても失敗しないか)。
  * 冪等でない場合に、どう冪等性を担保するか。
* 特に「全件再実行」方式を採る場合は、次の点に注意して方針を明記すること。初回構築時は `CREATE TABLE IF NOT EXISTS` だけで構成されるため冪等に見えるが、後からCRでカラム追加などが発生した時点で破綻するため、**この方針はデータモデルを最初に定義するP003の時点で決めておく必要がある**。
  * `ALTER TABLE ... ADD COLUMN` のような、多くのRDBMS(特にSQLite)で `IF NOT EXISTS` 相当の条件付き構文を持たないDDLは、2回目以降の実行で `duplicate column name` 等のエラーになり、アプリが起動しなくなる。
  * したがって、全件再実行方式を採る場合は「適用済みマイグレーションを記録するバージョン管理テーブルを設けて差分のみ適用する」「起動処理側で『既に適用済み』を意味するエラーを捕捉して読み飛ばす」など、冪等化の具体的な手段をP003の時点で決めて明記する。
  * この点は単体テスト・結合テストでは気づきにくい(テストごとに新しい一時DBを作る構成では常に初回実行になるため)。**アプリケーションを停止・再起動しても正常に起動すること**を確認する観点を `docs/P006-test-plan.md`(テスト計画)に含めるよう、ここで明記すること。この観点は永続化されたデータストアに対して実行する必要があり、単体テスト・スプリント内結合テスト(P007/P008)では代替できないため、**受け入れ結合テスト(P009)が担当する**旨も明記する。
* 非機能要件のうちインフラ寄りの項目(可用性・TLS終端・スケーラビリティ・ログ集約基盤など)を担当するフェーズを明確化する。
  * これらは`docs/P001-requirement.md`に記載された非機能要件のうち、アプリケーションコードの範囲を超え、実行環境・インフラ構成に依存する項目である。
  * P003では、これらの項目についてアプリケーションコード側で前提とする内容(例: 「TLS終端はリバースプロキシ側で行われる前提とする」)のみを明記し、実際のインフラ構成そのものの決定は `docs/P005-impl-plan.md`(インフラ・ミドルウェアが必要な場合のスプリント化)および `docs/P302-deliver.md`(Closing、実際の配布トポロジー整備)に委譲する旨を、該当箇所に明記すること。
  * この委譲の明記により、P004(トレーサビリティマトリクス)・P010(設計書横断レビュー)は、これらの非機能要件の充足確認をP005/P302の記載箇所で行う。P003側で「委譲する」旨の記載自体が無い場合は、P004/P010はMISSING/PARTIALとして扱う。

`docs/P001-requirement.md` になかったAPI実装をここで新たに追加しない。詳細化の過程でスコープの抜け漏れに気づいた場合は、勝手に拡張せず明示的に指摘すること。

* **クライアントとサーバを別プロセス/別ポートで開発・テストする構成の場合**(例: フロントエンドの開発サーバとバックエンドのAPIサーバを別ポートで起動する構成)、開発時・テスト時にクロスオリジンの問題が発生する。この対処方針をここP003で決め、その理由とともに技術的決定として記録する。
  * 最も鋭く現れるのは、`docs/P002-frontend-spec.md` が認証にCookieを用いると定めている場合である。ブラウザの仕様上、`Access-Control-Allow-Origin: *`(ワイルドカード)と `Access-Control-Allow-Credentials: true` は併用できないため、CORSヘッダを緩めるだけではCookieが送受信できるようにならない。トークン認証の場合も、CORSプリフライトの扱いは決めておく必要がある。
  * 採りうる方針の例: 開発用リバースプロキシ(フロントエンドの開発サーバのproxy機能など)でクライアントとAPIを同一オリジンに見せる / 認証をトークン方式にする / `SameSite=None` + HTTPS開発証明書を用いる。**どの方針を採るべきかは規定しない**。プロジェクトの状況に応じてこのフェーズが選び、選んだ理由を記録すること。
  * 決めた方針は、P021(ADR整理)が `docs/ADR.md` に取り込む技術的決定として記述する。本フェーズの実行時点でP021が未実行の場合は、暫定的なADR番号(例: 「ADR-001見込み」)を付し★FIXME★を添える(`SKILL.md` の「ADR番号の暫定参照について」に従う)。
  * この決定は、P103(結合テスト実行)・P201(受け入れ結合テスト実行)がテストハーネスを組む際、およびP009(受け入れ結合テスト定義)がテストの実行コマンドを記載する際の前提になる。決定を残さないと、各フェーズが場当たり的にハーネスを組むことになり、判断の理由がソースコードのコメントなど、後から追跡できない場所にしか残らなくなる。
* フェーズP002とP003の役割分担が曖昧になりやすい記載(例: 認証方式)について
  * 内部実現方法(例: パスワードのハッシュ方式、セッションの保存先・有効期限)をここP003で確定する際は、対応する外部から見える契約(例: Cookie/トークンの別、レスポンス形式)が `docs/P002-frontend-spec.md` のどこで確定しているかを参照として明記すること。
  * この相互参照は、P002・P003どちらで決めるべきか判断に迷う項目についてのみ行えばよい。役割分担が明確な項目にまで機械的に付ける必要はない。
* CR(`docs/P901-cr-direction/CR-NNN.md`)にもとづく再入時は、CRで指定された変更点のみを反映し、無関係な既存記述は変更しない。何をCRの何番にもとづいて変更したかを本文中に明記する。
