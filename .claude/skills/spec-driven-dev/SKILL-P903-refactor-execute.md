# 修正実施(Refactor)

## 目的

* P902で更新した `docs/P001-requirement.md` を起点に、Plan Loop Step(P002〜P012)、Overview Step(P020〜P022)、Executor(P101〜P104)、Reviewer Loop(P201〜P205)、Closing(P301〜P302)を通常のフローどおり再実行する。
* あわせて、本CRの対処記録 `docs/P903-cr-records/CR-NNN.md` を**着手前に作成**し、スコープ決定を記録する。作業完了後に、実際の変更内容・事前想定との差異・テスト結果を追記する。

### 動作内容

* 本フェーズを開始する前に、まず `docs/P903-cr-records/CR-NNN.md` を `TEMPLATE-P903-cr-record.md` にもとづいて作成し、対象CRの影響範囲を分類したうえで、P002〜P302のうちどのフェーズを実際に再オープンするかをスコープとして決定し、その決定と理由を「スコープ決定(P903が着手前に記載)」の節に書く(下記「CRスコープの決定」参照)。ファイル名の番号は、対応する `docs/P901-cr-direction/CR-NNN.md` と同じ番号にする。
  * スコープ決定は**作業を始める前**に行う判断であるため、記録も着手前に書く。完了後にまとめて書くと、事前の判断ではなく事後の正当化に変質し、「事前に対象外と見込んでいたフェーズが、作業中に対象へ変わった」という変化自体が残らなくなる。
* 記録ファイルを作成したら、`docs/CR.md` の対象CRの行について、状態列を `対応中` に、対処記録列を作成した記録ファイルへのリンクに更新する。
* スコープ決定後、対象と判断したフェーズについてのみ、`SKILL.md` の「ステップ0」と同じ判定ロジックで、P002から順に再実行する。ただし各フェーズは「既存の文書 + P001の更新差分 + `docs/P901-cr-direction/CR-NNN.md`」を入力として、差分更新を行う(全面的な書き直しはしない)。
  * この内部再実行の間、`docs/.inprogress` には素の `P0NN` ではなく **`P903:P0NN`** の入れ子表記(例: `P903:P006`)を記録する。これは、内部で再実行されるP302自身の完了時の指示(`SKILL.md` 各フェーズ共通指示)が「`.inprogress` を削除する」ではなく「`.inprogress` を `P904` に更新する」に変わることと対になっており、`SKILL.md` の「ステップ0」が、内部再実行中の中断をCRの文脈を保ったまま再開できるようにするための表記である。素の `P0NN` のまま記録すると、再開時に通常のPlan Loop等と誤認され、CRの内容を反映しない全面書き直しになりうる。
* CRと無関係な既存の仕様・実装・テストは変更しない。
* 各StepのStopping Condition(差し戻し上限)は通常実行時と同じルールに従う。
* すべての対象フェーズが完了したら、記録ファイルの「対処内容(P903が完了時に記載)」の節に、次を追記する。
  * 実際に変更したドキュメント・ソースコードの一覧
  * **事前のスコープ想定と実際の差異**(着手前に「対象外」としたフェーズが実際には必要になった、など)。差異が無かった場合も、その旨を明記する
  * 実行したテストと結果(`docs/test-records/*.md` への参照)

#### CRスコープの決定(必須の手順)

* CRの影響を、まず次のようなおおまかなカテゴリに分類する(複数該当してもよい)。この分類は目安であり、実際のCR内容に照らして判断が異なる場合はその判断を優先し、理由を記録する。

| カテゴリ | 典型例 | 目安として再オープンするフェーズ |
|---|---|---|
| UI表示文言のみ | ラベル・メッセージ文言の変更 | P002(該当箇所のみ)、P007・P101〜P104(該当タスクのみ) |
| 画面項目追加・変更(バックエンド契約変更なし) | 既存APIの範囲内で完結する画面項目の追加・並び替え | P002、P004、P005〜P009(該当スプリント/テストのみ)、P101〜P104(該当スプリント分) |
| API契約変更 | リクエスト/レスポンス形式、エンドポイントの追加・変更 | P002、P003、P004、P005〜P009(該当スプリント/テストのみ)、P101〜P104(該当スプリント分)、必要なら P022(ArchitectureHandbook) |
| データモデル変更 | テーブル追加・カラム変更、リレーション変更 | P002(該当する場合)、P003、P004、P005〜P009、P101〜P104 |
| 非機能・インフラ変更 | 可用性・TLS・スケーラビリティ・ログ集約基盤などの変更 | P003(委譲先の明記)、P005、P101〜P104(該当する場合)、P302 |

上記いずれのカテゴリでも、実際にコードを変更する以上P101〜P104(実装・結合テスト実行・実装構造修正)は通常対象になる。加えて、P020(実装構造)・P010(横断レビュー)・P201(実装横断レビュー)・P301(全体INDEX)・P302(納品物作成)は、対象範囲のフェーズに実質的な変更が入った場合は原則として再実行が必要になる(下記の別項目でも述べる)。

P011・P012(Plan Loopの差し戻し)およびP202〜P205(Reviewer Loopの差し戻し)は、それぞれP010・P201の結果次第で発生する条件付きフェーズである。着手前のスコープ決定表にはこれらを固定で「対象/対象外」と書かず、**「条件付きで対象になる(P010/P201の結果次第)」**と明記する。

* ★ACCEPTED★ CRの内容から再オープン対象フェーズを**自動的に分類する仕組み(影響分析エンジン)は、本SKILLでは作らない**。検討はしたが、影響分析を機械的なルールとして固定すると破綻リスクが高く(実際のCRは複数カテゴリにまたがり、同じカテゴリでも既存設計との関係で必要なフェーズが変わる)、誤った分類を出力したときにそれが誤りだと気づく手段が無くなるため採用しなかった。上記の対応表と、下記の「対象/対象外+理由を必ず記録する」義務が、この点に対する**恒久的な回答**である。残る制約は、スコープ判断の精度がAgentの判断力に依存し続けることだが、判断の理由が記録として残るため人間が後から検証・是正できる。この論点は判断済みであり、再度の指摘は不要。

* 「データモデル変更」カテゴリに該当する場合は、上記の再オープン対象に加えて、**スキーマ変更の適用方式が冪等かどうかを必ず確認する**。
  * `docs/P003-backend-spec.md` に記載されているマイグレーション方式(全件再実行/差分適用/バージョン管理テーブルの有無)を確認する。記載が無い場合は、実際のコード(マイグレーション実行処理)を読んで現在の方式を特定し、P003に追記する。
  * `ALTER TABLE ... ADD COLUMN` のように、条件付き実行の構文を持たないDDLを追加する場合は、既存の適用方式のままで**アプリケーションを再起動しても正常に起動するか**を必ず確認する。全件再実行方式のまま素朴に追加すると、2回目以降の起動で `duplicate column name` 等のエラーになりアプリが起動しなくなる。
  * 冪等でない場合は、冪等化(バージョン管理テーブルの導入、適用済みエラーの捕捉など)もCRの対応範囲に含め、その判断と実施内容を記録ファイルの「マイグレーション方式の確認」欄に残す。
  * この確認は単体テスト・結合テストでは代替できない(テストごとに新しい一時DBを作る構成では常に初回実行になるため)。**実際に初期化処理を2回連続で実行し、2回目も成功すること**をもって確認とし、結果をテスト記録に残す。
  * ★ACCEPTED★ この「2回連続実行して2回目も成功する」という基準は、冪等性の**必要条件であって十分条件ではない**。例えば、適用済みエラーをファイル単位で捕捉して打ち切る実装は、2回連続実行には成功する一方、同一ファイル内の後続の文を黙って読み飛ばす欠陥を抱えたままである。より強い基準(適用済み判定の仕組みそのものを説明させる、エラー捕捉のスコープが文単位かファイル単位かを確認させる、など)も検討したが、**十分性を証明する検証は費用に見合わないと判断し、確認をここで意図的に打ち切る**ことにした。この判断が成り立つのは、`SKILL-P003-backend-spec.md` が「その方式が冪等かどうか」「冪等でない場合にどう冪等性を担保するか」を設計文書に書き下ろすことを既に要求しており、実際にV0.6の欠陥を捕捉したのはそちらのルールだったためである。ここに重複する第二のルールは置かない。残る制約は、本フェーズの確認だけを読んだ実行担当が「2回成功したので問題なし」と判断しうることだが、その場合もP003側の記述義務が後段で働く。この論点は判断済みであり、再度の指摘は不要。
* 上記の対応表はあくまで目安であり、機械的に当てはめるだけでは不十分な場合がある。次を必ず行う。
  * **対象としたフェーズ**とその理由を記録する。
  * **対象外とした(再オープンしなかった)フェーズ**と、なぜ再オープンが不要と判断したかの理由も記録する(過小スコープ・過大スコープのどちらにもブレやすいのはこの「対象外」の判断であるため、理由の言語化を必須とする)。
  * P020(実装構造)・P010(横断レビュー)・P201(実装横断レビュー)・P301(全体INDEX)・P302(納品物作成)は、対象範囲のフェーズに実質的な変更が入った場合は原則として再実行が必要になる(目次・成果物一覧の整合性を保つため)。除外する場合はその理由も記録する。
* この「対象/対象外+理由」の記録は、`docs/P903-cr-records/CR-NNN.md` の「スコープ決定」の節に残す。P904(変更要求の反映確認)は、この記録を参照してスコープの妥当性も確認する。
