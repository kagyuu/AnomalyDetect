# 要求トレーサビリティマトリクス作成

## 目的

* `docs/P001-requirement.md` で定義された要求事項が、`docs/P002-frontend-spec.md` および `docs/P003-backend-spec.md` によってすべて満たされているかを検証する。
* 満たされていない要求事項が見つかった場合は、このフェーズでは修正せず、不足の性質に応じてP002またはP003に差し戻して詳細化をやり直させる(どちらに差し戻すかの判断基準は下記「アウトプットの記載内容」参照)。

## インプット文書

* `docs/P001-requirement.md`
* `docs/P002-frontend-spec.md`
* `docs/P003-backend-spec.md`

## アウトプット文書

* `docs/P004-traceability-matrix.md`

### アウトプットの記載内容

* `docs/P001-requirement.md` に記載された要求事項(画面・API・非機能要件など)それぞれに一時ID(例: `REQ-SCREEN-001` `REQ-API-001` `REQ-NFR-001`)を付ける。既に要求書側にIDがあればそれを使う。
* 各要求IDについて、`docs/P002-frontend-spec.md` および `docs/P003-backend-spec.md` のどこで対応する仕様が定義されているかを表形式で対応付ける。

```markdown
| 要求ID | 要求内容(要約) | 対応するP002の箇所 | 対応するP003の箇所 | 状態 | 差し戻し先(PARTIAL/MISSINGの場合) | 判断理由 |
|---|---|---|---|---|---|---|
| REQ-SCREEN-001 | ... | 2.1 ログイン画面 | - | OK | - | - |
| REQ-API-003 | ... | 3.2 予約API | 4.5 予約Repository | OK | - | - |
| REQ-NFR-002 | 可用性要件 | - | - | MISSING | P003 | 非機能要件(可用性)はP003の担当範囲のため |
```

* 状態は次のいずれかとする。

```text
OK        P002・P003の両方(該当する場合)で仕様が満たされている
PARTIAL   一部の側面(例: 異常系、非機能要件)が仕様化されていない
MISSING   対応する仕様が見つからない
DEVIATED  環境制約等により、要求どおりに満たすことが技術的に不可能で、意図的に代替実装を選んだ(例: サンドボックス環境でパッケージレジストリに接続できないため要求されたフレームワークを使えない)
```

* `DEVIATED` は、`PARTIAL`/`MISSING` と異なり**差し戻しでは解消しない**(差し戻しても同じ制約に再度ぶつかるだけである)ことが明らかな場合に限り使う。判断に迷う場合はまず `PARTIAL`/`MISSING` として差し戻す。`DEVIATED` を選んだ場合は、代替実装の内容とその判断理由を、該当箇所に隣接して★ACCEPTED★付きで記載する(`SKILL.md` 各フェーズ共通指示参照)。`DEVIATED` は非ブロッキングであり、単独では次フェーズ(P005)への進行を妨げない。
* `PARTIAL` または `MISSING` が1件でもある場合は、その要求ID1件ごとに、どちらのフェーズに差し戻すべきかを次の基準で判定し、判定結果(差し戻し先と理由)を表の備考または専用の列に明記する。差し戻し先を機械的にP002固定にしない。
  * 画面・UI表示・入出力項目・APIの外部契約(リクエスト/レスポンス形式、ステータスコード、エラーコードなど、`docs/P002-frontend-spec.md` が確定を担う範囲)に関する不足 → **P002**(`SKILL-P002-frontend-spec.md` のアウトプット)に差し戻す。
  * バックエンドの内部実現(処理ロジック、内部データモデル、状態管理方式など)や、非機能要件・インフラ寄りの項目(可用性・TLS・スケーラビリティ・ログ集約基盤など、`docs/P003-backend-spec.md` が担う範囲)に関する不足 → **P003**(`SKILL-P003-backend-spec.md` のアウトプット)に差し戻す。
  * 1件の要求IDの不足がP002・P003両方にまたがる場合は、両方に差し戻してよい。
  * 上記のいずれに該当するか迷う場合は、P002・P003どちらが本来その項目を確定させる役割かを判断し(`SKILL-P002-frontend-spec.md`/`SKILL-P003-backend-spec.md` の役割分担の記載を参照)、選んだ理由を記載する。
  * P002・P003は、差し戻された該当箇所を補って再度P004を実行する。
* すべての要求IDが `OK` になったら、その旨を明記してフェーズを完了とし、P005に進む。
* `docs/P001-requirement.md` にない項目を、P002・P003が勝手に実装していないかも合わせて確認する(過剰実装のチェック)。見つかった場合は「対応する要求なし」として記載し、要求書側に追加すべきか、実装側から削るべきかを明記する(このフェーズで一方的に削除はしない)。
  * 過剰実装(「対応する要求なし」の行)は、`PARTIAL`/`MISSING` とは異なり、それ単独では次フェーズ(P005)への進行をブロックしない。ただし記録は必須であり、後続フェーズ(P010横断レビュー、P302納品物作成など)に必ず引き継ぐこと。動作している機能を要求なしに削除するかどうかは自動判断せず人間の判断を仰ぐべき事項であるため、ブロッキングの`PARTIAL`/`MISSING`とは扱いを分けている。

### アウトプットを参照する文書

アウトプットの記載内容は、次の文書を作成できる程度に具体的であること

* `docs/P010-design-review.md` (設計書横断レビューで、本マトリクスの状態を参照する)

## 動作

* 共通指示に加えて、上記アウトプット記載内容に従う。
* `PARTIAL` / `MISSING` が残っている状態で次フェーズ(P005)に進んではならない。これは明確にブロッキングである。
* 「対応する要求なし」(過剰実装の検出)、および `DEVIATED`(環境制約による意図的な代替)は、記録(`DEVIATED`の場合は★ACCEPTED★付きの理由記載)が残っている限りにおいて次フェーズ(P005)への進行をブロックしない(非ブロッキング)。ただし記録なしに読み飛ばしてはならない。
