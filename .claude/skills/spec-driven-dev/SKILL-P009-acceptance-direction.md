# 受け入れ結合テスト定義

## 目的

* 受け入れ結合テスト定義を作成して、Reviewer Loop(高性能モデルを想定)に、スプリントをまたぐ結合テスト・システムテスト・受入テストをさせる指示を取りまとめる。実行はP201でReviewer Loopが行うので、ここでは実行は行わない。
* 単体テスト、スプリント内/モジュール間の結合テストの指示は、それぞれ `docs/P007-impl-direction.md`(P007)、`docs/P008-test-direction.md`(P008)で行うので、ここでは指示しない。

## インプット文書

* `docs/P001-requirement.md`
* `docs/P006-test-plan.md`

## アウトプット文書

* `docs/P009-acceptance-direction.md` (目次 OKF形式)
* `docs/P009-acceptance-direction/A000-{test-name}.md` (000はテスト番号(実行順)、test-name はテスト名)

### アウトプットの記載内容

* 目次は OKF 形式(`SKILL.md` の「目次(OKF形式)について」参照)で作成して、各テストタスクへのリンクを保持する
* テスト指示は、テストケースごとに行い `docs/P009-acceptance-direction/A000-{test-name}.md` に分割して記載する
  * `TEMPLATE-P009-acceptance-direction.md` の構成に則る
* 対象とするテスト範囲
  * 複数スプリントをまたぐモジュール間の連携テスト
  * 複数APIをまたぐ業務フローのテスト
  * 画面遷移を含むシナリオテスト
  * 認証・認可をまたぐ処理確認
  * エラーハンドリングの一連の確認
  * 外部APIやモックサービスを含む連携確認
  * システムテスト相当の主要シナリオ確認(`docs/P001-requirement.md` の要件・非機能要件を満たすか)
  * 受け入れテスト相当の主要シナリオ確認(発注者・利用者・運用者の視点)
  * 非機能テストのうち、実行可能な範囲の性能・負荷・セキュリティ観点確認
  * このSkillでは、純粋な関数単位のUnit Testや、単一クラス・単一コンポーネントだけのテスト指示、およびスプリントに閉じた結合テストは対象にしない(それらは `docs/P007-impl-direction.md` `docs/P008-test-direction.md` 側で指示済みの前提とする)。
* テスト前に必ず全モジュールをビルドするよう指示する
  * ビルド手順には以下を明記する。
    * ビルド対象
    * ビルドコマンド
    * 成功条件
    * 失敗時の記録方法
    * ビルド失敗時はテストへ進まないこと
* テスト失敗時にその場で修正しない
  * Reviewer Loopには、P201のテスト実行時点ではコードを修正させてはいけない。必ず以下を指示する。
    * アプリケーションコードを修正しない
    * テストコードをその場で都合よく変更しない
    * 失敗したテストをスキップしない
    * 期待値を変更して成功扱いにしない(=改ざん。ただし、対象テストのコードがまだ存在せず本フェーズの指示に従って新規作成する場合は、これに該当しない。改ざんが禁止するのは「既存のテストコードを、失敗を回避する目的で書き換えること」であり、新規作成そのものは妨げない)
    * 同じ失敗に対して場当たり的な再テストを繰り返さない
    * 失敗内容をテスト記録に残す
    * 修正が必要な場合はP202(修正計画)以降に引き渡す
* テスト記録を必ず残させる
  * 記録先 `docs/test-records/YYYYMMDD-HHMM-test-record.md`
  * 記録形式は `TEMPLATE-test-record.md` に定める共通形式(P008・P009・P103・P201・P205で共通)に従う。

* テストタスクを小さくする
  * 1つのテストタスクは、原則として以下の範囲に収める。
    * 1つの業務シナリオ
    * 1つの主要API連鎖
    * 1つのエラー系シナリオ
    * 1つの非機能観点
  * 避けること
    * 「全画面をテストする」
    * 「全APIを結合テストする」
    * 「正常系と異常系を全部まとめて確認する」
    * 「性能・セキュリティ・認証・業務フローを一度に確認する」
    * 「失敗したら直して成功するまで回す」
* 具体的に書く
  * 各テストタスクには、少なくとも以下を含める。
    * 目的
    * 対象モジュール
    * 前提条件
    * 使用するテストデータ
    * 事前準備
    * 実行手順
    * 実行コマンド
    * 期待結果
    * 合否判定基準
    * 失敗時に記録する内容
    * 修正禁止事項
    * 次タスクへ進む条件
  * クライアント・サーバ分離構成の場合、「事前準備」「実行コマンド」に書くテスト実行環境の構成(開発用リバースプロキシの要否、各プロセスの起動ポートなど)は、P003が決めて `docs/ADR.md` に記録した方針に従う(`SKILL-P003-backend-spec.md` 参照)。ここで独自にトポロジーを決めない。実行コマンドは、記載前に一度実際に実行して確認すること(`SKILL.md` の共通指示)。
  * 永続化されたデータストアを使うテストの「事前準備」には、`docs/P006-test-plan.md` が定めたテストデータのライフサイクル方針(ベースラインへ復元する単位と、ベースラインの定義)に従った手順を書く。ここで独自に方針を決めない。復元をテストスイートの実行ごとに行う方針の場合、個々のテストに復元手順を書くのではなく、**スイート全体で1回だけ、かつテスト対象アプリケーションを起動する前に**実行されるようにする(詳細と注意点は `SKILL-P008-test-direction.md` の同項を参照)。
    * ただし、**データが永続していること自体を確認するテスト**(再起動耐性の確認など)は、実行の途中でベースライン復元が挟まるとテストの前提が壊れる。この種のテストは、他のテストと同じデータストアを共有しない構成にするか、復元処理との実行順序を明示すること。
* テストタスクが完了したら(PASS/FAIL/BLOCKEDいずれの結果であっても記録が残った時点で)、Reviewer Loopは `docs/P009-acceptance-direction.md` の該当テスト行のチェックボックスを `[x]` に更新する。全テストが `[x]` になるまでP201は完了しない。ただしFAIL/BLOCKEDが残っている場合は、P202(修正計画)への引き渡しが必要である旨を目次に明記する。

### アウトプットを参照する文書

アウトプットの記載内容は、次の文書を作成できる程度に具体的であること

* Reviewer Loopが、テスト指示のみを参照してテストを行う(P201)。
* `docs/P302-deliver.md` (Closing)が、本フェーズの実行結果を確認する。

## 動作

* 共通指示に加えて、上記アウトプット記載内容に定めた事項に従う。
