# ADR.md

本プロジェクトで現在有効な設計判断を管理する。
過去に廃止された設計判断は `ADR_master.md` に移動する。

* 1つの決定 = 1つの ADR-NNN とする。
* 「決定内容」「理由」は、後続のAI(実装担当・修正担当)がそのまま読み込んで判断できる程度に簡潔にする。長い経緯や検討の過程そのものは書かず、結論とその根拠だけを残す。
* 状態が「廃止」になったADRは、本文を `ADR_master.md` に移し、この `ADR.md` の一覧・本文からは削除する。`ADR_master.md` 側には、廃止日と廃止理由(何のADRに置き換えられたか)を追記する。

## ADR-001

### タイトル

Spring Boot + MyBatis を採用する

### 状態

採用

### 日付

2026-08-03

### 関連要求

* REQ-001
* REQ-002

### 背景

REST APIを提供する業務アプリケーションを構築する。データベースアクセスにはSQLを明示的に管理したい。

### 決定内容

バックエンドフレームワークとしてSpring Bootを採用する。O/R Mapperは使用せず、MyBatisを採用する。

### 理由

* SQLを明示管理できる
* 性能問題を調査しやすい
* 業務SQLが複雑

### 検討した代替案

#### JPA / Hibernate

却下。理由: SQLチューニングが難しくなるため。

#### JDBC

却下。理由: コード量が増えるため。

### 残存リスク

この決定に★ACCEPTED★(意識的に受け入れた制約)を付す場合、`SKILL.md` 各フェーズ共通指示が要求する3要素のうち「何を検討したか」「なぜ採らなかったか」は上記「検討した代替案」節で表現し、「その結果として残る制約(残存リスク)」はこの節に書く。3要素を重複して書かない。★ACCEPTED★を付さないADRでは、この節は「なし」でよい。
