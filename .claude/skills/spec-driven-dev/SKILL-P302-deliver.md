# 納品物作成

## 目的

* 仕様・実装・テスト・修正結果・配布資産を確認し、成果物一式をまとめる指示書 `docs/P302-deliver.md` を作成する。
* 目的は、以下を人間がレビューできる形で明確にすることである。
  1. 仕様とテスト仕様とテスト実装が漏れなく対応していること
  2. ソースツリーにバージョンとビルド履歴が記録されていること
  3. 実行モジュールまたは配布物からバージョンを確認できること
  4. サービス提供型システムなら Docker Compose で起動できる資産一式が整っていること
  5. CLIコマンドまたはバッチ処理なら、実行可能な配布形式になっていること
  6. 実行環境で Docker Compose / CLI / バッチを実行できるまでの手順が明確であること
* このフェーズは最終成果物の見える化と配布準備を目的とする。必要に応じて設定ファイルやバージョンファイルの作成・更新も行ってよいが、仕様変更や機能追加は行わない。

#### 実行前チェック

作業開始時に以下を確認する。

1. `docs/P002-frontend-spec.md` と `docs/P003-backend-spec.md` が存在するか
2. `docs/P006-test-plan.md` が存在するか
3. `docs/test-records/*.md` (テスト実装またはテスト記録) が存在するか
4. `docs/P202-fix-plan/P202-fix-resolved.md` または `docs/P202-fix-plan/P202-fix-unresolved.md` が存在するか
5. ソースツリーからアプリケーション種別を推定できるか
6. `docs/P302-deliver.md` が既に存在するか
7. 配布トポロジーを決める前に、フロントエンドのAPI接続前提(例: 同一オリジンでの相対パスfetchか、絶対URLでのクロスオリジンfetchか)をコードで確認する。そのうえで、本フェーズで組み立てる実際の配布トポロジー(単一プロセスか、`client/` `server/` を別コンテナにするdocker-compose構成かなど)がこの前提と矛盾しないかを確認する。トポロジー未決定を理由にこの確認自体をN/A扱いにしない(この確認はトポロジーを決めるためのものである)。
8. データストアを持つ場合、**アプリケーションを停止・再起動しても正常に起動するか**(マイグレーション・初期化処理が冪等か)。配布物は繰り返し起動されるため、初回起動でしか成功しない初期化処理は配布時点の不具合として扱う

判定:

* 仕様書またはテスト計画が不足している場合 → 不足ファイルを「10. 未整備事項」に記載する。
* テスト記録や修正結果が不足している場合 → 最終品質確認が未完了であることを記載する。
* 7.のフロントエンド/バックエンドの接続前提と実際の配布トポロジーが一致しない場合(例: P009受け入れ結合テストはバックエンドに直接HTTPクライアントで接続して検証しており、同一オリジン前提の相対パスfetchが崩れることを検出できていなかった、など) → これを不具合として扱い、本フェーズを完了とする前に、フロントエンドの接続設定(例: `BASE_URL` の環境変数化、リバースプロキシの追加など)を修正する。修正せずに本フェーズを完了としない。単に「10. 未整備事項」に記載するだけで済ませ、壊れたトポロジーを黙って納品しない。
* 8.の確認結果は `docs/test-records/YYYYMMDD-HHMM-test-record.md`(他の全テストと同じ格納先)に記録する。`docs/P009-acceptance-direction/` のいずれかのテスト(例: 再起動耐性を確認するテスト)で、本フェーズと同一の観点(同一データストアに対する複数回の再起動)が既に確認・記録済みの場合は、その既存のテスト記録を参照するだけでよく、本フェーズで重複して再実行する必要はない(該当するテスト記録へのリンクを明記すること)。該当する既存記録が無い場合にのみ、以下の確認を新たに行う。
  * 8.の再起動時の起動可否が確認できていない場合 → 実際に初期化処理を2回連続で実行して確認する(実行環境の制約で確認できない場合は、その旨を「10. 未整備事項」に明記する)。2回目が失敗する場合は、7.と同様に不具合として扱い、冪等化を行ってから本フェーズを完了とする。
* 7.・8.の是正が、コード修正の範囲を超えて**仕様変更**を要する場合(例: `SKILL.md`のClosing停止条件が挙げる「`BASE_URL`の環境変数化」がP002の変更に相当する場合)は、本フェーズは仕様変更を行えない(前述「目的」参照)ため、修正・納品のいずれも行わずに処理を停止する。該当事項をCRの起票候補として「10. 未整備事項」に明記し、リリース判定は `保留` としたうえで、人間に報告する(Closing Stepの停止条件。`SKILL.md` 参照)。

#### アプリケーション種別の判定

ソースツリーと仕様書から、配布・起動方式を判定する。

分類:

1. サービス提供型システム(Webアプリケーション、APIサーバー、バックエンドサービス、常駐プロセス、フロントエンド+バックエンド+DBなど複数サービス構成)
2. CLIコマンド(コマンドラインから実行するツール。引数や設定ファイルを受け取り、標準出力またはファイルを生成するもの)
3. バッチ処理(定期実行または手動実行の一括処理。ジョブ、スクリプト、データ変換、レポート生成など)
4. ライブラリ(他システムから利用されるパッケージ)
5. 判定不能(ソースツリーまたは仕様書から実行形態が判断できない場合)

判定不能の場合は、勝手にDocker ComposeやCLI形式を決めず、「10. 未整備事項」に記載する。

#### 仕様・テスト・テスト実装の対応表(4章)

必ず、仕様とテスト仕様とテスト実装が対応することを示す表を作る。

表の基本形:

```markdown
| 仕様ID/項目 | 要求ID | 仕様内容 | 対応するテスト計画 | 対応するテスト指示 | 対応するテスト実装/実行コマンド | 最新結果 | 証跡 | 状態 | 出荷影響 |
|---|---|---|---|---|---|---|---|---|---|
| REQ-API-001 | REQ-API-001 | POST /api/auth/login | docs/P006-test-plan.md | docs/P009-acceptance-direction/A001-... | `npm run test:integration -- ...` | PASS | docs/test-records/... | OK | - |
| REQ-NFR-003 | REQ-NFR-003 | セキュリティのうちパスワード非露出・権限チェック(TLSは下記の副IDへ分離) | docs/P006-test-plan.md | A008 / A003 | `... test_a008 ...` / `... test_a003 ...` | PASS | docs/test-records/... | OK | - |
| REQ-NFR-003-TLS | REQ-NFR-003 | セキュリティのうちHTTPS(TLS終端) | docs/P006-test-plan.md | - | - | - | docs/P302-deliver.md 10章 | BLOCKED | 本番検証: TLS終端はリバースプロキシ側の責務(P003 §7)であり、本環境に該当構成が無いため原理的に確認できない。稼働前に運用側で確認する |
| SPEC-FLOW-001 | - | 一般ユーザーの標準的な業務フロー(画面・APIの単位に対応する要求が無いため要求IDは `-`) | docs/P006-test-plan.md | docs/P009-acceptance-direction/A001-... | `npx playwright test ...` | PASS | docs/test-records/... | OK | - |
```

**仕様IDと要求IDの対応**

* **`要求ID` 列には、その行が由来する `docs/P004-traceability-matrix.md` の要求IDを書く。** 仕様IDが要求IDと同じであれば、両方の列に同じ値を書いてよい(上記例の1行目)。
* 画面・APIの単位に対応する要求が存在しない行(業務フロー横断のシナリオなど)は `要求ID` を `-` とし、なぜ要求IDに紐づかないかを「仕様内容」欄に一言添える。
* 仕様IDが既存文書にない場合は、見出しやAPI名・画面名・シナリオ名をもとに一時IDを付ける(例: `SPEC-API-001` `SPEC-SCREEN-001` `SPEC-FLOW-001` `SPEC-NFR-001`)。`docs/P004-traceability-matrix.md` で既に要求IDが振られている場合はそれを使う。
* **識別子の表記は設計書からそのまま転記する。** APIエンドポイント名などを行のキーに使う場合、`docs/P002-frontend-spec.md`・`docs/P003-backend-spec.md` の表記をそのまま用い、独自に整形しない(例: 設計書が `/api/users/{id}` なら `/api/users/{user_id}` と書き換えない)。表記がぶれると、要求IDと仕様IDの突き合わせも、後からの検索も成立しなくなる。
* **網羅性を確認する。** `docs/P004-traceability-matrix.md` に載っている要求IDのうち、本表に1行も現れないものが無いことを確認する。現れないものがあれば対応表の漏れであり、`UNKNOWN` として行を起こす(黙って落とさない)。

**副IDの命名規約**

ある要求・仕様の一部だけを切り出す場合は **`{親ID}-{修飾子}`** とする(例: `REQ-NFR-003-TLS`、`REQ-NFR-006-集約`、`SPEC-SCREEN-003-参加者選択`)。番号を振り直さず親の番号を引き継ぐことで、親子関係が見た目で追える。副IDの `要求ID` 列には**親と同じ要求ID**を書く。

状態の分類:

```text
OK              仕様・テスト計画・テスト指示・実行結果が対応し、合格している
NO_TEST_PLAN    仕様に対するテスト計画が見つからない
NO_TEST_CASE    テスト計画はあるが具体的テスト指示が見つからない
NO_TEST_IMPL    テスト実装または実行コマンドが見つからない
NOT_RUN         テストが未実行
FAILED          テストが失敗している
BLOCKED         環境不備や仕様不明で実行できない
SPEC_CONFLICT   仕様とテスト期待値が矛盾している
DEVIATED        環境制約等により、仕様どおりに満たすことが技術的に不可能で、意図的に代替実装を選んだ(`docs/P004-traceability-matrix.md` のDEVIATEDと同義。★ACCEPTED★付きの理由記載が別途必要)
UNKNOWN         対応関係を判断できない
```

**出荷影響の分類**:

状態列が「**検証できたかどうか**」を表すのに対し、出荷影響列は「**出荷を妨げるかどうか**」を表す。両者は別の判断であり、1つの列に混ぜない。混ぜると「出荷に影響しない」という判断が「検証済み」に見えてしまい、テストしていないという事実が失われる。

状態が `OK` の行は出荷影響を `-` とする。状態が `OK` 以外の行には、次のいずれかを付し、**判断の理由を必ず併記**する。

```text
本番検証   本番相当環境でのみ検証可能。出荷そのものは妨げないが、稼働前に運用側での確認が必要
代替検証   別のテストで実質的にカバーされている。カバーしているテストIDを必ず明記する
自明       構成上・実装上、成立が自明。なぜテスト無しで成立が言えるかの根拠を必ず明記する
要対応     出荷に影響する。リリース前に対応または人間の判断が必要
```

各値の適用条件:

* **`本番検証`**: TLS終端、ログ集約基盤への転送、実負荷試験など、**開発・CI環境では原理的に確認できない**ものに限る。「今回は時間が無かった」「環境を用意できなかった」は該当しない(それは `要対応`)。該当する行は「10. 未整備事項・人間による確認事項」に**稼働前に確認すべき事項として必ず引き継ぐ**。判定から外すだけで放置しない。
* **`代替検証`**: カバーしているテストIDの明記を必須とする。テストIDを書けない場合はこの値を使ってはならない。
* **`自明`**: **根拠の記載が無い場合は使用禁止**とする。「フレームワークが保証している」「型検査で保証される」など、テスト無しで成立が言える具体的な理由を書く。**「テストしていないが動くはず」は `自明` ではない**(それは `要対応`)。本値は最も乱用されやすいため、迷った場合は `要対応` を選ぶ。
* **`要対応`**: 上記のいずれにも当てはまらないもの。

対応表作成時のルール:

* `docs/P002-frontend-spec.md` `docs/P003-backend-spec.md` のAPI、画面、データモデル、エラーケース、複雑な処理フローを確認する。
* `docs/P006-test-plan.md` のテスト観点とテストレベルを確認する。
* `docs/P008-test-direction.md` / `docs/P009-acceptance-direction.md` (目次) および各タスクファイルのテストタスクIDを確認する。
* `docs/test-records/*.md` と `docs/P202-fix-plan/P202-fix-resolved.md` / `docs/P202-fix-plan/P202-fix-unresolved.md` の実行結果を確認する。
* 対応が見つからない仕様は、必ず対応表に残す。対応が見つからないことを隠さない。
* **`OK` を付けてよいのは、引用したテストが、`docs/P004-traceability-matrix.md` に書かれた要求内容の全体をカバーしている場合に限る。** 要求の一部しかカバーしていない状態で `OK` を付けてはならない。一部しかカバーできていない場合は、次の手順を踏む。
  1. カバーできている範囲を親IDの行に残し、「仕様内容」欄をカバー範囲に合わせて書き換える。**ただし、元の要求から範囲を狭めたことが分かる書き方にする**(例: 要求が「セキュリティ(HTTPS/パスワードハッシュ/権限チェック)」なら、「セキュリティのうちパスワード非露出・権限チェック」と書き、TLSを外したことが読み取れるようにする)。狭めたことを書かずに要約だけ差し替えると、対応表だけを読んだ人が要求全体を検証済みと誤読する。
  2. カバーできていない範囲を `{親ID}-{修飾子}` の副IDとして**別行に起こす**。状態は実態に応じて `NO_TEST_IMPL` / `NOT_RUN` / `BLOCKED` / `DEVIATED` などを付け、理由を書く。
  3. 1つの要求が複数のテストに分かれてカバーされている場合は、「対応するテスト指示」「対応するテスト実装」「証跡」の各欄に**そのすべて**を挙げる。1つだけ挙げて残りを黙らせない。
* 仕様からテストを勝手に生成して「対応済み」にしない。

#### バージョン情報の整備(5章)

ソースツリーにバージョン情報がない場合は、作成または追記する。

優先順位: (1) 既存の言語・フレームワーク標準のバージョン定義を使う (2) 既存の `VERSION` があればそれを使う (3) なければ `VERSION` を作成する (4) 必要に応じて `BUILD_HISTORY.md` または `docs/BUILD_HISTORY.md` を作成する。

言語別の代表例:

```text
Node.js / TypeScript : package.json の version
Python               : pyproject.toml の project.version、または package __version__
Java / Maven         : pom.xml の project.version
Java / Gradle        : build.gradle または gradle.properties の version
Go                   : ビルド時の ldflags または version パッケージ
Rust                 : Cargo.toml の package.version
不明な場合           : VERSION
```

**バージョンの初期値**: 新規にバージョン定義を作成する場合(初回リリースなど、既存のバージョン情報が無い場合)、初期値は `0.1.0` とする。`1.0.0` のような特別な意味を持つ値から始めない。スキャフォールドツールの既定値(`0.0.0`/`0.1.0` など)が入っている場合も、`0.1.0` に統一する。

**MAJORが0の間の扱い**: MAJORが `0` の間(`0.y.z`)は初期開発版として扱い、**破壊的変更であってもMAJORを上げず、MINORを上げる**(例: `0.2.0` の時点で既存のAPI契約を壊す変更を行った場合は `0.3.0` とする)。`1.0.0` への移行は、人間から明示的な指示があった場合にのみ行う。本Skillはバージョンを単なる連番として扱い、`1.0.0` に「正式版」等の特別な意味を持たせない。

可能であれば、実行モジュールからもバージョンを確認できるようにする。

```text
CLIの場合          : <command> --version / <command> version
Web/APIサービス    : GET /health, GET /version, アプリ起動ログ, 画面フッターまたは管理画面
バッチ処理         : <batch-command> --version
```

実装済みでない場合は、「10. 未整備事項」に記載する。最終仕上げとして軽微な追加で済む場合は実装してよいが、仕様変更を伴う場合は「10. 未整備事項」に記載し、CRの起票候補とする(このフェーズでは仕様変更を行わない)。

**CR対応後の版数更新方針**: Refactor(P901〜P905)経由でCRが完了し本フェーズが再実行される場合は、セマンティックバージョニング(MAJOR.MINOR.PATCH)にもとづき版数を更新する。バグ修正のみ(仕様・契約の変更を伴わない)は PATCH、後方互換性を保った機能追加(画面項目追加・API追加など、既存の契約を壊さない変更)は MINOR、既存の画面・API・データ契約を破壊する変更は MAJOR を上げる。**ただし、MAJORが `0` の間は上記「MAJORが0の間の扱い」が優先し、破壊的変更であってもMINORを上げる**(この規則は、MAJORが1以上になった後に適用される)。`docs/P903-cr-records/CR-NNN.md` のスコープ決定で「API契約変更」または「データモデル変更」に分類されているCRは、少なくとも MINOR を上げる。機械的に判断がつかない場合は安全側(より大きい方の桁)を選び、判断理由とともに★FIXME★を付す。

ビルド履歴がない場合は `BUILD_HISTORY.md` または `docs/BUILD_HISTORY.md` を作成し、少なくとも以下を記載する。

```markdown
# Build History

| Build ID | Version | Date/Time | Commit | Build Command | Test Command | Result | Notes |
|---|---|---|---|---|---|---|---|
| ... | ... | ... | ... | ... | ... | PASS/FAIL | ... |
```

日時・コミット・コマンドが取得できない場合は、空欄にせず `未取得` と書く。

#### 配布資産の整備方針(6章)

サービス提供型システムの場合は、Docker Compose から起動できるように資産一式を整備する。

確認・整備対象: `Dockerfile` / `docker-compose.yml` または `compose.yml` / `.env.example` / `README.md` または `docs/P302-deliver.md` の起動手順 / 必要な初期化スクリプト / DBマイグレーション手順 / ヘルスチェック / ログ出力先 / 永続ボリューム / ネットワーク設定。

Docker Compose ファイルには、可能な範囲でアプリケーションサービス、フロントエンド/バックエンドサービス、DBやキューなど依存ミドルウェア、必要な環境変数、ポート公開、ボリューム、healthcheck、depends_on を含める。ただし、実装言語や構成により適切な内容は異なるため、既存の構成を優先する。

実行環境にDocker CLIはあるがデーモンが起動していない場合、またはDockerそのものが利用できない場合(サンドボックス環境などで実際にありうる)は、Dockerfile / docker-compose.yml などの資産自体は通常どおり作成・整備する。ただし、実際にビルド・起動して動作確認できていないことを `docs/P302-deliver.md`(9章「最終確認結果」および11章「リリース判定」)に明記する。動作確認していないことを黙って「整備済み」「動作確認済み」であるかのように書いてはならない(前述「作業時の禁止事項」の「実行していないコマンドを実行済みと書かない」も参照)。この場合、リリース判定は原則として `保留` とする。

CLIコマンドの場合は、実行可能な配布形式を整備する。確認・整備対象: 実行コマンド / インストール手順 / 依存関係の導入手順 / 設定ファイル例 / 入力ファイル例 / 出力ファイル例 / `--help` / `--version` / 配布パッケージ作成手順(例: `npm pack` / `python -m build` / `pipx install dist/*.whl` / `java -jar app.jar --version` / `go build -o dist/app ./cmd/app` / `cargo build --release`)。

バッチ処理の場合は、実行可能な配布形式と運用実行手順を整備する。確認・整備対象: 実行スクリプト / 設定ファイル例 / 入力データ配置場所 / 出力データ配置場所 / ログ出力先 / 再実行可否 / 異常終了時の扱い / スケジューラ登録例 / `--version` または実行ログ上のバージョン表示。

#### 実行環境で実行できるまでの手順(7章)

`docs/P302-deliver.md` には、実行環境で実行できるまでの手順を必ず書く。

サービス提供型システムの例:

```markdown
### Docker Compose 起動手順

1. 必要な前提ソフトウェアを確認する
2. `.env.example` を `.env` にコピーする
3. 環境変数を設定する
4. Dockerイメージをビルドする
5. Docker Compose で起動する
6. ヘルスチェックを確認する
7. 初期データまたはマイグレーションを実行する
8. ブラウザまたはAPIで動作確認する
```

CLIの例:

```markdown
### CLI 実行手順

1. 配布物を取得する
2. 依存関係をインストールする
3. バージョンを確認する
4. `--help` を確認する
5. サンプル入力で実行する
6. 出力結果を確認する
```

バッチの例:

```markdown
### バッチ実行手順

1. 配布物を配置する
2. 設定ファイルを配置する
3. 入力データを配置する
4. バージョンを確認する
5. バッチを実行する
6. ログと出力ファイルを確認する
7. 異常終了時の再実行条件を確認する
```

#### テスト実行手順(8章)

`docs/P302-deliver.md` には、最終確認として以下を記載する: Unit Test 実行コマンド / 結合テスト実行コマンド / 必要なE2E・システムテスト実行コマンド / テスト結果の格納先 / 合格条件。

全テストが合格していない場合は、リリース判定を `NG` または `保留` にする。

#### リリース判定(11章)

判定は次のいずれかとし、根拠を必ず書く。

```text
OK       主要成果物が揃い、テスト合格、配布手順あり
保留     軽微な未整備事項があるが、人間判断でリリース可否を決められる
NG       テスト失敗、仕様矛盾、配布不能など重要な未解決事項がある
UNKNOWN  根拠資料不足で判定できない
```

**4章の対応表(出荷影響列)との接続**:

* 出荷影響が **`要対応` の行が1件でもあれば、判定を `OK` にしない**(`保留` または `NG`)。
* **`本番検証` / `代替検証` / `自明` は、判断理由が書かれている限り `NG`/`保留` の根拠に数えない**(★ACCEPTED★と同じ扱い)。ただし「10. 未整備事項・人間による確認事項」には全件を列挙する。判定から外すことと、記載を省くことは別である。
* 判定の根拠には、**`要対応` の件数と内訳を必ず明記**する。
* **4章の対応表と本章の判定が食い違ってはならない。** 4章で `OK` としている要求を、本章で未整備事項・保留理由として挙げている(またはその逆)状態は、対応表側の分割(前述の副IDによる切り出し)が済んでいないことを意味する。判定を書く前に4章へ戻って是正する。

#### 未整備事項・人間による確認事項(10章)

以下がある場合は必ず記載する: 対応するテストがない仕様 / 実行結果がないテスト / 失敗したままのテスト(`docs/P202-fix-plan/P202-fix-unresolved.md` に記録が残っているもの) / 仕様矛盾 / Docker Compose 未整備・動作未検証(前述「配布資産の整備方針」参照) / CLI配布形式未整備 / バージョン確認手段がない / ビルド履歴がない / 実行手順が未確認 / 本番環境固有の値が未確認 / ADRの決定自体は正しいがその前提条件が本実行環境では実現されていないもの(例: ADRはTLS終端の存在を前提にしているが、本環境にはTLS終端コンポーネントがない。`SKILL-P202-fix-plan.md` の「修正成功時に更新するdocs」の第4分類も参照)。

未整備事項のうち、仕様変更を要するものは、そのままCRの起票候補として明記する(実際の起票はP901が `docs/P901-cr-direction/CR-NNN.md` として行い、`docs/CR.md` の台帳に行を追加する)。

★ACCEPTED★が付された既知の制約(例: 実ブラウザ不在で一部テストがNOT RUNのまま★ACCEPTED★付きで確定している場合)は、本章に記載してよい。ただし★ACCEPTED★は既に判断済みの受容済みリスクであるため、次の「11. リリース判定」を `NG`/`保留` にする根拠には数えない。11章の判定材料になるのは、★FIXME★(未解決)および、記録が無い/理由の説明が無い純粋な未実施事項のみである。

**未解消の★FIXME★を全件一覧化する(V1.2で追加)。** `docs/` 配下の全成果物を検索し、残っている★FIXME★を次の表にまとめる。

| # | 所在(ファイル・章節) | 想定で補った内容 | CR起票候補か |
| --- | --- | --- | --- |
| 1 | `docs/P003-backend-spec.md` 5.2 | セッション有効期限を8時間と仮定 | ○ |

* **件数だけを書いて済ませない。** 1件ずつ、所在と「Agentが何を想定で補ったか」を書く。人間が確認すべき対象はこの一覧であり、ここに載らなかった★FIXME★は事実上失われる。
* `docs/.mode` が `一気通貫` の場合、★FIXME★は各Stepで解消されずに納品時点まで残る。**この一覧が、人間がCRを起票するための入口になる。** 一覧が無いと「その後CRで直す」という運用そのものが成立しない。
* `docs/.mode` が `工程確認` の場合、★FIXME★は各Step境界のゲートで解消されているため、この一覧は原理的に空になる。**空であること自体が、モードが機能した証跡である。** 空の場合は「未解消の★FIXME★: 0件」と明記する(表ごと省略しない)。
* 前述のとおり、★FIXME★は11章のリリース判定の材料に数える。本一覧に挙げた件数と内訳を、11章の判定根拠から参照できるようにする。

#### 作業時の禁止事項

* 仕様上存在しない機能を追加しない
* テスト未実行なのに合格扱いにしない
* 要求の一部しか確認していないのに `OK` と書かない
* 「仕様内容」欄を書き換えて、要求の範囲を黙って狭めない
* 出荷影響の判断理由を書かずに `本番検証` / `代替検証` / `自明` を付けない
* リリース判定を `OK` にしたいがために、`要対応` を他の値に付け替えない
* 未解消の★FIXME★を、件数だけ書いて内訳を省略しない。また、判定を通したいがために★FIXME★を勝手に外さない(外してよいのは人間が確認して解消した場合だけであり、それは本フェーズの仕事ではない)
* 配布資産が未確認なのに整備済みと書かない
* 実行していないコマンドを実行済みと書かない
* バージョンやビルド履歴を推測で捏造しない
* Docker Compose のサービス構成を根拠なく作らない
* 既存のリリース手順を無視して別方式に置き換えない
