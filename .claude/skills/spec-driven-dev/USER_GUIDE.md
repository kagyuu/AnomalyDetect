# spec-driven-dev Skill 利用マニュアル (V1.2)

このマニュアルは、`spec-driven-dev` という Claude Code の Skill(`V1.2/SKILL.md` 以下のファイル一式)を実際に使う「人間」向けの説明書です。SKILL本体のファイル群(`SKILL.md`・`SKILL-P0NN-*.md`・`TEMPLATE-*.md`)は Claude Code 自身が読んで実行するための指示書であり、専門用語やフェーズ番号(P001、P302 など)が多く、そのまま人間が読むには不向きです。このマニュアルでは、そうした内部の仕組みにはあまり立ち入らず、「何をすればいいか」「何が起きるか」「何を確認すればいいか」だけを実務的にまとめます。

## この Skill は何をしてくれるのか(全体像)

一言でいうと、**要件をざっくり伝えるだけで、要件定義書・画面設計・API設計・実装計画・テスト計画・実際のソースコード・単体/結合/受け入れテスト・Docker配布資産まで、一連の開発工程をAIが一気通貫で作ってくれる Skill** です。日本の受託開発でよく使われる「ウォーターフォール/V字モデル」の工程(要件定義→設計→実装→テスト→納品)を模していますが、V0.4以降は**フェーズが完了するたびに人間の確認を待つことをしません**。人間が関わるタイミングは大きく3つです。

1. 最初に、作りたいアプリの要件をざっくり伝える(①)
2. 実際にビルドしてもらう(自動で最後まで一気に進む)(②)
3. 出来上がったものを見て、直してほしい点を「変更要求(CR)」として伝える(③)

以下、①②③の順に説明します。①の前に、まず「Skillをどう用意し、どう使い始めるか」を説明します。

---

## 導入: Skillのインストールと使い始め方

①②③の話に入る前に、そもそも Claude Code にこの Skill を使わせるための準備を説明します。ここは最初の1回だけ必要な作業です。

### 前提: Claude Code CLI 本体

Claude Code CLI自体(npm経由のインストール・ネイティブインストーラ・VSCode拡張など、導入方法はOS・環境によって複数あります)がすでに使える状態になっていることを前提とします。導入方法の詳細は公式ドキュメントを参照してください。ここから先は、ターミナルで `claude` コマンドを実行できる状態からの説明です。

### Skillのインストール(プロジェクトへの配置)

Skillのインストールに特別なコマンドはありません。**このリポジトリの `V1.2/` フォルダの中身を、アプリを作りたいプロジェクトのフォルダ内にコピーするだけ**です。

1. アプリを作りたいプロジェクト用のフォルダを用意する(空のフォルダで構いません。まだ `git init` していなくても構いません)。
2. そのフォルダの中に `.claude/skills/spec-driven-dev/` というフォルダを作る。
3. このリポジトリの `V1.2/` フォルダの中身(`SKILL.md`・`SKILL-P0NN-*.md` 一式・`TEMPLATE-*.md` 一式)を、2で作ったフォルダにそのままコピーする。`USER_GUIDE.md`(本書)や `review-report.md` は人間向けの参考資料であり Skill 自体の動作には使われませんが、一緒にコピーしておいても害はありません。

コピー後は次のような配置になります。

```
your-project/                       ← アプリを作りたいプロジェクトのルート
└── .claude/
    └── skills/
        └── spec-driven-dev/
            ├── SKILL.md
            ├── SKILL-P001-requirement.md
            ├── SKILL-P002-frontend-spec.md
            ├── ...(SKILL-P0NN-*.md が続く)
            ├── TEMPLATE-ADR.md
            ├── ...(TEMPLATE-*.md が続く)
            └── USER_GUIDE.md        ← 本書(任意、なくても動作に支障なし)
```

この時点では、プロジェクトフォルダの中に他に何もなくて構いません(`docs/` フォルダやソースコードは、これから Skill が作っていきます)。複数のプロジェクトで使い回したい場合は、プロジェクトごとにこの手順を繰り返して `V1.2/` の中身を複製してください(`Vx.y/` フォルダはそれぞれ自己完結したスナップショットなので、バージョン間・プロジェクト間で共有すべきファイルはありません)。

個人的に多くのプロジェクトで常用したい場合は、プロジェクトごとのフォルダ(`your-project/.claude/skills/`)の代わりに、ホーム直下のユーザースコープのフォルダ(`~/.claude/skills/spec-driven-dev/`)に置く方法もあります。この場合は毎回コピーする手間がなくなりますが、プロジェクトごとに使うSkillのバージョンを変えたい場合はプロジェクトスコープ配置の方が扱いやすくなります。

### Claude Code CLIからの使い始め方

1. ターミナルで、Skillを配置したプロジェクトのフォルダに移動する。

   ```
   cd your-project
   ```

2. `claude` コマンドで Claude Code CLI を起動する。

   ```
   claude
   ```

3. 起動したセッションで、次の①で説明する要件を、最初のメッセージとして伝える。その際、**「spec-driven-dev の Skill を使って」のように Skill 名を明示する**のがおすすめです。Skillは `SKILL.md` の `description` の内容にもとづいて自動的に認識される仕組みになっていますが、こうした独自Skillは依頼内容だけでは自動選択されないことがあるため、最初の一言に含めておくと確実に本Skillのフェーズ構成で進めてくれます。

   > 「spec-driven-dev の Skill を使って、社内の会議室予約システムを作ってください。社員が空き状況を見て予約・変更・取消できるようにしたい。……」

4. あとは、以降の①(要件定義)→②(初回ビルド)→③(変更依頼)の流れが、このセッション(および必要なら後続のセッション)の中でそのまま進みます。

### 導入にあたっての注意点

* 本SkillはP001〜P302だけで数十〜百件規模のMarkdown成果物と実際に動くアプリケーションコードを生成するため、1回のビルドは長時間・大量のやり取りになるセッションになります。途中でセッションが切れても `docs/.inprogress` を見て自動的に再開できるので(②で後述)、無理に1回のセッションで完走させる必要はありません。
* Skillのインストール自体に、ネットワーク接続やビルドツールは不要です。ファイルをコピーするだけで使い始められます。

## ① アプリケーション要件定義のやり方

### 2つの伝え方から選ぶ(V1.2で追加)

最初に Skill を起動すると、**P000(要求整理)** が次の2つを提示して、どちらで要求を伝えるかを尋ねてきます。

| 方式 | どうなるか | 向いている場面 |
| --- | --- | --- |
| **(a) ファイルで整理する** | `docs/P000-concept-analysis.md` という**記入用のひな型**が作られ、いったん処理が止まります。人間がそれに記入してから、もう一度 Claude Code に「続けてください」と伝えると、その内容を読んでP001が始まります | 画面数が多い、操作時の振る舞いを細かく決めたい、要求を落ち着いて書き出したい |
| **(b) プロンプトで伝える** | ファイルは作られず、従来どおり会話で要求を伝えます | 小さめのアプリ、まず作り始めたい |

**(a)を選ぶと、ひな型は2種類から選べます。**

* **GUIアプリ用** — 画面を持つアプリ向け。画面一覧と、画面ごとの構成・**アクション定義**(ボタンを押したときに何が起きるか)を書く形式です。
* **CLIアプリ用** — コマンドラインで動くアプリ向け。コマンド一覧と、コマンドごとの引数・処理内容・**終了コードと異常系**を書く形式です。

どちらのひな型にも、**章ごとに【必須】【任意】の区別**があります。【必須】が1つでも空欄だと、P000が空欄の箇所を教えてくれて先へ進みません。【任意】は空欄のままで構いません(AIが想定で補い、その箇所に★FIXME★という目印を付けるので、あとからまとめて確認できます)。

> **ひな型で一番大事なのは「前提を満たさないとき」の列(GUI)と「終了コードと異常系」の表(CLI)です。**
> 「検索ボタンを押すと一覧が出る」は誰でも書きますが、「何も選ばずに表示ボタンを押したらどうなるか」「結果が0件だったらどうなるか」は書き忘れがちです。文章で書くと*書き忘れたこと自体が見えません*が、表の列になっていれば空欄として目に見えます。思いつかない場合は空欄のままにせず「おまかせ」と書いてください。

### 人間が最初に用意するもの

(b)プロンプト方式を選んだ場合の話です。特別なフォーマットのテンプレートを事前に埋める必要はありません。P001(システム要件定義フェーズ)のインプットは「システム設計者の頭の中にある、まだ漠然としたアイデア」でよいとされており、人間がゼロから完成された仕様書を書く必要はありません。とはいえ、思いつきレベルの一言だけだと、AIが★FIXME★(後述)だらけの仮置き文書を作ってしまうため、最低限次のような情報を伝えると仕上がりが良くなります。

* **アプリの目的**: 何のためのアプリか、誰が使うか、どんな課題を解決するか
* **想定規模・前提**: 利用者数の目安、社内向けか一般公開かなどのデプロイ想定、ログイン(認証)が必要か
* **技術的な制約があれば**: 使いたい/使いたくない言語・フレームワーク、既存システムとの連携要否など(特にこだわりがなければ「AIにおまかせ」でも問題ありません)
* **画面や機能のイメージ**: 箇条書きでよいので、欲しい画面や主要な操作の一覧

### 実際に何を伝えればよいか(例)

会話やプロンプトで、次のように伝えるだけで十分です。

> 「spec-driven-dev の Skill を使って、社内の会議室予約システムを作ってください。社員が空き状況を見て予約・変更・取消できるようにしたい。管理者は会議室とユーザーの登録・編集ができるようにしてください。社員数は300人程度、会議室は10室くらいです。社内向けなのでログインは必須にしてください。フロントエンドはReact、バックエンドはPythonでお願いします。」

これくらいの粒度で伝えれば、Claude Code はこの内容をもとに対話をしながら(P001フェーズは「作業主体: 人間+AI」であり、漠然とした部分を詰める会話をしてよいことになっています)、要件を具体化して `docs/P001-requirement.md` を作成します。技術選定の理由まで指定していなくても、AIが妥当な理由を補って記載してくれます。

### P001フェーズが実際にやってくれること・人間の役割

* **AIの仕事**: 伝えた内容をもとに、次の項目を備えた要件定義書 `docs/P001-requirement.md` を作成する。
  * アプリケーションの概要(目的・利用者・解決する課題)
  * システムの前提(規模、デプロイ先、認証要否、既存システム連携の有無)
  * フロントエンド/バックエンドの採用技術と選定理由
  * 画面一覧・画面遷移図(Mermaid図)
  * 各画面の入出力項目
  * 画面とバックエンドAPIの対応、API一覧
  * 非機能要件(性能・可用性・セキュリティなど、決められる範囲で)
  * テスト方針(方針レベルのみ)
* **人間の仕事**: 上記のような材料を伝えること、そして対話の中で聞かれたことに答えること。要件定義書そのものをMarkdownで書く必要はありません。

### 完成した要件定義書のイメージ

実例として、`V0.7_testbed/docs/P001-requirement.md` にある「会議室予約システム」の要件定義書の一部を紹介します。実際にはこのくらいの粒度・分量の文書がP001フェーズの成果物として自動生成されます。

```markdown
## アプリケーションの概要

* **何のためのアプリか**: 社内の会議室予約を一元管理し、空き状況の確認から予約・変更・取消までをオンラインで完結させる。
* **誰が使うか**: 社員(一般ユーザー / 予約者)、および会議室・ユーザーを管理する管理者(総務・情シス想定)。
* **どんな課題を解決するか**: Excelや口頭連絡による会議室管理で発生していた二重予約、空き状況が分からないことによる確認の手間、予約変更・取消の連絡漏れを解消する。

## システムの前提

* **想定ユーザー数・規模**: 従業員数300名程度、会議室10室程度の中規模オフィスを想定。
* **デプロイ先**: 社内向けWebアプリケーションとしてクラウド環境(例: AWS)にデプロイ。
* **認証要否**: 必要。社内アカウント(ID/パスワード)によるログインを必須とする。
```

さらに、画面一覧(S01ログイン画面〜S07ユーザー管理画面)、画面遷移図、画面ごとの入出力項目表、API一覧なども含まれ、この1つの文書だけで後続の設計フェーズがすべて具体化できるだけの情報量になっています。

### 「良い入力」の目安

* アプリの目的・利用者・課題感が一文でも書けている
* 画面や機能について、思いつく範囲で箇条書きできている(完璧な網羅は不要)
* 技術スタックにこだわりがあるかどうかだけは伝えておく(こだわりがなければ「おまかせ」でOK)

これだけ揃っていれば、足りない部分はAIが自分の判断で補い、補った箇所には目印(★FIXME★、後述)を付けてくれるので、人間があとから探しやすくなっています。

## ② 初回ビルドの流れ

### 何をすればビルドが始まるか

要件定義(①)が済んだら、あとは基本的に「続けてください」「最後まで進めてください」のように一言伝えるだけです。SKILL側には「今 `docs/` に何があるかを見て、どのフェーズから再開すべきかを自動判定する」仕組み(SKILL.mdの「ステップ0」)が組み込まれているため、人間がP番号を指定したりフェーズを意識したりする必要はありません。例えば次のように伝えれば十分です。

> 「そのまま最後まで実装・テスト・納品準備までお願いします。」

すでに要件定義まで終わっている場合は、これだけでP002(画面設計)からP302(納品物作成)までが自動的に連続実行されます。

### 要件定義の最後に2つのことを聞かれます(V1.2で追加)

P001が要件定義書の草案を書き終えると、**1回だけ**人間に確認が入ります。ここで初めて、この先の進み方が決まります。

1. **要求の入力は以上でよいか。** AIが自分の想定で補った箇所(★FIXME★)の一覧も一緒に提示されます。追加で伝えたいことがあればここで伝えてください。**「はい」と答えるまで、P002以降には進みません。**
2. **この先の進め方(実行モード)をどちらにするか。**

| モード | 挙動 | 向いている場面 |
| --- | --- | --- |
| **一気通貫**(既定) | P302(納品)まで人間に一切聞かずに走り切ります。決めきれなかったことはAIが仮決めして★FIXME★を付け、あとからCRで直します | まず動くものを見たい。長時間放っておける |
| **工程確認** | 大きな区切り(**最大6箇所**)で止まり、そこまでに溜まった★FIXME★を人間が解消してから次へ進みます | 要求の解釈違いを早い段階で潰したい |

**工程確認モードで止まる場所は「Step の境界」**です。すなわち 要件定義 ⇒ 設計 ⇒ 概観 ⇒ 実装 ⇒ 最終確認 ⇒ 納品 の各切り替わり目だけで、実装のスプリントごとやテストの修正ごとには止まりません。**フェーズ(P002、P003…)ごとに止まることは、どちらのモードでもありません。**

止まったとき、AIは (1)そのStepで作った成果物の一覧、(2)**そこまでに溜まった★FIXME★の全件**、(3)次へ進んでよいかの確認 を提示します。★FIXME★については「こう直して」と答えるか、「そのままでよい」と答えてください。後者の場合は★ACCEPTED★(検討したうえで受け入れた、という目印)に書き換えられ、以後のレビューで蒸し返されなくなります。

> **どちらを選ぶか迷ったら「一気通貫」で構いません。** これがこのSkillの標準的な使い方です。工程確認モードは、要求が固まりきっていないとき、あるいは初めてこのSkillを使って挙動を見たいときに向いています。
> 途中でモードを変えたくなったら、いつでも「工程確認モードに変えてください」と伝えれば、以降の区切りから適用されます(すでに通り過ぎたStepまで遡ることはしません)。

### 実行中に何が起きるか(V0.4以前との違い)

ここが V0.4以降の一番大きな設計方針です。**フェーズが1つ終わるごとに「次はこれでいいですか?」と人間に確認を求めることはありません。** 以前のバージョン(V0.3以前)は各フェーズの完了ごとに人間のレビューを挟んでいましたが、V0.4以降は、設計の矛盾チェック(P010)や実装後の単体・結合テストもすべてAI自身が行い、あらかじめ決められた「停止条件」(たとえば同じ問題を3回差し戻しても解消しない場合など)に該当したときだけ処理を止めて人間に報告する、という設計に変わっています。

以下は**一気通貫モード**(既定)を選んだ場合の話です。工程確認モードを選んだ場合は、上記のとおり最大6箇所で確認が入ります。

したがって、人間から見ると次のような体験になります。

* 「Reactにしますか、Vueにしますか?」のような細かい追加質問は原則来ません(要件定義フェーズで確認しきれなかった事項は★FIXME★という注記付きでAIが仮決めして進みます)。
* 画面設計ができた時点、実装ができた時点、テストが終わった時点、それぞれで「確認してください」と止まることはありません。
* 数十〜百件規模のMarkdown成果物(`docs/` 配下)と、実際に動くアプリケーションのソースコード、実行済みの単体・結合テストの結果が、1回のセッションでまとめて出来上がります。
* セッションはかなり長時間・長い作業になります。対話的なやり取りではなく、「一気に任せて、出来上がったものをあとでまとめて見る」という使い方を想定してください。

つまり、②でやることは実質「進めてください」と伝えることだけで、そのあとは基本的に見守るだけになります。

### 「完了した」とはどういう状態か

以下が揃っていれば、初回ビルドは一通り完了したとみなせます。

* `docs/P302-deliver.md` が作成されている(納品物まとめ・配布手順を記載した最終成果物)
* `docs/.inprogress` というファイルが**存在しない**こと(このファイルは「今どのフェーズを実行中か」を記録する一時ファイルで、最後のフェーズ(P302)が終わると削除される決まりになっています)
* `docs/P001-requirement.md` から `docs/P302-deliver.md` まで、一連のドキュメント(P001〜P302)が `docs/` 配下に揃っている

### 完了後に人間が実際に確認すべきもの

まず見るべきファイルは `docs/P302-deliver.md` です。ここに、成果物全体のサマリと「リリース判定」が書かれています。

* **ソースコード**: アプリケーション本体は `docs/` の外、プロジェクトルート直下(例: `client/`・`server/` のようなソースツリー)に生成されます。各ソースツリー直下の `INDEX.md` がその中の目次になっているので、まずそこから見ると迷いません。プロジェクト全体の目次は `./INDEX.md`(P301の成果物)です。
* **設計ドキュメント**: `docs/P001-requirement.md`(要件)、`docs/P002-frontend-spec.md`(画面設計)、`docs/P003-backend-spec.md`(バックエンド設計)など、`docs/P0NN-*.md` の一連のファイル。
* **テスト結果**: `docs/test-records/YYYYMMDD-HHMM-test-record.md` に、結合テスト・受け入れテストの実行記録が時系列で残ります。
* **リリース判定**: `docs/P302-deliver.md` の最後の章(「11. リリース判定」)に、`OK` / `保留` / `NG` / `UNKNOWN` のいずれかが根拠つきで書かれています。
  * `OK`: 主要成果物が揃い、テストも合格し、配布手順も整っている状態。
  * `保留`: 軽微な未整備事項は残っているが、人間が判断すればリリース可否を決められる状態(例: テストはすべてPASSしているが、サンドボックス環境ではDockerを実際に起動して確認できなかった、TLS終端や初期管理者アカウントの投入手順など運用開始前に詰める必要がある事項が残っている、といったケース)。
  * `NG`: テスト失敗や仕様矛盾など、重要な未解決事項が残っている状態。
  * この判定と根拠は必ず記載されるので、`保留`や`NG`が出ていたら、その根拠(`docs/P302-deliver.md` の「9. 最終確認結果」「10. 未整備事項・人間による確認事項」)を読んで、実際にリリースしてよいか、追加対応が必要かを人間が判断します。
* **★FIXME★の一覧**: ビルド中にAIが自分の判断で仮決めした箇所には、その記述のすぐ隣に `★FIXME★` という目印が付きます。ドキュメント全体を `★FIXME★` で検索すれば、人間が優先的にレビューすべき「AIが独断で埋めた部分」だけをまとめて拾い出せます。
  * **V1.2以降、自分で検索しなくても `docs/P302-deliver.md` の「10. 未整備事項・人間による確認事項」に全件の表が載ります**(所在・AIが何を想定で補ったか・CRの起票候補かどうか)。一気通貫モードで作った場合、この表が**次にCRで直すべきことの一覧**になります。
  * 工程確認モードで作った場合、★FIXME★は各区切りで解消済みのはずなので、この表は「0件」になります。0件であること自体が、確認が機能した証拠です。

### 途中で止まった/中断した場合(簡単に)

長時間の自動実行の途中でセッションが中断されても、`docs/.inprogress` に「今どのフェーズを実行していたか」が記録されているため、次に「続けてください」と伝えれば、SKILL側がそのファイルを見て続きから自動的に再開してくれます。人間が「どこまで進んでいたか」を調べて指示し直す必要は基本的にありません。

## ③ ビルド後の変更依頼(CR)のやり方

初回ビルドが終わったら、それで終わりではありません。V0.4以降のコンセプトは「フェーズの途中では人間のレビューを挟まない代わりに、**動くものが一通り出来上がったあとに人間がまとめてレビューし、直してほしい点を変更要求(CR: Change Request)として伝える**」という進め方です。実装の途中経過を逐一チェックするのではなく、完成品を見てフィードバックする、という位置づけです。

### CRの伝え方

人間がやることは、ファイルを自分でMarkdown編集することでも、テンプレートの書式を暗記することでもありません。基本的には**普通の言葉で「これを直してほしい」と伝えるだけ**で構いません。AIがそれをP901フェーズで正式なCRの形式に整理し、`docs/P901-cr-direction/CR-001.md` のような変更要求ファイルとして書き起こしてくれます。

**V1.2以降は、要件定義のときと同じように2つの伝え方を選べます。** 変更依頼を伝えると、まず **P900(変更要望の整理)** が次を尋ねてきます。

| 方式 | どうなるか | 向いている場面 |
| --- | --- | --- |
| **(a) ファイルで整理する** | `docs/P900-change-concept.md` という記入用のひな型が作られ、いったん処理が止まります。記入してから「続けてください」と伝えるとP901が始まります | 直してほしいことが複数ある。落ち着いて書き出したい |
| **(b) プロンプトで伝える**(既定) | 従来どおり、会話で伝えるだけです | 1〜2件の軽い修正依頼 |

**(a)のひな型は、複数の要望を1つのファイルに並べて書けます。** 1項目が1つのCRになります。各項目には次を書きます。

| 欄 | 書くこと |
| --- | --- |
| 対象 | どの画面・API・機能か |
| **現状** | **今どうなっているか。実際に見た動作・表示・エラーメッセージを具体的に** |
| **変更後** | どうなってほしいか |
| 困っていること | なぜ変えたいか |
| 変えなくてよいこと | ついでに触ってほしくない範囲(任意) |

> **「現状」を必ず書いてください。** 「〜してほしい」だけだと、変更前と変更後の差分が定義できません。差分が決まらないと、あとの工程(P904)が「本当に直ったか」を確認しようとしたときに、何を確認すればよいか決められなくなります。
> なお、まだ存在しない機能を足してほしい場合は「無い」だけでなく**どこに無いのか**(例:「予約一覧画面に絞り込みの入力欄が無い」)を書いてください。場所が分かれば、どこに足すかが決まります。

記入内容に足りないところがあれば、P901がプロンプトで質問して補ってくれます。ただし**不足が多い(4件以上)場合はいったん処理を止めて**、どこが足りないかを教えてくれます。その場合はファイルを整理し直してからもう一度実行してください。

記入したファイルは、CRへの整理が全部終わると `docs/P900-cr-concept/` へ日時付きの名前で移されて保存されます(人間が書いた原文として残ります)。各CRの「起票者」欄に、どのファイルのどの項目から起票されたかが記録されます。

伝える際に含めておくと良い情報は次の3点です。

* **何を変えてほしいか**(画面のどこに、どんな機能・項目を追加/変更してほしいか)
* **なぜ変えてほしいか**(背景・困りごと)
* **完了の基準**(「こうなっていれば直った、と言えるのはどういう状態か」がもしイメージできれば)

例えば、実際にこのSkillのテストベッドで処理された実例(`V0.7_testbed/docs/P901-cr-direction/CR-001.md`)は、次のような依頼から始まっています。

> 「ハイブリッド会議が増えたので、予約にオンライン会議URLを登録できるようにしてほしい。予約作成画面(S03)と予約詳細・編集画面(S04)で任意入力にして、S04では登録されたURLをクリックできるリンクとして表示してほしい。URLは最大500文字で、入力する場合は `http://` か `https://` で始まっていないとエラーにしてほしい。空欄のままでも予約できるようにしてほしい。カレンダー画面(S02)には出さなくていい。」

この依頼は画面2つの入力欄追加にとどまらず、API契約(予約の登録・更新・取得)とデータベース(`reservations` テーブルへのカラム追加)にまで影響します。このように、CRは「ラベル文言を直してほしい」程度の軽微なものから、「画面・API・DBにまたがる機能追加」までさまざまな粒度で構いません。優先度や影響範囲の見積もりは、人間が明示しなければAI側が仮に判断し、その判断根拠と★FIXME★を残してくれます。

なお上の例のように、**「ここは変えなくていい」を明示すると効きます**。「カレンダー画面には出さなくていい」と伝えたことで、AIはS02を対象外として記録し、実際にそのコードに手を付けませんでした。

### CRに関わる3つのファイル

CR対応では次の3つのファイルが使われます。役割がきれいに分かれているので、目的に応じて見る場所を選べます。

| ファイル | 中身 | 誰が書くか |
| --- | --- | --- |
| `docs/CR.md` | **状態の台帳**。CRの一覧と、それぞれの状態・優先度だけを持つ。本文は持たない | AI(状態が変わるたびに更新) |
| `docs/P901-cr-direction/CR-{番号}.md` | **変更要求**。何をなぜ変えてほしいか | AIが起票。**人間が後から修正してもよい** |
| `docs/P903-cr-records/CR-{番号}.md` | **対処の記録**。何をどう変えたか、テスト結果 | AI |

(V1.2でファイル方式を使った場合は、これに加えて `docs/P900-cr-concept/P900-change-concept_{日時}.md` が残ります。**人間が書いた要望の原文**であり、AIは書き換えません。上の3つがAIの整理した文書であるのに対し、これは人間の言葉がそのまま保存されたものです。)

人間が「今どのCRがどうなっているか」を知りたいときは `docs/CR.md` だけを見れば済みます。完了したCRの行も消えずに残るので、過去の依頼の一覧としても使えます。

変更要求ファイルは、AIが書き起こしたあとに人間が読んで直せます。「意図が正しく伝わっていないな」と思ったら、その場で書き換えてください。ただし**AIが作業に着手したあと(状態が「対応中」になったあと)は変更しないでください** — 作業の前提が動いてしまうためです。着手後に変えたいことが出てきた場合は、新しいCRとして伝えるのが安全です。

### CRを伝えたあとに起きること(P901〜P905)

CRを伝えると、Refactor(修正)ステップと呼ばれる一連の処理が自動的に走ります。人間がP番号を意識する必要はありませんが、内部では次のような流れになっています。

1. **P901(変更要求作成)**: 伝えた内容を正式なCRとして整理し、`docs/P901-cr-direction/CR-{番号}.md` に「タイトル/背景・課題/変更要求の内容/期待する振る舞い/影響が想定される範囲」などの項目で記録する。あわせて `docs/CR.md`(状態の台帳)に1行追加される。優先度も自動で仮置きされる(明示していれば人間の指定が優先される)。
2. **P902(要件定義更新)**: `docs/P001-requirement.md` をCRの内容に沿って更新する。更新前の原本は消さずに `docs/P001-requirement-old/` フォルダへ移して保存される(例: `docs/P001-requirement-old/P001-requirement_20260803_CR-002.md`)ので、変更前の状態にもいつでも戻って参照できる。
   * **V1.2で変わった点**: 以前は退避された原本が `docs/` 直下に置かれ、有効な `P001-requirement.md` と並んでいたため、どちらが現在有効かが分かりにくくなっていました。V1.2からは**`docs/` 直下に置かれる要件定義は常に有効な1本だけ**で、無効になった原本は `docs/P001-requirement-old/` に隔離されます。退避されたファイルの冒頭にも「この文書は無効です」という注記が入ります。
3. **P903(修正実施)**: まず着手前に「どのフェーズを対象にし、どのフェーズを対象外とするか」とその理由を `docs/P903-cr-records/CR-{番号}.md`(対処の記録)に書き出す。そのうえで、必要な設計フェーズ(P002〜P009など)と実装・テスト(P101〜P205)を、影響範囲だけに絞って再実行する。無関係な既存の仕様・実装は変更しない。作業が終わると、実際に変更したもの・事前の想定と違った点・テスト結果が同じファイルに追記される。
4. **P904(変更要求の反映確認)**: CRの「期待する振る舞い」を1項目ずつ、それを確認したテストと突き合わせて検証し、対応表を対処の記録に書く。確認できたら `docs/CR.md` の状態を「完了」に更新する。
5. **P905(ADR更新確認)**: 今回の変更が、これまでの設計方針の記録(ADR、`docs/ADR.md`)を覆すような大きな決定を伴っていないかを確認する。伴っていれば更新し、伴っていなければ「更新不要」という判断結果を対処の記録に残す。

この一連の流れも、②の初回ビルドと同様、途中で人間の確認を待たずに連続して実行されます。ただし、CRの内容がテストで確認できなかった場合は、そこで対応を打ち切らず状態を「対応中」のままにして人間に報告する、という安全弁は用意されています。

### 実例で見る対応範囲の違い

CRの規模によって、再実行される範囲は大きく変わります。過去のテストベッドで処理した実例を並べると、その幅がよくわかります。

* **小規模(画面だけで完結)**: 「予約作成画面に『終日』チェックボックスを追加してほしい」——画面設計とテスト計画の該当箇所を更新し、フロントエンドのコード1ファイルに処理を追加するだけで完了。バックエンドとデータベースは変更なしと判断され、テストも初回から全件PASSした。
* **大規模(画面+API+データベース)**: 上で挙げたオンライン会議URLの例(`V0.7_testbed` のCR-001)——画面設計・バックエンド設計・トレーサビリティ・実装計画・テスト計画を更新し、データベースにカラムを追加するマイグレーションを新規作成、バックエンドの検証/リポジトリ/サービス層とフロントエンドの入力欄・表示を実装。テストは22件+26件が追加された。設計レビュー(P010)で矛盾が1件見つかったため、当初「対象外」と見込んでいた修正フェーズが実際に動いた。

どちらのケースでも、人間が個別のフェーズに口を出す必要はなく、「CRを伝える」→「出来上がったものを確認する」という進め方は変わりません。

### 完了後に人間が確認すべきもの

CR対応が終わったら、次を見れば十分です。

* **`docs/CR.md`**: まずここで、依頼したCRの状態が「完了」になっているかを確認します。「対応中」や「反映確認中」で止まっている場合は、何かが確認できずAIが報告を出しているはずです。
* **`docs/P903-cr-records/CR-{番号}.md`**: 「何を変更したか」「何を変更しなかったか(その理由)」「期待する振る舞いをどのテストで確認したか」「テスト結果」が1つのファイルにまとまっています。変更の全体像を把握するのに最も手っ取り早いファイルです。特に「対象外としたフェーズとその理由」は、**AIが何を意図的に触らなかったか**を確認できる場所なので、依頼の意図とずれていないか目を通す価値があります。
* **テスト記録**: `docs/test-records/` 配下に、CR対応にともなうテスト実行記録が残っています。すべてPASSしているかをここで確認できます。
* 最後に、依頼した内容(`docs/P901-cr-direction/CR-{番号}.md` の「期待する振る舞い」)と、対処の記録の対応表を突き合わせて、意図通りに直っているかを人間の目で確認してください。

## FAQ / ちょっとしたトラブルシューティング

**Q. 処理が止まっているように見える(応答が長時間ない)**
初回ビルド(②)もCR対応(③)も、複数のフェーズを連続して自動実行するため、1回の指示に対する処理時間は数十分〜それ以上になることがあります。これは想定内の挙動です。本当に停止している場合は、SKILL側が「停止条件」(同じ問題を3回差し戻しても解消しない、など)に該当して人間への報告を出しているはずなので、その報告内容を確認してください。

**Q. テストが失敗したまま終わっているように見える**
初回ビルドの「Executor」ステップ(実装)では、結合テストが失敗していても記録に残すだけで先に進む設計になっています。その後の「Reviewer Loop」で失敗テストの修正が試みられ、それでも3回差し戻して解消しない場合にはじめて処理が止まり人間に報告されます。まずは `docs/P302-deliver.md` の「11. リリース判定」と「9. 最終確認結果」を確認してください。判定が `NG` や `保留` になっている場合、根拠が明記されているので、それを読めば何が未解決なのか分かります。

**Q. `docs/P302-deliver.md` の「リリース判定」が `保留` だった**
`保留` は「重大な欠陥ではないが、人間の判断が必要な軽微な未整備事項がある」状態です(例: サンドボックス環境でDockerを実際に起動確認できなかった、運用開始前に詰めるべき設定が残っている、など)。ただちに失敗というわけではないので、「9. 最終確認結果」「10. 未整備事項・人間による確認事項」を読み、実際にリリースして問題ないか、追加のCRとして対応を依頼すべきかを判断してください。

**Q. AIが仮決めした箇所を見つけたい**
`docs/` 配下のドキュメントを `★FIXME★` で検索してください。AIが要件の記述不足を自分の判断で補った箇所すべてに、その記述のすぐ隣に `★FIXME★` という目印が付いています(まとめて文末に書かれることはなく、該当箇所ごとに散らばって付いています)。

**Q. `★ACCEPTED★` という目印を見かけた。`★FIXME★` と何が違うのか**
役割が逆です。`★FIXME★` は「AIが想定で埋めた、**後で人間に確認してほしい**箇所」= 未解決の目印。`★ACCEPTED★` は「検討したうえで意識的にそう決めた、**追加の対応が要らない**箇所」= 解決済みの目印で、なぜそう決めたか・その結果どんな制約が残るかが同じ場所に書かれています。人間が確認すべきなのは `★FIXME★` の方だけです。`★ACCEPTED★` は、レビューのたびに同じ論点が何度も指摘されるのを防ぐために付けています。

**Q. 前回の続きから再開したい**
特別な操作は不要です。「続けてください」とだけ伝えれば、`docs/.inprogress`(実行中フェーズの記録)や `docs/CR.md` の状態(未対応/対応中/反映確認中)をSKILL側が自動で確認し、適切なフェーズから再開してくれます。

**Q. 一度に複数の変更をお願いしたい**
CRは「1件の要望=1つのCR」として管理する決まりになっています。複数の要望がある場合は、それぞれ別々に伝えれば、AI側で個別のCR(CR-001、CR-002、…)に分けて処理してくれます。優先度が高いものから順に対応されます。
