# Spec-Driven Dev Skill Ver1.1 → Ver1.2 改訂レポート

作成日: 2026-08-26

## 経緯

`V1.1_testbed` の実地検証では新たな不具合は見つからなかった。V1.2の契機は検証ではなく、**Skillを実プロジェクト(SysstatView)で使った人間からの申し出**である。指摘された4点はいずれも **「仕様を指示する人間」と「このSkill」のインタフェース**に関する問題であり、**内部のLoop(Plan Loop / Executor / Reviewer Loop)の構造には一切手を入れていない**。

1. 要求・要望をあらかじめファイルに整理できるようにする(P000新設)+ 入力完了の確認
2. P001完了時に、この先の進め方(工程確認 / 一気通貫)を選べるようにする
3. 変更要求(CR)の起票でも、プロンプト方式 / ファイル方式を選べるようにする(P900新設)
4. CR対応で退避される要件定義の原本を隔離する

**V0.4以降で初めてフェーズを追加した改訂**である(P000、P900)。ただしP番号の振り直しは発生していない(先頭に足しただけ)。既存フェーズの実行順序・差戻条件・停止条件は変更していない。

なお本改訂では、上記4点の実装過程で**既存記述の誤りが2件見つかり、あわせて是正した**(下記5・6)。いずれも「V0.3時代の記述の消し忘れ」および「新機能と両立しない断定」であり、次の改訂で元に戻されないよう、理由をここに明記する。

## 1. 要求・要望の事前ファイル化 (P000新設)

### 事象

`SKILL-P001-requirement.md` はインプット文書を「なし (システム設計者の中にある漠然としたアイデア)」と規定しており、**要求はプロンプトで伝えるしかなかった**。実プロジェクトで人間が自発的にファイル(`require.txt`)へ書き下した実例を確認したところ、次が書けていなかった。

* **アクションの結果が断片的** — 「表示ボタンを押すと画面2に切り替わる」はあるが、*未選択のまま押したら / 検索結果が0件だったら / 開始日 > 終了日だったら* が未定義。
* **非機能要件が皆無**、**API定義が処理名だけ**。

つまり必要なのは「ファイルに書ける」ことではなく、**何を書けば足りるのかを示すひな型**だった。

### V1.2での変更

* **`SKILL-P000-concept-analysis.md` を新設**。`docs/P000-concept-analysis.md` の有無を確認し、無ければ人間に「(a)ファイルで整理する / (b)プロンプトで伝える」の2択を提示する。(a)ならひな型を生成して**いったん処理を終える**。
* **`TEMPLATE-P000-concept-analysis-gui.md` / `-cli.md` を新設**。章ごとに【必須】【任意】を区別し、必須章が未記入ならP001へ進まない。
* **`SKILL-P001-requirement.md`** のインプット文書に `docs/P000-concept-analysis.md` を追加。

### 設計の中心: 空欄を可視化する

GUIテンプレートのアクション定義表には **「前提を満たさないとき」列**を、CLIテンプレートには **「終了コードと異常系」表**を必須で置いた。**散文で書くと書き忘れたこと自体が見えないが、表の列になっていれば空欄として目に見える。** 人間が空欄のまま出しても、P001が「異常系が未定義である」と認識できる。

これはV0.8の 2-15(「テスト実行コマンドは記載前に一度実際に実行する」)と同じ構造である。抽象的な注意喚起ではなく、**欠落が機械的に目に見える形**に置き換えている。

### 「ここで処理を終える」を停止条件にしなかった理由

V1.0で導入した `docs/.stop-report.md` は異常事象の報告先であり、**対処案の併記が義務づけられている**。P000の終了は設計どおりの正常な中断であり、提案すべき対処案は存在しない。`.stop-report.md` を書かせると、この規定の意味が薄れる。代わりに `docs/.inprogress` を `P000` のままにして再開位置を保持する方式を採った。

### ステップ0の落とし穴への対処

ステップ0は成果物の**有無**でフェーズの進捗を判定する。ひな型を生成した直後は「ファイルは存在するが中身は空」であり、この規則のままでは**「P000は完了済み」と誤判定する**。そこで `SKILL.md` のステップ0に、**P000だけは完了判定をファイルの有無ではなく中身(プレースホルダの残存)で行う**旨を明記した。

### 代筆の禁止

P000には「`docs/P000-concept-analysis.md` の空欄をAgent自身の想定で埋めない」を禁止事項として明記した。**代筆を許すと、「勝手に作り始める」問題がP000に移動するだけ**である。枠を用意するのがP000、想定で補うのがP001(そこで初めて★FIXME★が付く)、という責任分界を置いた。

### 割り切り

GUI・CLIのいずれにも当てはまらないアプリ(APIサーバ、バッチ等)は、近い方をベースに章を読み替えて使うこととし、両テンプレート冒頭に**★ACCEPTED★**で記録した(検討した代替案=形態別テンプレートの追加、却下理由=形態の網羅は際限がなく章立ての大半は共通)。

## 2. 入力完了の確認と実行モードの選択

### 事象

P001には「人間の入力が完了したか」を確認する手続きが無く、**指示が終わっていないのに納品まで走り切る**。加えて実運用では、P001後にAgentが**工程ごとの完了判断を人間に求めてくる**という、V0.4が撤廃したはずの挙動が観測された。

### V1.2での変更

* **`SKILL.md` に「実行モード」の節を新設**。`docs/.mode` に `一気通貫`(既定)または `工程確認` を記録し、以降のすべてのフェーズがこれに従う。
* **`SKILL-P001-requirement.md` に完了確認を追加**。要求の入力完了とモード選択を**1回の問い合わせにまとめて**提示する(人間から見れば「要求は出し終えた、ここからこう進めてくれ」という1つの意思決定であるため)。

### ゲートの粒度を Step 単位にした理由

**判断材料のないゲートは無価値である。** 「次へ進みますか?」だけを問うゲートは肯定の連打に堕ち、V0.4が撤廃したのはまさにその形骸化したゲートだった。そこで工程確認モードのゲートを、**溜まった★FIXME★を人間に解消させる場**と定義した。

粒度をフェーズ単位(約30回。Executorはスプリント数×4、Reviewer Loopは反復ごと)にすると人間が耐えられず、結局は形骸化する。Step単位なら最大6回に収まり、かつ `SKILL.md` は既に各Stepに「終了条件」を定義しているため、**ゲートの位置として既存の構造をそのまま使える**。Executorのスプリント反復とReviewer Loopの修正反復の内部では止まらないため、「内部のLoopには手を入れない」という今回の前提も守られる。

### ★FIXME★ の解消先をモードで分けた

* `一気通貫` — ★FIXME★は納品まで残り、**P302が全件を一覧化してCR起票候補として引き渡す**(下記4-2)。
* `工程確認` — 各Step境界のゲートで解消する。人間が「そのままでよい」と判断した箇所は**★ACCEPTED★に書き換える**(既存の記法をそのまま使い、新しい記法を増やしていない)。

### 既定を `一気通貫` にした理由

V0.4の設計思想を既定として維持し、工程確認モードを**オプトイン**にした。非対話実行で選択が得られない場合も `一気通貫` とする。`docs/.mode` が存在しない場合(V1.1以前に開始されたプロジェクト)も同様であり、後方互換性が保たれる。

## 3. 変更要求の事前ファイル化 (P900新設)

**P000 : P001 = P900 : P901** の対応として設計し、判断はできる限り1点目に揃えた(新しい流儀を発明しない)。

### V1.2での変更

* **`SKILL-P900-change-concept.md`** と **`TEMPLATE-P900-change-concept.md`** を新設。複数の要望を項目として並べられる。
* **`SKILL-P901-cr-create.md`** に、ファイル方式を入力とする場合の手順を追加。

### 設計の中心: 「現状」を必須にする

テンプレートは、各項目で **「現状」と「変更後」を隣接する必須行**に置く。「〜してほしい」だけを書くと現状の記述は自然に省略されるが、行として存在すれば埋まっていないことが見える。1点目の「前提を満たさないとき」列と同じ機構である。

これが致命的である理由は、**P904が「期待する振る舞い」をテストIDと突き合わせて検証する**ためである。変更前後の差分が定義できないと、P904が何を確認すべきか決まらない。

### 中間状態を作らない設計

`docs/P900-change-concept.md` はファイル名が固定であり、退避前は上書きの危険がある。そこで、記載内容の不足が**多数(4件以上)の場合はCRを1件も起票せずに中止する**と規定した。これにより「3項目のうち2項目だけCRになった」状態が発生しない。

結果、起こりうる中断状態は**「全項目のCRは起票済みだが、退避の直前でセッションが切れた」の1種類だけ**になり、冪等性の確認が1回の検索で済む。V0.8の「P902は冪等」と同じ考え方だが、**中間状態そのものを作らせないことで、確認すべき状態の種類を減らしている**点が異なる。

### 既存の枠を使う

出所の記録には **`TEMPLATE-P901-cr-direction.md` の既存の「起票者」節**を使い、新しい欄を足していない。同節は実質「出所」節として定義されており、`議事録への参照` や `issueへのリンク` を書く場所として既に規定されていたため、退避ファイル名+項目番号+見出し文字列がそのまま収まる。本リポジトリの原則「追加する前に、既存の規定で足りないかを問う」に従った。

項目番号だけでなく**見出し文字列も併記**させるのは、人間が項目を挿入・削除すると番号がずれるためである。

### 1項目とCRの対応

原則 **1項目 = 1CR** とし、Agentが異なる分割が妥当と判断した場合は**その判断と理由をCRの「備考」に記録**させる。CRのスコープ分類を機械化する案は既に人間の判断で却下されている(「影響分析エンジンは破綻リスクが高い」)ため、形式化せず、**判断はAIに委ね記録させる**という確立済みの原則を適用した。

### 判定閾値の再利用

記載内容の不足量の判定には、**各フェーズ共通指示の既存閾値**(4件以上、または全体の半数以上=多数)をそのまま使い、新たな基準を設けていない。

## 4. 退避された要件定義原本の隔離

### 事象

CR対応後、`docs/` 直下に `P001-requirement.md`(有効)と `P001-requirement_20260911_CR-001.md`(無効)が並び、**どちらが有効かがファイル名から判別できない**。CRを重ねるたびに退避ファイルが増える。

### これは新方針ではなく、既存原則の適用漏れ

同じ問題を、本Skillは**ADRでは既に解決している**。

```
SKILL-P021-adr.md L11:
  廃止された決定は docs/ADR_master.md に退避し、
  docs/ADR.md には現在有効な決定のみを残す。
```

「現在有効なものだけを定位置に残し、無効になったものは退避先へ移す」という原則が確立しているにもかかわらず、**P001だけが例外になっていた**。

### V1.2での変更 (4-1)

* 退避先を **`docs/P001-requirement-old/P001-requirement_{YYYYMMDD}_{CR番号}.md`** に変更(`SKILL-P902-requirement-update.md` の3箇所、`SKILL.md` の成果物一覧、`USER_GUIDE.md`)。
* **冪等性判定が退避先パスを見ている**ため、手順1・3・4のすべてを書き換えた。片方だけ直すとV0.8で作り込んだ冪等性が壊れる。
* **退避ファイル冒頭に固定書式の注記**を入れる。ディレクトリ名だけでは足りないのは、**IDEのタブや検索結果にはディレクトリ名ではなくファイル名しか出ない**ためである。本文は改変せず注記を先頭に足すだけにとどめた。
* **既存プロジェクトの移行**をP902の着手時に行う。パターンには**アンダースコアを必須で含め**、本体(`P001-requirement.md`)を誤って退避しないようにした。移行は既に無効と確定した過去のバックアップのみを対象とし、再実行しても何も起きない(冪等)。
* `SKILL-P301-root-index.md` に `docs/P001-requirement-old/` と `docs/P900-cr-concept/` を追加した。**ディレクトリ単位でリンクし配下の個別ファイルは列挙しない**という、`docs/P901-cr-direction/` `docs/P903-cr-records/` に対して従来から採っている扱いをそのまま適用している。

### 副次的な効果

ステップ0は `docs/` 配下の成果物の有無で進捗を判定する。直下に `P001-requirement_20260911_CR-001.md` のような似た名前のファイルがあることは、この判定にとって誤検知の材料でしかなかった。**退避ファイルがサブディレクトリへ移ることで、この誤検知源が構造的に消えた。**

### V1.2での変更 (4-2): 未解消★FIXME★の一覧化

2点目の一気通貫モードでは★FIXME★が納品時点まで残る。「その後CRで直す」という運用を成立させるには、**残った★FIXME★が納品物から見えなければならない**。

`SKILL-P302-deliver.md` は既に「11章の判定材料になるのは★FIXME★(未解決)および…」と規定しており、**リリース判定への算入は済んでいた**。不足していたのは一覧化だけである。そこで10章に、所在・想定で補った内容・CR起票候補かを1件ずつ書く表を追加した。

工程確認モードで完走した場合、この一覧は原理的に空になる。**空であること自体が、モードが機能した証跡**になる(0件の場合も「0件」と明記させ、表ごと省略させない)。

## 5. 既存記述の是正: `SKILL.md` 冒頭の矛盾 (V0.3時代の消し忘れ)

### 事象

V1.1の `SKILL.md` は、**3行の間で真逆のことを言っていた**。

```
L9  : 各フェーズは …成果物を生成する。**1回の実行につき1フェーズだけ**進める。
L10 : 次フェーズに必要な情報が技術的に揃っていても、複数フェーズを一度に進めてはいけない。
L12 : V0.3までと異なり、**フェーズごとに人間のレビューを待たない**。
```

### なぜ L9・L10 が異物と判断できるか

* L12が「V0.3までと異なり」と明示的に断っている対象そのものが、L9・L10の挙動である。
* フロントマターの `description`(L3)は「人間のレビューを挟まず**一気通貫**で実行し」と書いており、L12側に立っている。
* ステップ0の冒頭も「V0.4では、フェーズ完了ごとに人間の確認を待たない」と書いており、L12側に立っている。

**L9・L10だけが孤立している。** V0.4がL12を追加したときに、上を削除し忘れたものと判断した。

**これが、2点目の事象「工程ごとの完了判断を求めてくる」の根本原因である。** これを読んだAgentが「1フェーズ進めたら実行を終える = 人間に返す」と解釈するのは自然である。

### V1.2での変更

L9・L10を削除し、次に置き換えた。

* 「フェーズは必ず番号順に、1つずつ実行する。飛ばさない」— **順序を守る規定(旧L11)は残す**。削除したのは「1回の実行につき1フェーズ」という*実行の切れ目*に関する部分だけである。
* 「どこまで連続して実行するかは `docs/.mode` に従う。**フェーズ単位で処理を止めて人間に返すことは、どちらのモードでも行わない**」

## 6. 既存記述の是正: `SKILL-P901-cr-create.md` の「人間にファイルを書かせない」

### 事象

```
SKILL-P901-cr-create.md L13:
  要望は…任意の形式で示されてよい。それを本フェーズがCRの形に整理するのであって、
  **人間にファイルを書かせない**。
```

3点目でファイル方式を選択肢にする以上、この断定とは両立しない。

### V1.2での変更

「**人間にファイルを書くことを強制しない**」に改め、「ファイル方式は人間が選んだ場合の任意手段であり、**既定はプロンプト方式である**」を続けた。**趣旨(人間に書く義務を課さない)は保たれている。**

なお `TEMPLATE-P901-cr-direction.md` の「人間がこのファイルを自分で書く必要はない」は `CR-NNN.md` について述べたものであり、P900導入後も真である(P900を書いてもCR-NNNは依然AIが書く)。**こちらは変更していない。**

## 7. V1.2で変更しなかった点

* **内部のLoopの構造** — Plan Loop(P002〜P012)、Executor(P101〜P104)、Reviewer Loop(P201〜P205)の実行順序・差戻条件・停止条件はすべて現状維持。工程確認モードのゲートもこれらの**内部**には入れていない(Step境界のみ)。
* **P番号の振り直し・再グルーピング** — P000とP900を先頭に足しただけで、既存の番号は1つも動いていない。
* **★FIXME★ / ★ACCEPTED★ 以外のインライン記法** — 未記入の目印にはテンプレート内の `<!-- 記入してください: … -->` HTMLコメントを使い、**第3のインライン記法を増やしていない**。Markdownとして描画されないため、記入済みの文書に混ざっても読み手を惑わさない。
* **CR運用の3ファイル分離** — `docs/CR.md`(台帳)/ `docs/P901-cr-direction/`(要求)/ `docs/P903-cr-records/`(記録)の役割分離は維持。`docs/P900-change-concept.md` は状態も対処内容も持たない**入力の原文**にすぎず、V0.7が解消した「1ファイルが状態と本文を兼ねる」defect class を再導入するものではない。
* **上流文書へのID体系の導入** — V1.1で「行わない」と判断した方針を維持。
* **既に人間の判断で却下された論点** — P008テストIDとP102命名の構造的保証、修正ファイルの粒度規則の形式化、CRスコープ分類の自動化、マイグレーション冪等性チェックの十分性証明。いずれも再提案していない。

## 8. 「省略できる手順が無いか」の再確認

V1.1の §6 で実施した監査(出力/入力依存グラフに孤立フェーズが無いこと)の結論が、フェーズ追加後も維持されるかを確認した。

* **P000の成果物** `docs/P000-concept-analysis.md` → P001が消費する。P301の索引にも載る。
* **P900の成果物** `docs/P900-change-concept.md` → P901が消費する。退避後は `docs/P900-cr-concept/` として各CRの「起票者」節から参照される。

**いずれも孤立していない。結論は変わらない。** V1.1の §6 に記したとおり、この監査を定期的に繰り返す必要はない。
