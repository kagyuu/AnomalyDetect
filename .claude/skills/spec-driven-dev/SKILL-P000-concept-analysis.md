# 要求整理

## 目的

* 人間の要求・要望を、P001が読める形に整理する。
* 要求をプロンプトだけで伝えると、画面ごとの操作結果・非機能要件・異常系が書き漏れやすい。**何を書けば足りるのかを示すひな型**を用意することで、この書き漏れを人間が自分で気づけるようにする。
* **本フェーズは「人間に書いてもらうための枠を用意する」フェーズであり、内容を代筆するフェーズではない。** 想定で補う作業はP001の責務である。

## インプット文書

* なし (システム設計者の中にある漠然としたアイデア)
* `TEMPLATE-P000-concept-analysis-gui.md` / `TEMPLATE-P000-concept-analysis-cli.md` (ひな型の元)

## アウトプット文書

* `docs/P000-concept-analysis.md` (ファイル方式を選んだ場合のみ。**本文を書くのは人間**)

### アウトプットの記載内容

* ひな型は、対象アプリケーションの形態に応じて次のいずれかをそのまま複製する。内容を先回りして埋めない。
  * **GUIアプリ** (画面を持つもの) → `TEMPLATE-P000-concept-analysis-gui.md`
  * **CLIアプリ** (コマンドラインで動くもの) → `TEMPLATE-P000-concept-analysis-cli.md`
* テンプレート内の未記入箇所は `<!-- 記入してください: … -->` 形式のHTMLコメントで示される。これは★FIXME★・★ACCEPTED★とは別物であり、**人間がまだ書いていない箇所**を表すだけの目印である(Markdownとして描画されないため、記入済みの文書に混ざっても読み手を惑わさない)。

### アウトプットを参照する文書

* `docs/P001-requirement.md` (P001が唯一の読み手である)

## 動作

### 1. `docs/P000-concept-analysis.md` の有無を確認する

### 2. 存在しない場合 — 人間に2択を提示する

次の2つを提示し、人間に選ばせる。**勝手にどちらかを選んで先へ進まない。**

* **(a) 要求・要望をファイルの形で整理する**
  * 対象アプリケーションの形態(GUI / CLI)を人間に確認する。
  * 対応するテンプレートを複製して `docs/P000-concept-analysis.md` を作成する。
  * **ここで処理を終える。P001以降へ進まない。** 人間がひな型に記入するまで、後続フェーズには何の入力も無いためである。
  * `docs/.inprogress` は `P000` のままにする(次回のセッションが同じ場所から再開できるようにするため)。
  * 人間には、ひな型を作成したこと・記入後に再度実行すればP001から続きが始まること・必須章と任意章の区別を伝える。
  * **これは異常事象ではないため、`docs/.stop-report.md` は書かない。** 同ファイルは停止条件に該当した場合の報告先であり、対処案の併記が義務づけられている。本フェーズの終了は設計どおりの正常な中断であり、提案すべき対処案は存在しない。
* **(b) 従来どおりプロンプトで伝える**
  * `docs/P000-concept-analysis.md` は作成しない。
  * そのままP001へ進む(`docs/.inprogress` を `P001` に更新する)。

### 3. 存在する場合 — プレースホルダの残存を確認する

`docs/P000-concept-analysis.md` の中に `<!-- 記入してください:` が残っていないかを確認する。**ファイルが存在することをもって「記入済み」と判断してはならない。** ひな型を生成した直後は、ファイルは存在するが中身は空である。

**判定の単位は章・節であり、表のセル1つではない。** この区別を取り違えると本フェーズは有害になる(理由は後述)。

* **必須の章・節が丸ごと未記入**(見出しの直下に本文が無く、プレースホルダしか置かれていない)場合
  * 残っている箇所を**章・節の単位で列挙**して人間に報告し、処理を終える(`docs/.inprogress` は `P000` のまま)。
  * **未記入のひな型をP001の入力にしてはならない。** 未記入のまま先へ進むと、P001がAgentの想定でアプリケーション全体を組み立てることになり、本フェーズを設けた意味が失われる。
  * ここでも `docs/.stop-report.md` は書かない(理由は上記(a)と同じ)。
* **表のセル単位でプレースホルダが残っている**(章としては記入されているが、一部のセルだけ埋まっていない)場合
  * **停止しない。** P001へ進む。
  * P001がAgent自身の想定で補い、補った記述に★FIXME★を付ける。
  * **この区別は本テンプレート設計の要である。** セル単位の未記入で停止させると、「前提を満たさないとき」列や「終了コードと異常系」表が**空欄として欠落を可視化する**という設計の目的そのものが働かなくなる(P001が欠落を検出して★FIXME★を付ける機会が永久に来ない)。テンプレートが可視化した空欄は、**人間を止めるためではなく、P001に拾わせるため**にある。
* **任意章にのみ残っている、または何も残っていない場合**
  * P001へ進む(`docs/.inprogress` を `P001` に更新する)。
  * 任意章の未記入は、P001がAgent自身の想定で補い★FIXME★を付ける(各フェーズ共通指示の既定どおり)。

### 禁止事項

* **`docs/P000-concept-analysis.md` の空欄を、Agent自身の想定で埋めない。** ひな型の枠を用意するのが本フェーズの仕事である。想定で補うのはP001の仕事であり、そこで初めて★FIXME★が付く。ここで先回りして埋めると、「人間が書いた要求」と「AIが想定した要求」の区別が付かなくなる。
* 人間が記入した内容を、読みやすさを理由に書き換えない。誤字と思われる箇所があっても、勝手に直さずP001で確認する(誤字だと思ったものが固有名詞であることがある)。
* GUI/CLIの判断を人間に確認せずに決めない。

### 補足

* 本フェーズは、要求をファイルで受け取る手段を**任意で提供する**ものである。プロンプトで伝える従来の方式を廃止するものではなく、既定でもない。
* GUI・CLIのいずれにも当てはまらないアプリケーション(APIサーバ、バッチ処理など)については、各テンプレート冒頭の指示に従い、近い方をベースに章を読み替えて使う。
