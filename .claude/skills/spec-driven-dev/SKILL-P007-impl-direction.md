# プログラム実装定義

## 目的

* プログラム実装定義を作成して、Executor(実装担当Agent、低性能モデルを想定)にプログラム実装をさせる指示を取りまとめる。プログラム実装はExecutorが行うので、ここではコードの実装は行わない。
* 単体テストの指示は、ここで作成するプログラム実装定義で行う。
* スプリント内/モジュール間の結合テストは `docs/P008-test-direction.md`(P008)で、スプリントをまたぐ結合テスト・システムテスト・受け入れテストは `docs/P009-acceptance-direction.md`(P009)で、それぞれ別途指示するので、ここでは指示しない。

## インプット文書

* `docs/P002-frontend-spec.md`
* `docs/P003-backend-spec.md`
* `docs/P005-impl-plan.md`
* `docs/P006-test-plan.md`

## アウトプット文書

* `docs/P007-impl-direction.md` (目次 OKF形式)
* `docs/P007-impl-direction/U000-{sprint-name}.md` (各スプリントの実装指示、000はスプリント番号(実行順))

### アウトプットの記載内容

* 目次は OKF 形式(`SKILL.md` の「目次(OKF形式)について」参照)で作成して、各スプリントの実装指示へのリンクを保持する
* 実装指示は、スプリントごとに行い `docs/P007-impl-direction/U000-{sprint-name}.md` に分割して記載する
  * `TEMPLATE-P007-impl-direction.md` の構成に則る
* コードの格納先は、現在作業中のディレクトリ配下に、アプリケーション名のディレクトリを仮定する
  * 単一アプリの場合は `app/` とする
  * クライアント・サーバ型の場合は `client/` `server/` とする
  * 実装指示には、どのアプリの何を変更する・作成するかを明記する
* 目次・見出し・概要文などに、使用する技術スタック名(例: 「React+TS+Vite」のような具体的なフレームワーク・ライブラリ名)を直接ハードコードしない。技術スタックは環境制約などにより代替実装に置き換わることがあり(例: サンドボックス環境でパッケージレジストリに接続できない場合)、ハードコードした記述はその際に陳腐化する。代わりに「フロントエンド技術(`docs/ADR.md`参照)」のようにADRへの参照で表現し、該当するADR-NNNを明記する。実装内容の詳細な説明の中で技術名に言及すること自体は問題ない(そこはハードコードの是非を問わない)が、目次・見出し等の陳腐化しやすい箇所ではADR参照を優先する。
* コードの格納先の初期化は、**本フェーズでは実行しない**。最初のスプリントの最初のタスク(`U0NN-T1`)の【実装内容】に、初期化の手順として書く(実際に初期化を行うのはExecutor、P102である)。本フェーズは指示書を書くフェーズであり、コードの実装・ディレクトリの初期化は行わない(前述「目的」参照)。
  * コードの格納先がすでにある場合は、初期化のタスクを書かない。
  * コードの格納先を新たに作る場合は、実装言語・フレームワークの標準のビルドツールによる初期化を、タスクの【実装内容】に明記する。どのビルドツールを前提とするかは次を目安とする。
    * Java : maven でビルドすることを前提にする
    * Python : uv でビルドすることを前提にする
    * React : npm でビルドすることを前提にする
    * Angular : ng でビルドすることを前提にする
  * 初期化タスクの【実装内容】には、「`{ツール名}` 相当の構成で初期化する」という書き方を用いる。Executorが着手する時点では、コード格納先のディレクトリが既に存在し `{ソースツリー}/INDEX.md`(P020の成果物)を含んでいるため、スキャフォールドツールをそのまま実行できない場合があるためである(詳細は `SKILL-P102-implement.md` 参照)。
* Executorに判断を残しすぎない。Executorは、このドキュメントを作っている計画担当Agent(高性能モデル)よりも低性能なので、各タスクには具体的に書く。
  * 目的
  * 作成・編集対象ファイル
  * 参照すべき仕様箇所
  * 実装内容
  * 実装してはいけないこと
  * Unit Test内容
  * 実行コマンド
  * 完了条件
  * 次タスクに進む前の停止条件
* Executorが一度に多くのことを考慮しなくてよいように、タスクは次のような観点で分割する。
  * 型・スキーマ・データモデルなどの土台
  * バリデーションや純粋関数
  * Repository / DAO などのデータアクセス層
  * Service / UseCase 層
  * API handler / Controller 層
  * Frontend component / page
  * 画面とAPIの接続
  * エラー処理・認証・認可などの横断機能
  * 結合確認用の薄いタスク
* 上記は分割を検討する観点であり、1観点=1タスクにする必要はない。関連が強い観点(例: Repository層・Service層・APIハンドラ層)は1タスクにまとめてよい。Executorが把握しきれない量にならないよう、1スプリントあたり目安4〜6タスク程度に収まるよう関連する観点をまとめること。
* Repository/DAO層のタスクを書く際は、関数シグネチャに**現在時刻・現在日付を暗黙に取得させない**(内部で`datetime.now()`のようなシステム時計呼び出しを行わせない)。「今日」「現在」を基準にした絞り込み(例: 期限切れ判定、当日以降の予約一覧)が必要な場合は、呼び出し側(Service層)が計算した具体的な日時をRepository関数の引数として明示的に渡すシグネチャにする。これは単体テストで日時を固定するために必要であり、この方針をタスクの【実装内容】に明記すること。
* 1スプリント分の実装指示 `docs/P007-impl-direction/U000-{sprint-name}.md` の中に、複数のタスクを `TEMPLATE-P007-impl-direction.md` の構成どおり記載する。タスクIDは `U0NN-Txx`(`U0NN` はスプリント番号、`Txx` はスプリント内のタスク連番。例: `U001-T1`)とする。各タスクは、スプリントファイル冒頭の「タスク一覧」に `[ ]`/`[~]`/`[x]` のチェックボックス付きOKF副目次として列挙し、タスクの進捗はここで個別に追跡する(`docs/P007-impl-direction.md` 側のスプリント単位チェックボックスとは別の、1段細かい粒度。詳細は `SKILL.md` の「目次(OKF形式)について」参照)。
* 実装指示には Unit Test を必ず含める
  * `docs/P006-test-plan.md` の単体テストの観点に則って、Unit Test の実装指示を行う
  * テストの実装指示には以下を明記する。
    * テスト対象
    * 正常系テスト
    * 主要な異常系テスト
    * 実行するテストコマンド
    * 合格条件
  * テストが難しいタスクの場合でも、「なぜUnit Testが難しいか」を書いて逃げるのではなく、最低限テスト可能な単位を切り出す。
    * バリデーション関数
    * APIハンドラ
    * Repository/Service層
    * UIコンポーネントの表示・イベント
    * 設定読み込み処理
* スプリント内/モジュール間の結合テストの実施指示は行わない。これは `docs/P008-test-direction.md` 側の対象として扱う(重複して指示しない)。
* 仕様外の拡張を禁止する
  * `docs/P002-frontend-spec.md` `docs/P003-backend-spec.md` にない画面・API・DB項目・業務ルールを勝手に追加しないよう指示する
* 不足や矛盾を見つけた場合は、実装タスクに含めず、`docs/P007-impl-direction.md` の「未解決事項」に記載する。
* スプリントの実装(該当する Unit Test を含む)が完了したら、ExecutorはP102の一部として `docs/P007-impl-direction.md` の該当スプリント行のチェックボックスを `[x]` に更新する。全スプリントが `[x]` になるまでP007(の実行対象であるスプリント群)は完了しない。

### アウトプットを参照する文書

アウトプットの記載内容は、次の文書を作成できる程度に具体的であること

* Executorが、実装指示のみを参照してコードの実装を行う(P102)。

## 動作

* 共通指示に加えて、上記アウトプット記載内容に定めた事項に従う。
