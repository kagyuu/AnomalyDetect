# ユーザインタフェース設計

## 目的

* ユーザインタフェース設計書を作成して、フロントエンドの仕様を確定する。

## インプット文書

* `docs/P001-requirement.md`
* `docs/ADR.md` (既存のADRがあれば)
* `docs/P901-cr-direction/CR-NNN.md` (Refactorステップからの再入時。対応中の変更要求の本文。対象CRの特定には状態の台帳 `docs/CR.md` を見る)

## アウトプット文書

* `docs/P002-frontend-spec.md`

### アウトプットの記載内容

* `docs/P001-requirement.md` の画面一覧にある全入力項目のバリデーションルール(必須・形式・文字数・範囲など)
* `docs/P001-requirement.md` のAPI一覧にある全エンドポイントの完全な外部仕様(メソッド、パス、リクエストボディ/パラメータ、レスポンス形式、ステータスコード、エラーケース)
* ユーザインタフェースを成立させるためのデータモデル: ER図 + テーブル定義書(主要カラム・型・制約・リレーション)
* 複雑な処理フロー(複数のユーザインタフェースをまたぐ処理など)があれば、シーケンス図で流れを明確化する

`docs/P001-requirement.md` になかった画面やAPIをここで新たに追加しない。詳細化の過程でスコープの抜け漏れに気づいた場合は、勝手に拡張せず明示的に指摘すること。

* 非機能要件のうちインフラ寄りの項目(可用性・TLS・スケーラビリティ・ログ集約基盤など)は、原則としてP002では確定させない。`docs/P003-backend-spec.md` 側でP005(実装計画)/P302(納品物作成)への委譲が明記される(詳細は `SKILL-P003-backend-spec.md` 参照)。P004・P010の充足確認は、この委譲先の記載を根拠として判定してよい。
* フェーズP002とP003の役割分担が曖昧になりやすい記載(例: 認証方式)について
  * 外部から見える契約(例: ログインでCookieを使うのかトークンを返すのか、レスポンス形式、クライアントが認識できるエラーコード)はこのフェーズP002で確定する。
  * その内部実現方法(例: パスワードのハッシュ方式、セッションの保存先・有効期限)はフェーズP003(`docs/P003-backend-spec.md`)で確定する旨を、該当箇所に明記すること。
  * この相互参照は、P002・P003どちらで決めるべきか判断に迷う項目についてのみ行えばよい。役割分担が明確な項目(例: 単純なCRUD API)にまで機械的に付ける必要はない。
* CR(`docs/P901-cr-direction/CR-NNN.md`)にもとづく再入時は、CRで指定された変更点のみを反映し、無関係な既存記述は変更しない。何をCRの何番にもとづいて変更したかを本文中に明記する。

### アウトプットを参照する文書

アウトプットの記載内容は、次の文書を作成できる程度に具体的であること

* `docs/P003-backend-spec.md`
* `docs/P004-traceability-matrix.md`
* `docs/P005-impl-plan.md`
* `docs/P006-test-plan.md`
