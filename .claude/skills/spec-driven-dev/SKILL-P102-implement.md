# プログラム実装

## 目的

* `docs/P007-impl-direction.md` の目次で未完了(`[ ]`または`[~]`)になっている先頭のスプリントについて、対応する `docs/P007-impl-direction/U000-{sprint-name}.md` を実行し、実装と単体テストを行う。
* ここで行うのはコードの実装と単体テストのみである。結合テストの実行はP103で行う。

## インプット文書

* `docs/P101-impl-context.md`
* `docs/P007-impl-direction/U000-{sprint-name}.md` (着手対象の1スプリント分)
* `docs/P008-test-direction/` のうち、着手対象スプリントに関連する `T0NN-*.md`(結合テストが対象とするテスト関数名・実行コマンドを、実装するコード側の命名と一致させるため。詳細は下記「動作内容」参照)
* `docs/ArchitectureHandbook.md` / `docs/ADR.md` (詳細確認が必要な場合)

## アウトプット文書

* `{application root}/` 配下のソースコード(新規作成・編集)
* 単体テストコードと、その実行結果

### 動作内容

* `docs/P007-impl-direction/U000-{sprint-name}.md` の「タスク一覧」を確認し、`[x]` でない先頭のタスクから実施する。着手したタスクは直ちにチェックボックスを `[~]` に更新し、完了条件をすべて満たしたら `[x]` に更新する(`TEMPLATE-P007-impl-direction.md` 参照)。この更新は、スプリント全体が終わるまで待たず、**タスク完了のたびに**行う。
  * `docs/P007-impl-direction.md`(親の目次)側のスプリント単位チェックボックスは、スプリント内の全タスクが `[x]` になった時点で初めて `[x]` にする。1件以上のタスクが `[~]`/`[x]` で残りが `[ ]` の場合は `[~]` にする(スプリント途中であることが親の目次からも分かるようにするため)。
  * **中断からの再開**: セッションが中断した場合、対象スプリントファイルの「タスク一覧」を確認する。`[~]` のタスクがあれば中断時点の作業対象だが、`[~]` という状態だけでは進捗の実態(どこまでファイルが書けているか)は分からないため、必ず該当タスクの【完了条件】(単体テストなど)を実際に再実行して現状を確認してから、続きを行うか最初からやり直すかを判断する。まだ `[ ]` の後続タスクについて、ファイルが部分的に存在していても「先行実装の形跡」であり「完了」ではない。
  * **先行実装の禁止**: `[~]` のタスクを進める間、まだ `[ ]` の後続タスク(同一スプリント内・他スプリントとも)が対象とするファイルには着手しない。どこまでが完了でどこからが先行実装かを、中断時に区別できなくするため。
* **コード格納先の初期化について**: 最初のスプリントの最初のタスクに、コード格納先の初期化手順が書かれている場合は、それに従って初期化を実行する(初期化は計画フェーズであるP007ではなく、本フェーズの作業である)。コード格納先が既に初期化済みの場合は何もしない。初期化タスクも他のタスクと同じ扱いであり、完了条件の確認・チェックボックスの更新・中断時の再確認は、下記の一般ルールがそのまま適用される(初期化専用の特別な再開処理は設けない)。
  * **既存ディレクトリへのスキャフォールドに注意する**。本フェーズが着手する時点では、P020(実装構造生成)が既にコード格納先のディレクトリを作成し、その中に `{ソースツリー}/INDEX.md` を配置している。したがってディレクトリは**空ではない**。
    * スキャフォールドツールを**対話モードで実行しない**。空でないディレクトリに対して `npm create vite@latest .` のようなコマンドをそのまま実行すると、「Current directory is not empty. Remove existing files and continue?」のような対話プロンプトで停止し、無人実行が進まなくなる。
    * ツールをその場で実行する代わりに、そのツールが**生成する構成と同等になるようにファイルを配置してよい**(P007の指示が「`{ツール名}` 相当の構成で初期化する」と書かれているのはこのためである)。非対話オプションが利用できる場合はそれを使ってもよい。
    * **既存の `{ソースツリー}/INDEX.md` を削除しない**。これはP020の成果物であり、P104(実装構造修正)・P301(全体INDEX作成)が更新・参照する前提になっている。スキャフォールドツールが既存ファイルを消す動作をする場合は、そのツールをその場で実行してはならない。
* タスクの範囲外のファイルは編集しない。ただし、後続スプリントでのスキーマ変更・仕様変更により前スプリントの既存テストが構造的に無効化された場合(例: マイグレーションファイルの追加でバージョン一覧を検証するテストが壊れる)は、そのテストの更新を「範囲外の編集」とはみなさない。この場合、どの変更によりどのテストが無効化されたかをタスクの完了条件確認時に記録する。
* テストコード(単体テスト、および結合テスト対象になりうるコード)を実装する際、対応する `docs/P008-test-direction/T0NN-*.md` が既に実行コマンドとして具体的なテスト関数名・ファイルパス(例: `tests/test_api_auth.py::test_login_success_then_me`)を明記している場合は、実装するテストコードの関数名・ファイル名をその記載と厳密に一致させる。これは、P103(結合テスト実行)がP008に書かれた実行コマンドをそのまま実行できるようにするためであり、勝手に別の名前を付けない。該当するP008のテストがまだ書かれていない、または対象スプリントの範囲外である場合は、この限りではない。
  * ★ACCEPTED★ P008のテストIDと本フェーズの実装命名の対応づけを、**構造的に保証する仕組み(命名規約の自動検証、ID対応表の機械的な突き合わせなど)は作らない**。検討はしたが、この種の自動検証は言語・テストフレームワークごとの命名規則の差異を吸収しきれず複雑化し、破綻しやすい(検証器自体が誤検知を出すようになり、やがて無視されるようになる)ため採用しなかった。上記の「P008の該当 `T0NN-*.md` を本フェーズのインプットに含める」+「記載された名前と厳密に一致させる」という指示が、この点に対する**恒久的な回答**である。残る制約は、一致の保証がAgentの遵守に依存することだが、不一致はP103(結合テスト実行)がP008の実行コマンドをそのまま実行した時点で必ず顕在化するため、検出は後段で担保される。この論点は判断済みであり、再度の指摘は不要。
* 各タスクの完了条件(Unit Test成功など)を満たしたことを確認してから、次のタスクに進む。
* 1つのタスクで単体テストが3回自己修正しても合格しない場合は、これ以上進めず処理を停止して人間に報告する(Executor Stepの停止条件)。
* 未完了スプリントが他にもある場合は、続けて次のスプリントのP101〜P102を実行する。すべてのスプリントが `[x]` になったら、P103(結合テスト実行)に進む。
  * `docs/P008-test-direction/T000-*.md` にスプリント名(例: 「Sprint 3」)が付されている場合、これはテストを整理するためのラベルであり、実行単位ではない。P103はスプリント単位で分割実行せず、全スプリントのP102完了後に `docs/P008-test-direction.md` の全T0NNタスクをまとめて実行する(詳細は `SKILL-P103-integration-test.md` 参照)。
* 仕様外の拡張(`docs/P002-frontend-spec.md` `docs/P003-backend-spec.md` にない画面・API・DB項目・業務ルール)を行わない。矛盾や不足に気づいた場合は、実装を進めず `docs/P007-impl-direction.md` の「未解決事項」に記載する。
