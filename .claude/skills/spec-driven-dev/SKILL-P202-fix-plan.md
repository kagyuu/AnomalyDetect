# 修正計画

## 目的

* `docs/P201-review-report.md` で列挙された、PASS以外(FAIL/BLOCKED)のテストを選び出して修正する計画をつくる。
* この時点でこのフェーズ自体が修正を行うのではなく、修正を行うための手順を修正指示書に取りまとめる。修正の実行はP203で行う。
* 修正指示は、原則として失敗したテスト1件について1ファイル作成する `docs/P202-fix-plan/F000-{fix-name}.md` (000は連番、fix-name は修正概要)。ただし、複数の失敗テストが単一の根本原因に起因すると判断できる場合の例外を認める(詳細は下記「アウトプットの記載内容」参照)。
* 修正はReviewer Loop(高性能モデル)が行うことを前提にする。

## インプット文書

* `docs/P001-requirement.md` 〜 `docs/P009-acceptance-direction.md`
* `docs/P201-review-report.md`
* `docs/test-records/YYYYMMDD-HHMM-test-record.md` (最新のもの)

## アウトプット文書

* `docs/P202-fix-plan.md` (目次 OKF形式。個々の修正指示 `docs/P202-fix-plan/F000-{fix-name}.md` へのリンクを保持する)
* `docs/P202-fix-plan/F000-{fix-name}.md` (個別の修正指示、000は連番、fix-name は修正概要)

### アウトプットの記載内容

* 作成する修正指示書の目的を明確化する
  * `docs/P201-review-report.md` に記載されている、PASS以外(FAIL/BLOCKED)のテストを修正する
  * 単体テスト、スプリント内の結合テスト(P007・P008)は、Executor実行時にすべて合格していることを前提とする
  * 修正するのは、次の種類のテストの失敗となる(いずれもP009 受け入れ結合テスト、または未解決のままP201に持ち込まれたP008結合テストの失敗)。
    * 複数モジュール間の連携テスト
    * 複数APIをまたぐ業務フローのテスト
    * 画面とAPIの接続テスト
    * 画面遷移を含むシナリオテスト
    * DB・Repository・Service・APIの組み合わせ確認
    * 認証・認可をまたぐ処理確認
    * エラーハンドリングの一連の確認
    * 外部APIやモックサービスを含む連携確認
    * システムテスト相当の主要シナリオ確認
    * 非機能テストのうち、実行可能な範囲の性能・負荷・セキュリティ観点確認
* 修正指示は、原則として失敗したテスト1件について1ファイル作成する `docs/P202-fix-plan/F000-{fix-name}.md` (000は連番、fix-name は修正概要)
  * 記載内容は `TEMPLATE-P202-fix-direction.md` の構成に則る
  * **例外(複数テスト1根本原因)**: 複数の失敗テストの原因調査を行った結果、同一の根本原因(例: 特定のCookie属性の設定ミス1箇所など)に起因すると判断できる場合は、それらをまとめて1件の修正指示ファイルにしてよい。この場合、`TEMPLATE-P202-fix-direction.md` の【対応する失敗テスト】欄に、対応するすべてのテストID(T0xx/A0xxの一覧)を明記する。1テスト1ファイルの原則を無条件に崩してよいわけではなく、「同一の根本原因であると具体的に説明できる」ことを条件とする。単に「関連がありそうだから」ではまとめない。
    * ★ACCEPTED★ 1つの根本原因が多数のテストに波及した場合の、修正指示ファイルの粒度について、**形式的な基準(「N件までは1ファイル」「同一モジュール内に限る」といった数値・構造による線引き)は設けない**。検討はしたが、この種の形式化はAIが苦手とするところで、基準を満たすかどうかの判定自体で誤りが増え、本来まとめるべきものを分割する/分割すべきものをまとめる、という別種のブレを生むため採用しなかった。上記の条件付き例外(「同一の根本原因であると具体的に説明できること」)が、この点に対する**恒久的な回答**である。残る制約は、粒度の妥当性がAgentの説明の質に依存することだが、説明が修正指示ファイルに残るため人間が後から検証できる。この論点は判断済みであり、再度の指摘は不要。
    * まとめた場合も、`docs/P202-fix-plan/P202-fix-resolved.md`/`docs/P202-fix-plan/P202-fix-unresolved.md`(`TEMPLATE-P202-fix-resolved.md`/`TEMPLATE-P202-fix-unresolved.md`)の「対応障害」列には、そのF0xxが対応する全テストIDを列挙し、トレーサビリティ(どのF0xxがどのテストの失敗に対応したか)を失わないようにする。
* `docs/P202-fix-plan.md` は OKF 形式(`SKILL.md` の「目次(OKF形式)について」参照)の目次とし、各 `F000-{fix-name}.md` へのリンクを保持する。修正が完了した項目はチェックボックスを `[x]` に更新する。
* **結果区分「テスト指示側の誤り」**: 障害の原因調査を行った結果、失敗の原因がアプリケーションコードの欠陥ではなく、**テスト指示自体が上位文書(`docs/P002-frontend-spec.md`・`docs/P003-backend-spec.md` 等)と矛盾している、またはテスト指示内で自己矛盾している**と判明した場合は、これを「テスト指示側の誤り」として扱う。この区分は、コードの欠陥修正と同格の一級の結果区分であり、副次的な事後処理として埋め込まない。
  * 判定には証拠を要件とする: 矛盾する上位文書の該当箇所を引用すること、修正によって検証カバレッジが失われないこと(同じ観点を確認する他のテストが存在すること、または新設すること)を明記すること。
  * この場合の修正指示ファイルには、【修正方針】に「テスト指示側の誤り」である旨と上記の証拠を書き、コード修正は行わない。`TEMPLATE-P202-fix-resolved.md` の「変更したソースコード」欄には「なし(テスト指示側の誤りのため、`docs/P009-acceptance-direction/A0NN-*.md` 等を修正)」のように明記してよい(この欄は必須だが「なし」を許容する)。
  * P205(結合テスト再実施)における「期待値改ざん禁止」は、この区分による期待値修正を妨げない。**改ざん**(失敗を回避する目的で期待値を弱体化させること)と、**訂正**(上位仕様に合わせて誤っていた期待値を是正すること)は別物であり、訂正は上記の証拠とともに許可される。
* 作成する修正指示書に記載する修正のルール
  * 修正担当はReviewer Loop(高性能モデル)を前提にする
    * 各種設計書、実装コード、テストコードを参照するため、Executorよりも高性能なモデルを使う
    * 原因調査や複数ファイル横断の分析を許可してよい。
    * ただし、一度にひとつずつ修正を行い、範囲を無制限に広げてはいけない。各修正タスクには、対象障害、対象テスト、想定影響範囲、確認すべきファイルを具体的に書く。
  * ソースコードの試行錯誤は許可する
    * 原因調査のために以下を行ってよい。
      * ソースコードを読む
      * 関連する設定ファイルを読む
      * 失敗したテストを再実行する
      * 小さな修正を試す
      * ログを追加して原因を確認する
      * 修正案を複数比較する
    * ただし、試行錯誤する場合は、開始前に作業前状態を確認するよう指示する。
      * Git管理されている場合は、作業開始時点の状態を記録する。
      * そうでない場合は、資産一式を圧縮ファイルにして退避する。ファイル名は `{アプリケーション名}-YYYYMMDDHHMMSS.zip` などとし、**保存先はプロジェクトのソースツリー・`docs/`のいずれの外側**(例: リポジトリルートの外、または `/tmp` 相当の作業用ディレクトリ)とする。ソースツリー内に置くと納品物や `git status` を汚すため避ける。
  * 修正成功時は関連する docs/* も更新する
    * 障害修正が成功した場合、関連する `docs/*` も確認し、必要に応じて更新する。
    * 更新が必要なケース:
      * 実装が仕様書と異なっていたため、仕様通りにコードを修正した → 原則として仕様書は変更しない。修正結果のみ記録する。
      * テスト指示や期待結果に誤りがあった(上記「結果区分『テスト指示側の誤り』」に該当) → `docs/P009-acceptance-direction.md` および `docs/P009-acceptance-direction/A000-{test-name}.md` (またはP008側)を修正する。
      * CRによるAPI契約変更で、既存テストが検証していたリクエスト/レスポンス全体の期待値が仕様どおり変化した(例: レスポンスに項目が増え、全体一致比較のテストが必然的に落ちる) → 該当テストの期待値を新しい仕様に合わせて更新する。これは「失敗を隠す改ざん」ではなく「契約変更への正当な追随(訂正)」であるため、更新箇所ごとに対象テストID・更新理由・根拠とする仕様変更箇所を、修正指示ファイルおよび `docs/P202-fix-plan/P202-fix-resolved.md` に明記する。
      * 仕様書に曖昧さがあり、コード修正時に解釈を明確化した → 関連する仕様書に明確化内容を追記する。ただし、仕様判断を伴う場合はP204(影響分析)で扱う。
      * ADRの決定自体は正しいが、その前提条件が本実行環境ではまだ実現されていない(例: ADRはTLS終端の存在を前提にしているが、本環境にはTLS終端コンポーネントがない) → コード・テスト・仕様書のいずれも変更しない。かわりに、環境上の制約であることを既知の制約として記録する(`docs/P302-deliver.md` の「未整備事項・人間による確認事項」、または `docs/P202-fix-plan/fixed/F000-{fix-name}.md` 内の既知の制約として明記する)。ADRやコードを、実現されていない前提に合わせて書き換えない。
  * 修正しきれない場合は試行錯誤したソースコードを元の状態に戻す
    * 障害を修正しきれない場合、試行錯誤で変更したソースコードを元の状態に戻すよう指示する。
    * 既に修正に成功した別障害の変更まで戻してはいけない。
    * 自分が試行錯誤で変更した未完了の変更だけを戻す。
    * Git管理されていない場合は、作業前に保存した差分またはバックアップをもとに戻す。
  * 障害を修正できた場合(P203で行う)
    * 修正指示 `docs/P202-fix-plan/F000-{fix-name}.md` を `docs/P202-fix-plan/fixed/` にコピーする
    * 修正内容の詳細を `docs/P202-fix-plan/fixed/F000-{fix-name}.md` に追記する
      * この障害について、過去のループ(P202〜P205の差し戻し)で未修整記録 `docs/P202-fix-plan/P202-fix-unresolved.md` に該当箇所が**既に存在する場合は**、その内容を修正内容の詳細の修正経緯にコピーしたうえで、未修整記録側の該当箇所を削除する。今回のループで初めて着手し、これまで未修整記録に記載が無かった障害の場合は、コピー・削除の対象が無いためこの手順は不要である(スキップしてよい)。
    * 修正内容の概要を `docs/P202-fix-plan/P202-fix-resolved.md` に記載する。記載内容は `TEMPLATE-P202-fix-resolved.md` に則る
    * 修正指示 `docs/P202-fix-plan/F000-{fix-name}.md` を削除する。
    * `docs/P202-fix-plan.md` の該当行のチェックボックスを `[x]` に更新すると同時に、リンク先を移動後のパス `docs/P202-fix-plan/fixed/F000-{fix-name}.md` に書き換える(削除済みの元パスへのリンクをそのまま残さない)。
  * 障害を修正できなかった場合
    * 修正できなかった理由を未修整記録 `docs/P202-fix-plan/P202-fix-unresolved.md` に追記する。記載内容は `TEMPLATE-P202-fix-unresolved.md` に則る。
    * 原因が仕様の矛盾・仕様不足である場合は、必ずその旨を書き、P204(影響分析)を経て人間への申し送り事項として `docs/P302-deliver.md` に残す
      * 例: "未解決理由: docs/P003-backend-spec.md では 404 を返す仕様だが、docs/P006-test-plan.md では空配列 200 を期待している。どちらを正とするか人間の判断が必要。"

### アウトプットを参照する文書

アウトプットの記載内容は、次の文書を作成できる程度に具体的であること

* P203(修正実施)が、修正指示のみを参照して調査・修正を行う。
* `docs/P302-deliver.md` (P302) が、本フェーズの解決済み・未解決の状態を確認する。
