# 結合テスト定義(スプリント内/モジュール間)

## 目的

* 結合テスト定義を作成して、Executor(実装担当Agent、低性能モデルを想定)に結合テストをさせる指示を取りまとめる。実行はP103でExecutorが行うので、ここでは実行は行わない。
* 単体テストの指示は `docs/P007-impl-direction.md`(P007)で行うので、ここでは指示しない。
* ここでは、各スプリントに閉じて実行できる結合テスト、および同一スプリント内の複数モジュール間の連携テストの指示を行う。スプリントをまたぐ結合テスト・システムテスト・受け入れテストは `docs/P009-acceptance-direction.md`(P009)で指示するので、ここでは指示しない。

## インプット文書

* `docs/P002-frontend-spec.md`
* `docs/P003-backend-spec.md`
* `docs/P005-impl-plan.md`
* `docs/P006-test-plan.md`
* `docs/P007-impl-direction.md` (目次 OKF形式) および各 `U000-{sprint-name}.md`

## アウトプット文書

* `docs/P008-test-direction.md` (目次 OKF形式)
* `docs/P008-test-direction/T000-{test-name}.md` (000はテスト番号(実行順)、test-name はテスト名)

### アウトプットの記載内容

* 目次は OKF 形式(`SKILL.md` の「目次(OKF形式)について」参照)で作成して、各テストタスクへのリンクを保持する
* テスト指示は、テストケースごとに行い `docs/P008-test-direction/T000-{test-name}.md` に分割して記載する
  * `TEMPLATE-P008-test-direction.md` の構成に則る
* 対象とするテスト範囲(いずれも同一スプリント内で完結するもの)
  * 同一スプリント内の複数モジュール間の連携テスト
  * 画面とAPIの接続テスト(同一スプリント内で実装が閉じているもの)
  * DB・Repository・Service・APIの組み合わせ確認(同一スプリント内)
  * このSkillでは、純粋な関数単位のUnit Testは主対象にしない(それらは `docs/P007-impl-direction.md` 側で指示済みの前提とする)。スプリントをまたぐ確認や、認証・認可をまたぐ横断確認、システムテスト相当の確認は `docs/P009-acceptance-direction.md` 側の対象とする。
* テスト前に必ず対象スプリントの全モジュールをビルドするよう指示する
  * ビルド手順には以下を明記する。
    * ビルド対象
    * ビルドコマンド
    * 成功条件
    * 失敗時の記録方法
    * ビルド失敗時はテストへ進まないこと
* テスト失敗時にその場で修正しない
  * Executorには、テスト失敗時にコードを修正させてはいけない。必ず以下を指示する。
    * アプリケーションコードを修正しない
    * テストコードをその場で都合よく変更しない
    * 失敗したテストをスキップしない
    * 期待値を変更して成功扱いにしない(=改ざん。ただし、対象テストのコードがまだ存在せず本フェーズの指示に従って新規作成する場合は、これに該当しない。改ざんが禁止するのは「既存のテストコードを、失敗を回避する目的で書き換えること」であり、新規作成そのものは妨げない)
    * 同じ失敗に対して場当たり的な再テストを繰り返さない
    * 失敗内容をテスト記録に残す
    * 次工程(Reviewer Loop)の修正フェーズに引き渡す
* テスト記録を必ず残させる
  * 記録先 `docs/test-records/YYYYMMDD-HHMM-test-record.md`
  * 記録形式は `TEMPLATE-test-record.md` に定める共通形式(P008・P009・P103・P201・P205で共通)に従う。

* テストタスクを小さくする
  * 1つのテストタスクは、原則として以下の範囲に収める。
    * 1つの画面/API連携
    * 1つのモジュール間連携
    * 1つのエラー系シナリオ
  * 避けること
    * 「スプリント内の全画面をテストする」
    * 「正常系と異常系を全部まとめて確認する」
    * 「失敗したら直して成功するまで回す」
* 低性能モデル(Executor)向けに具体的に書く
  * 各テストタスクには、少なくとも以下を含める。
    * 目的
    * 対象モジュール
    * 前提条件
    * 使用するテストデータ
    * 事前準備
    * 実行手順
    * 実行コマンド
    * 期待結果
    * 合否判定基準
    * 失敗時に記録する内容
    * 修正禁止事項
    * 次タスクへ進む条件
  * 永続化されたデータストアを使うテストの「事前準備」には、`docs/P006-test-plan.md` が定めたテストデータのライフサイクル方針(ベースラインへ復元する単位と、ベースラインの定義)に従った手順を書く。ここで独自に方針を決めない。復元をテストスイートの実行ごとに行う方針の場合、個々のテストに復元手順を書くのではなく、**スイート全体で1回だけ、かつテスト対象アプリケーションを起動する前に**実行されるようにする。
    * 「テストごとに復元」は避ける(先行するテストが用意したデータまで消してしまうため)。
    * **復元はテスト対象アプリケーションの起動より前**に行う。起動後に復元すると、アプリケーションが既に開いているデータストアを外から作り替えることになり、動作が不安定になる。テストフレームワークが提供する初期化フック(Playwrightの `globalSetup` など)は、アプリケーションの起動より**後**に実行される場合があるため、フックの実行順序を必ず確認すること。順序が保証できない場合は、アプリケーションの起動コマンド自体に復元処理を含める。
  * テストデータの値は、実行のたびに一意になるようにするか、上記の復元によって前回実行分が残らないようにするかの、いずれかで重複を避ける。**一意化だけに頼らないこと**: 一意化は同名要素の重複は防げるが、「一覧が N 件であること」のような件数を検証するテストには効かない。
* テストタスクが完了したら(PASS/FAIL/BLOCKEDいずれの結果であっても記録が残った時点で)、Executorは `docs/P008-test-direction.md` の該当テスト行のチェックボックスを `[x]` に更新する。全テストが `[x]` になるまでP103は完了しない。ただしFAIL/BLOCKEDが残っている場合は、Reviewer Loop(P201〜)への引き渡しが必要である旨を目次に明記する。

### アウトプットを参照する文書

アウトプットの記載内容は、次の文書を作成できる程度に具体的であること

* Executorが、テスト指示のみを参照してテストを行う(P103)。
* `docs/P201-review-report.md` (Reviewer Loop)が、本フェーズの実行結果を確認する。

## 動作

* 共通指示に加えて、上記アウトプット記載内容に定めた事項に従う。
