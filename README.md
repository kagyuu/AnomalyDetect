# S_ANOMALY — 運用ログの異常検知 CLI

DB 接続数 / JavaEE の JVM GC 統計 / LSF キュー状態の運用ログを読み込み、
**11 個の異常検知アルゴリズム**を適用して、異常な箇所を Markdown のレポート群にまとめる
コマンドラインツールである。

* **オフライン動作**。ネットワーク通信を一切行わない(NFR-008)。
* **外部依存は DuckDB のみ**(FR-003)。それ以外は Python 標準ライブラリだけを使う。
* **インストール不要**。ディレクトリごとコピーして実行する(NFR-011)。

---

## 1. 実行方法

```
python app/s_anomaly.py <解析対象ディレクトリ>
```

`<解析対象ディレクトリ>` を再帰的に探索し、次の 3 種類のファイルを読み込む。

| ファイル名 | 内容 |
| --- | --- |
| `DBConnection_{yyyymmdd}.csv` | DB コネクションログ |
| `{コンテナ名}_gc_{ホスト名}_{yyyymmdd}.txt` | JavaEE の `jstat` 出力(`-gcutil` / `-gc` の両形式) |
| `bqueues_{ホスト名}_{yyyymmdd}.txt` | LSF のキュー状態 |
| `sa-{ホスト名}-{yyyymmdd}.csv` | **OS 資源統計(sar / sysstat)**。`sadf -d` で CSV 化したもの(※CR-010。付録A) |

**これ以外のファイルは無視される**(置いてあっても失敗しない)。

> **★CR-010 で sar(sysstat)に対応した。★** `sa-{ホスト名}-{yyyymmdd}.csv` を
> 置けば、他のログと同じ 11 アルゴリズムが適用され、レポートに出る。
> **`sadf -d` による変換手順と変換スクリプトの例は付録A にある。**
>
> **★注意★ sar を導入すると、既存イベントの ID の連番がずれる。** 連番は
> 「日 × ホスト」ごとに 1 から振るため(CR-003)、同じ日・同じホストに sar の
> イベントが増えると、その後ろの番号が繰り上がる。**過去のレポートと ID で
> 突き合わせている場合は注意すること。** 内容そのものは変わらない。

結果は**カレントディレクトリ**に、次の 2 種類のファイルとして出力される。

| ファイル名 | 内容 | 単位 |
| --- | --- | --- |
| `report_{ホスト名}_{年月}.md` | そのホスト・その年月のイベント本文 | ホスト × 年月ごとに 1 ファイル |
| `report_summary_{年月}.md` | 全ホスト横断の集計サマリ | 年月ごとに 1 ファイル |
| `charts/{イベントID}.svg` | **アノマリーの状況の折れ線チャート**(※CR-009。4.5 参照) | 対象イベントごとに 1 ファイル |
| `charts/no-chart.svg` | チャートが無いイベント用の `[NO CHART]` 画像 | **全体で 1 ファイル** |

**ファイル数は多くなる。** 30 日分の解析で 18 ファイル、90 日分で 54 ファイルになる(実測)。

### 1.1 引数

引数は解析対象ディレクトリの **1 つだけ**である。`--help` / `--version` オプションは持たない
(`docs/P002-frontend-spec.md` UI-01)。**バージョンは起動時の進捗ログに出る。**

```
2026-09-04 05:13:12 [INFO] [--] s_anomaly 0.3.0 を起動しました (Python 3.14.2, DuckDB 1.5.5)
```

### 1.2 終了コード

**9 種類**である。

| コード | 意味 | 対処 |
| --- | --- | --- |
| 0 | 正常終了 | — |
| 1 | 引数が不正(個数違い、パスが存在しない / ディレクトリでない / 読み取り権限がない) | 引数は**解析対象ディレクトリの 1 つだけ**。パスと読み取り権限を確認する |
| 2 | 対象のログファイルが 1 件も見つからない | **ファイル名の規則**(1 章の表)に合っているか確認する。再帰探索するのでサブディレクトリでもよい |
| 3 | `settings.properties` の値が不正 | **標準エラーに、キー・与えた値・期待する範囲がまとめて全件出る。** そのとおりに直す |
| 4 | 見つかったファイルの解析にすべて失敗した | ファイルの中身が想定の形式か確認する。**一部だけの破損なら終了コード 0 で続行**し、読み飛ばした件数がサマリの 5.1 に出る |
| 5 | レポートを書き込めない | **カレントディレクトリ**に書き込む。書き込み権限とディスク空き容量を確認する。**生成できた分の全文は標準出力に出る** |
| 6 | メモリ不足、または DuckDB の実行時エラー | `[duckdb] max_memory` を増やすか、`temp_directory` に空きのあるパスを指定する(4.3) |
| 7 | DuckDB を読み込めない | 閉域環境では `vendor/` の準備が要る(**6 章**)。読み込み元は起動時の進捗ログに出る |
| 99 | 想定外の内部エラー | **スタックトレースが標準エラーに出る。** 開発元へ、それと進捗ログを添えて連絡する |

**進捗は標準出力、警告とエラーは標準エラーに出る。** 切り分けるときは分けて保存するとよい。

```
python app/s_anomaly.py /var/log/collected > run.log 2> run.err
```

### 1.3 レポート群の構成

**出力は 2 種類に分かれる。** 大きなレポート 1 つでは、コンテキスト長の小さい
LLM が読めないためである。**まずサマリを読み、必要なホストだけ本文へ進む**
使い方を想定している。

#### `report_summary_{yyyymm}.md` — 集計サマリ

**1 ファイルあたり 4,000 バイト以内**に収まるよう、すべての表に行数上限を置いてある
(実測: 90 日規模で最大 3,873 バイト)。

| 章 | 内容 |
| --- | --- |
| 1. 全体の集計 | 対象期間・ホスト数・イベント数・脅威度別の内訳 |
| 2. ホスト別の集計 | **最大 10 行**(イベント数の多い順) |
| 3. 日別のイベント数 | **最大 10 行**。対象が 31 日を超える場合は週単位 |
| 4. 複数ホストで同時に発生したアノマリー | **最大 8 行** |
| 5. 実行時の注意事項 | 5.1 読み飛ばした行 / 5.2 点数不足でスキップした系列 / 5.3 失敗したアルゴリズム |

#### `report_{ホスト名}_{yyyymm}.md` — イベント本文

| 章 | 内容 |
| --- | --- |
| 1. このホストの集計 | メトリクス別の脅威度内訳(**実測 最大 674 バイト**) |
| 2. 実行サマリ | 実行日時、対象ディレクトリ、対象期間、ファイル数、総レコード数、系列数 |
| 3. 適用したアルゴリズム | 11 個の ID・名称・パラメータ・ON/OFF |
| 4. 検知イベント | **1 イベント = 1 ブロック。脅威度の降順** |
| 5. 実行時の注意事項 | サマリと同じ 3 節 |

各イベントは次の 10 項目を**必ず**持つ(該当が無い場合も「(なし)」を書き、
項目そのものは省略しない)。

```
# イベントID( EVT-{yyyymmdd}-{ホスト名}-{連番} )
* イベント種別 : 検知したアルゴリズム ID(統合された場合は複数)
* 脅威度       : SEVERE / FATAL / WARN / INFO
* データ       : {テーブル} / {メトリクス} / {系列を特定するキー}
* 値           : 該当区間の値(長い場合は先頭・末尾を残して間引き)
* 開始         : yyyy-mm-dd HH:MM:SS
* 終了         : yyyy-mm-dd HH:MM:SS
* 現象         : 何が起きたかの 1 行要約
* 説明         : なぜ異常と判断したか(使った統計量と閾値)
* 原因候補     : 原因ルールに一致した候補(確度: 高 / 中 / 低)
* 同時に発生したアノマリー :
  - 発生時間に重なりのある他のアノマリー(**最大 10 件**)
    並び順は「同一ホスト優先 → 脅威度の高い順 → 重なり時間の長い順」
```

**「同時に発生したアノマリー」欄の詳細は 5.1 節にある。**

「原因候補」は次の 9 個の原因ルールとの照合結果である。**断定はせず、候補と確度を
示すに留める**(最終的な判断は人間、またはレポートを読ませた LLM が行う)。

| ID | 原因候補 | 確度 |
| --- | --- | --- |
| CR-01 | メモリリーク | 高 |
| CR-02 | 負荷増に伴う正常な増加 | 中 |
| CR-03 | コネクションリーク(クローズ漏れ) | 高 |
| CR-04 | 計算資源の枯渇、またはジョブのスタック | 高 |
| CR-05 | クラスローダリーク(動的クラス生成) | 中 |
| CR-06 | ヒープ不足による Full GC 頻発 | 高 |
| CR-07 | 一時的な負荷スパイク、または採取タイミングの揺れ | 低 |
| CR-08 | 設定変更・負荷段階の変化 | 中 |
| CR-09 | 定期的な処理による周期的な負荷 | 低 |

レポートは **BOM なし UTF-8 / 改行 LF** で出力する(OS によらず同一)。
同じ入力・同じ設定なら、**実行日時の欄を除いて常に同一の内容**になる。

### 1.4 コンテキストの小さい LLM に読ませる場合

レポートは「**列挙**」と「**集計**」の 2 層構造になっている。
**コンテキスト長 4K トークン程度のローカル LLM でも扱えるよう**、次の順で読むとよい。

1. **`report_summary_{年月}.md` を読む**(実測 約 3,800 バイト)。全体像と、注目すべきホストが分かる
2. **`report_{ホスト名}_{年月}.md` の先頭「1. このホストの集計」を読む**(実測 最大 674 バイト)
3. 個々のイベントの詳細が要るときだけ、本文(ホスト別ファイルの 4 章)を読む。**ここは大きい**(1 イベント約 700 バイト)

**集計はアプリが行っている。** LLM に数えさせる必要はない。

## 3. 異常検知アルゴリズム

**3 つの観点に、計 11 個**を実装している(観点1 に 5 個、観点2 に 5 個、観点3 に 1 個)。
**すべてが同じ入力に対して
並行に適用され、同一箇所を複数のアルゴリズムが検知した場合は 1 つのイベントに統合される**
(FR-061)。単独では弱点のある手法を、互いに補い合わせる構成である。

### 3.1 観点1: 瞬間的な外れ値(point anomaly)

「普段と比べて突出した値」を捉える。

| ID | 名称 | 原理 | 弱点 | 補うアルゴリズム |
| --- | --- | --- | --- | --- |
| **ALG-A1** | 移動平均乖離率(Moving Average ± kσ) | 直前 N 点の移動平均 `MA` と標準偏差 `σ` を求め、`|value − MA| > k × σ` を外れ値とする。`k=2` を WARN、`k=3` を FATAL とする | **外れ値自身が平均と σ を押し上げる**(マスキング)。連続する異常を見逃す | ALG-A2(頑健統計)、ALG-A3(窓を持たない) |
| **ALG-A2** | Hampel フィルタ(移動中央値 + MAD) | 移動中央値 `median` と MAD(中央絶対偏差)を用い、`|value − median| > k × 1.4826 × MAD` を外れ値とする。係数 1.4826 は正規分布で MAD を σ に換算する定数 | 窓内の過半数が異常だと中央値そのものがずれる | ALG-A3(系列全体の分布) |
| **ALG-A3** | Tukey の外れ値境界(IQR 法) | 系列全体の四分位数から `Q3 + 1.5×IQR` を WARN、`Q3 + 3.0×IQR` を FATAL の境界とする。**窓を持たない** | 系列全体が緩やかに増加していると、後半がすべて外れ値になる。分布が広いと適用できない | ALG-A1 / A2(局所的な窓)、観点2 の各手法 |
| **ALG-A4** | EWMA 管理図 | 指数加重移動平均 `z_t = λ·x_t + (1−λ)·z_{t−1}`(λ=0.2)と管理限界を用いる | 単発の大きな跳ねに鈍い(平滑化されるため) | ALG-A1(単発に敏感) |
| **ALG-A5** | 曜日・時刻別ベースライン | 「同じ曜日 × 同じ時刻帯」の分布を基準に Z スコアを求める | 学習に複数週が必要(既定 2 週以上)。周期の無い系列では効かない | ALG-A1〜A4 |

**ALG-A1** は要求元が例示した「移動平均乖離率(2σ、3σ)」そのものである。
**ALG-A2 / A3** はそのマスキング弱点を補う頑健版、**ALG-A5** は「平日昼は高く夜間は低い」
といった運用ログの周期性を平常とみなすために置いている。

### 3.2 観点2: 持続的な数値の増加(trend / leak)

「じわじわ増え続けている」ことを捉える。**メモリリークの検出が主な狙い**である。

| ID | 名称 | 原理 | 弱点 | 補うアルゴリズム |
| --- | --- | --- | --- | --- |
| **ALG-B1** | 短期/長期移動平均のクロス継続 | 短期移動平均(既定 1 時間)が長期移動平均(既定 24 時間)を上回る状態が M 点以上連続することを検知する | 判定が単純で、ノイズの多い系列では誤検知しやすい。**長期の系列では条件が厳しくなり検知 0 件になることがある**(下記 8 章) | ALG-B2(統計的検定) |
| **ALG-B2** | Mann-Kendall 傾向検定(+ Theil-Sen 勾配) | 全ペアの増減の符号和 `S` から傾向の有無を**非パラメトリックに検定**する。`p<0.05` を WARN、`p<0.01` を FATAL とする。増加の大きさは Theil-Sen 中央値勾配(全ペアの傾きの中央値)で表す | 単調増加の**開始点**が分からない。全期間を 1 つの傾向として見る | ALG-B4(変化点)、ALG-B3(窓ごと) |
| **ALG-B3** | ローリング最小値(下限包絡線)の単調増加 | 窓内の**最小値**の系列が単調に増加しているかを見る。**メモリリーク検出の定番手法**である。GC で回収しきれない分だけ下限が押し上がることを捉える | 増加が小さいと窓の粒度に埋もれる | ALG-B2 / B5 |
| **ALG-B4** | CUSUM(累積和管理図) | 基準値からの偏差を累積し、閾値 `h × σ` の超過で**水準シフト**を検知する。シフト前後の水準は、その時点の前後 24 時間の窓平均で求める | **検知点数が多くなりやすい**(下記 8 章) | ALG-B2(全体傾向) |
| **ALG-B5** | 線形回帰の傾きと決定係数 | DuckDB の `regr_slope` / `regr_r2` を用い、**傾きが正かつ R² が閾値以上**のとき増加傾向とする | 直線から外れる増加(階段状・指数的)に弱い | ALG-B3 / B4 |

**ALG-B1** は要求元が例示した「長期の移動平均よりも短期の移動平均が常に上にある」そのものである。
**ALG-B2** はそれに統計的な裏付けを与え、**ALG-B3** はメモリリーク検出の定番手法として置いている。

### 3.2a 観点3: 上限への張り付き(saturation)

**「上限に達して頭打ちのまま平坦」という状態**を捉える。
「DBConnection や Java のメモリが**上限値に張りついている**ことを知りたい」という
要求に対応する。

| ID | 名称 | 原理 | 弱点 | 補うアルゴリズム |
| --- | --- | --- | --- | --- |
| **ALG-C1** | 上限への張り付き | 上限に対する比率が `ratio_pct`(既定 90%)以上である状態が `min_minutes`(既定 360 分)以上続いたことを検知する。**上限が入力に無い場合は解析期間中の実測最大値から推定する** | **推定上限は真の上限とは限らない。** 期間中ずっと上限の半分までしか使われていなければ、その半分が「上限」と推定される | 観点1(跳ねたこと自体)、観点2(そこへ至る増加) |

**なぜ観点1・観点2 で代用できないのか。**

| 状況 | 観点1(外れ値) | 観点2(増加) | **観点3** |
| --- | --- | --- | --- |
| 一時的に跳ねた | ○ | ✕ | ✕ |
| 増え続けている | ✕ | ○ | ✕ |
| **上限に達して頭打ち** | ✕ | **✕** | **○** |
| **期間の最初から張り付き** | ✕ | **✕** | **○** |

**上限に達すると増加が止まる。** 観点2 は増加を見るため、
「末尾の最大 > 以前の最大」も「短期移動平均 > 長期移動平均」も偽になり、
**最も知りたい状態を取りこぼす。** 観点1・観点2 が「変化」を見るのに対し、
観点3 は**「変化していないこと」を見る。**

**誤検知を抑えるため、次の系列は対象から外す。**

| 除外する対象 | 理由 |
| --- | --- |
| 値の種類が 10 未満の系列 | 0/1 のフラグ系列は推定上限が 1 になり、必ず「90% 以上」が成立してしまう |
| 最大値が下位 5% 水準の 1.5 倍に満たない系列 | 常時ほぼ一定の系列を「張り付き」と誤認しないため |
| **`%idle`(sar)** ※CR-010 | **100% の遊休は正常である。** 除外しないと閑散なホストが全件「張り付き」になる |
| **`kbmemfree`(sar)** ※CR-010 | 「小さいほど逼迫」であり向きが逆。空きメモリの逼迫は `%memused` の側で捉える |

**★sar の比率は推定上限を使わない(※CR-010)。★** `%memused` / `%util` /
`%swpused` などは**上限が 100 と自明**であるため、上表の「推定上限は真の上限とは
限らない」という弱点がそもそも生じない。**sar は ALG-C1 にとって好条件である。**
| `fgc_delta` / `fgct_delta` / `ygct_delta` / `njobs` / `run` | 累積回数・件数であり、上限の概念が無い |

**使用率(`ou_pct` / `eu_pct` / `mu_pct`)が取れる系列では、推定ではなく実際の上限 100% を使う。**
レポートには「実際の上限」か「推定上限」かを明記する。

### 3.3 共通の要件

* 検知結果は `series_id` / `metric` / `algorithm` / `start_ts` / `end_ts` / `values` / `score` / `explanation` を持つ。観点1 は単点(`start = end`)、観点2 は区間である。
* **必要最小点数(既定 30 点)に満たない系列はスキップし、その旨を記録する。**
* 1 つのアルゴリズムが失敗しても他は続行する(FR-032)。
* **時刻窓の集計は、時刻昇順を利用した二分探索で範囲を絞ってから走査する**(`docs/ADR.md` ADR-013)。
* **同一系列のデータを検知器ごとに読み直さない**(ADR-017)。系列を処理するあいだ保持し、検知器間で共有する。

**アルゴリズムに共通する仕組み**

| 仕組み | 内容 |
| --- | --- |
| **実効的なばらつき** | `effective_σ = max(σ, sigma_floor_ratio·|μ|, sigma_floor_abs)`。`pend` / `susp` のようにほぼ一定の小さな整数の系列で `|x−μ|/σ` が発散し、些細な変化が大量に検知されるのを防ぐ。**誤検知が多いときは、まずこの 2 つを大きくすること。** |
| **持続性規則** | Western Electric 規則の簡易版。「3σ を 1 点」または「2σ を 2 点以上連続」で初めて検知とする。4,000 点の系列に 2σ を当てると、正規ノイズだけで約 180 点が偶然超えるため |
| **季節差分** | `d_t = x_t − x_{t−24h}`。日内周期を取り除いてから当てる(ALG-A4 / B4) |
| **区間のまとめ** | 隣り合う検知点は 1 つの区間にまとめる |
| **最小点数** | 系列の点数が足りない場合はスキップし、件数をサマリの「5.2 点数不足でスキップした系列」に集計する。**エラーにはしない** |
| **セグメント分割** | JVM の再起動を検出すると系列を分割し、再起動をまたぐ差分は計算しない |

### 3.4 採用しなかった手法

Isolation Forest / One-Class SVM / LOF / STL 分解は**採用していない**。
いずれも scikit-learn または statsmodels に依存し、**外部依存を DuckDB のみとする要求(FR-003)**
および閉域環境への配布コストに反するためである。この割り切りの結果、
**多変量の異常検知(複数メトリクス間の相関崩れ)と複雑な季節性には対応できない。**
**同時に発生したアノマリーの提示までは行う**(5.1)ため、その先の判断は人間と後段の LLM に委ねる設計である。

### 4.4 `[timezone]` — タイムゾーン(※CR-008)

| キー | 既定値 | 意味 |
| --- | --- | --- |
| `storage` | `UTC` | **DuckDB へ投入するときのタイムゾーン。** レポートの時刻はこれになる |
| `db_connection` | `UTC` | `DBConnection_*.csv` の時刻のタイムゾーン |
| `jvm_gc` | `UTC` | `*_gc_*.txt` の時刻のタイムゾーン |
| `lsf_queue` | `UTC` | `bqueues_*.txt` の時刻のタイムゾーン |
| `sar` | `UTC` | `sa-*.csv` の時刻のタイムゾーン(※CR-010)。**`sadf -d` の既定は UTC** |

**取り込み(S4)の時点で `storage` へ変換して格納する。** レポートは格納された時刻を
そのまま出し、**再変換はしない。** 時刻の末尾にはタイムゾーンを併記する。

```
| 対象期間 | 2026-06-01 00:00:00 (UTC) 〜 2026-06-30 23:55:00 (UTC) |
* 開始   : 2026-06-05 03:20:00 (UTC)
```

**読み込み元と `storage` が同じなら、変換は行わない。**
既定はすべて `UTC` であるため、**通常の構成では変換が一度も発生しない。**

> **★IANA の名前付きタイムゾーンだけを受け付ける**(例 `UTC`, `Asia/Tokyo`)。
> **固定オフセット(`+09:00`)は使えない。大文字小文字も区別する**(`utc` は不可)。
> 誤った名前は起動時に検出し、**終了コード 3** で停止する。

**なぜタイムゾーンを分けて設定できるのか。** 本ツールはイベントの区間の重なりで
「同時に発生したアノマリー」を判定する(5.1)。**入力ごとに採取時のタイムゾーンが
違うと、実際にはずれた時刻同士を突き合わせてしまう。**
とくに sar(付録A)は `sadf` の既定出力が UTC であり、他のログがローカル時刻の
環境では時差ぶんずれる。

★ACCEPTED★ **夏時間(DST)の妥当性は検証しない。** 名前付きタイムゾーンを使うため
DuckDB 側が DST を解釈するが、本ツールはその結果を検証しない。
**想定システムはすべて UTC であり DST が存在しない**ためである。
**残存リスク**: DST のある地域を設定した場合、切り替え時刻付近の 1 時間で
時刻の重複または欠落が起きうる。その区間の検知結果は信用できない。

### 4.5 `[chart]` — チャート(※CR-009)

**アノマリーの状況を SVG の折れ線にして `charts/` 配下へ出力し、
ホスト別レポートから画像リンクで参照する。**

```markdown
![EVT-20260605-host01-015 ou の推移](charts/EVT-20260605-host01-015.svg)
```

| キー | 既定値 | 意味 |
| --- | --- | --- |
| `enabled` | `true` | `false` で一切出力しない |
| `min_severity` | `FATAL` | この脅威度以上を対象にする(`SEVERE`/`FATAL`/`WARN`/`INFO`) |
| `max_per_host` | 100 | ホストあたりの上限(脅威度の高い順) |
| `max_overlay_per_host` | 100 | ホストあたりの上限(**同時アノマリーを持つイベント。別枠**) |
| `pad_ratio` | 0.25 | 異常区間の前後に取る余白の比率 |

#### 図の見かた

**2 段構成である。**

| 段 | 内容 |
| --- | --- |
| 上 | **そのイベントの系列を実単位で描く。** 異常と判定された区間を黄色で網掛けする |
| 下 | **同時に発生したアノマリーを重ねる**(5.1 参照)。各系列を自身の最小〜最大で 0〜100% に正規化する |

**下段の縦軸は無次元である。** DB コネクション数・メモリ使用率・待ちジョブ数は
単位が違い、そのままでは同じ縦軸に載らないため正規化している。
**実際の最小値・最大値は凡例に併記してある。**

#### `min_severity` を `SEVERE` にすると重ね合わせが出なくなる

**`SEVERE` は定義上「観点2 の検知」である**(5 章)。
**観点2 のイベントには同時アノマリーが付かない**(5.1)ため、
`SEVERE` 止まりにすると重ね合わせのチャートが 1 枚も出ない。
**既定を `FATAL` にしているのはこのためである。**

#### チャートが無いイベントには `[NO CHART]` の画像が出る

**上限や脅威度で対象から外れたイベントにも画像を出す。**
図が無いと「ツールの不備」と誤解されるためである。

```markdown
![EVT-20260601-host02-014 チャートなし](charts/no-chart.svg)
```

* **画像は `charts/no-chart.svg` の 1 つだけ**であり、全イベントが同じものを参照する。
* **理由は書かない。** 脅威度・件数の上限・点数不足と複数あり、1 行で正確に言えない。
  レポートの分量にも効く。
* **`enabled = false` のときは画像を一切出さない**(誰も図を期待しないため)。

#### 点数が足りないときは生の値を表で出す

**窓の中の点が 5 点未満のときは、折れ線にしても線に見えない**ため図にしない。
その場合は `[NO CHART]` の画像に続けて、**元の値をそのまま表で出す**。

```markdown
![EVT-20260601-host02-014 チャートなし](charts/no-chart.svg)

| 時刻 | 値 |
| --- | --- |
| 2026-06-01 00:00:00 (UTC) | 12 |
| 2026-06-01 00:05:00 (UTC) | 13.5 |
```

#### 点数の上限と下限(設定では変えられない)

| 定数 | 値 | 意味 |
| --- | --- | --- |
| **`MIN_POINTS`** | **5** | **これに満たなければ図にせず、上記の表を出す。** 点が 4 つ以下では折れ線が線に見えない |
| **`MAX_POINTS`** | **360** | **これを超える点列は等間隔に間引く。** 先頭と末尾は必ず残す |

**`MAX_POINTS = 360` の根拠**: 図の横幅は 720px であり、360 点なら **2px に 1 点**である。
これ以上細かくしても見た目は変わらず、ファイルサイズだけが増える。

**窓を広げると解像度が下がる。** 点数の上限は固定なので、
`pad_ratio` を大きくすると間引きが粗くなる。

```
窓 1 時間   → 5 分間隔で   12 点  … 全点を描画
窓 12 時間  → 5 分間隔で  144 点  … 全点を描画
窓 60 時間  → 5 分間隔で  720 点  → 360 点に間引き(2 点に 1 点)
```

**いずれも設定ファイルでは変えられない**(`app/src/s_anomaly/charts.py` の定数)。
運用で調整する必要が出た場合に設定へ出す。

#### 出力量に直結する

**30 日規模でイベントは約 7,200 件ある。** 上限が無いと出力が肥大する。

| `max_per_host` + `max_overlay_per_host` | 枚数(30 日 / 17 ホスト) | 合計サイズ | 実行時間 |
| --- | --- | --- | --- |
| 10 + 10 | 340 枚 | 3.7MB | 55.3s |
| **100 + 100(既定)** | **2,429 枚** | **17.8MB** | **103.2s** |

**既定は 100 + 100 である。** 上限を上げるほど枚数・サイズ・実行時間が増える。
**サマリ(`report_summary_*.md`)にはチャートを入れない。** 4K トークンの目標を守るためである。

> **★チャートは人間向けである。** SVG は後段の LLM からは見えない。
> LLM だけで完結する運用では使われないが、**サマリを変えていないため
> その運用は現在どおり成立する。**

| 名前 | `sadf` の指定 | 取り込むメトリクス | 系列の単位 |
| --- | --- | --- | --- |
| `cpu` | `-u` | `pct_user` / `pct_system` / `pct_iowait` / `pct_idle` | CPU 番号(`-1` = 全 CPU) |
| `memory` | `-r` | `pct_memused` / `pct_commit` / `kbmemfree` | ホスト |
| `swap_space` | `-S` | `pct_swpused` | ホスト |
| `io` | `-b` | `tps` / `bread_s` / `bwrtn_s` | ホスト |
| `load` | `-q` | `runq_sz` / `ldavg_1` / `ldavg_5` / `blocked` | ホスト |
| `swapping` | `-W` | `pswpin_s` / `pswpout_s` | ホスト |
| `disk` | `-d -p` | `pct_util` / `await` / `tps` | **デバイス**(`sda` など) |
| `network` | `-n DEV` | `pct_ifutil` / `rxkb_s` / `txkb_s` | **インタフェース**(`eth0` など) |

| **`nfsd`** ※CR-011 | `-n NFSD` | `scall_s` / **`badcall_s`** / `hit_s` / **`miss_s`** / `sread_s` / `swrite_s` / `saccess_s` / `sgetatt_s` | ホスト |

**★系列数に直結する。★** `disk` と `network` はデバイス・インタフェース単位で
系列が増える。検知(S6)の所要時間は系列数にほぼ比例するため、**大規模環境で
実行時間が問題になる場合はここを絞る。**

```ini
[sar]
# ディスクとネットワークを外す (系列数を大きく減らせる)
activities = cpu,memory,swap_space,io,load,swapping,nfs,nfsd
```

**`nfs` / `nfsd` は系列数への影響が小さい**(デバイス単位ではなくホスト単位のため、
1 ホストあたり 6 + 8 = 14 系列)。**NFS を使う環境では外さないほうがよい。**

* **未知の名前は警告を出して無視する。** 終了コード 3 にはならない。
* **空にすると sar を取り込まない。** これもエラーではない。

### メトリクス名の読み方

sar の列名は次の規則で正規化される。

| sar の列名 | メトリクス名 |
| --- | --- |
| `%user` | `pct_user`(先頭の `%` が `pct_` になる) |
| `rd_sec/s` | `rd_sec_s`(`/` が `_` になる) |
| `ldavg-1` | `ldavg_1`(`-` が `_` になる) |

**★接頭の `pct_` と接尾の `_pct` は別物である。★**

| 記法 | 例 | 意味 | 検知の対象か |
| --- | --- | --- | --- |
| **`pct_*`(接頭)** | `pct_memused` | **sar が直接出す比率** | **対象。** 他のメトリクスと同じ扱い |
| **`*_pct`(接尾)** | `ou_pct` | 本ツールが容量から**導出した**使用率 | 対象外。脅威度判定にのみ使う |

**`%memused` / `%util` / `%swpused` などは上限が 100 と自明**であるため、
「上限への張り付き」(ALG-C1)では**推定上限を使わない**(3.2a 参照)。
**`%idle` は対象外である** — 100% の遊休は正常であり、除外しないと
閑散なホストが全件「張り付き」になる。

## 5. 脅威度の判定

検知結果は 4 段階に分類される。

| 脅威度 | 判定条件 | 意味 |
| --- | --- | --- |
| `SEVERE` | 観点2 の検知であり、**かつ対象が上限に接近している**(使用率メトリクスが `events.severe_pct`(既定 90%)超、または `pend` が単調増加で最大値を更新中) | 放置すると停止に至る |
| `FATAL` | 観点1 で 3σ 相当を超える、または観点2 で強い傾向(ALG-B2 が `p<0.01`) | 明確な異常。調査が必要 |
| `WARN` | 観点1 で 2σ〜3σ 相当、または観点2 で弱い傾向(ALG-B2 が `p<0.05`) | 逸脱はあるが単独では判断できない |
| `INFO` | 上記に該当しないが複数アルゴリズムが同一箇所を検知した、または単発の軽微な逸脱 | 参考情報 |

* **同一の系列・メトリクス・時間帯を複数のアルゴリズムが検知した場合は 1 つのイベントに統合する**(FR-061)。
* **3 つ以上のアルゴリズムが一致した場合は脅威度を 1 段階引き上げる**(FR-062)。検知アルゴリズム数が多いほど確度が高いとみなすためである。

**★重要★ この判定規則も実データ未検証の想定である。** 運用上の重み付けは対象システムの
事情に依存するため、人間による確認が必要である。

---

### 5.1 「同時に発生したアノマリー」

各イベントには、**同じ時間帯に検知された他のアノマリー**が最大 10 件まで載る。

```
* 同時に発生したアノマリー :
  - EVT-20260605-host01-015 (同一ホスト) jvm_gc / ou : FATAL / 重なり 5 分
  - EVT-20260605-host09-008 (他ホスト) db_connection / active_connections : FATAL / 重なり 5 分
```

**「DB コネクションの高止まりと利用メモリの高止まりが同時に起きている」**といった、
アノマリー同士の同時発生を見つけるための欄である。

| 項目 | 内容 |
| --- | --- |
| 「同時」の判定 | **発生時間(開始〜終了)の区間に重なりがあること** |
| 対象 | **観点1(瞬間的な外れ値)のイベントのみ。** 観点2 を含むイベントには**この欄自体が出ない** |
| 上限 | 10 件 |
| 並び順 | 同一ホストを優先 → 脅威度の高い順 → 重なっている時間の長い順 |

* **相手のイベント ID にホスト名が含まれる**ため、**どのファイルを開けばよいかが行から分かる**。
* **「持続的な増加の期間中に瞬間的な外れ値が起きた」ことは報告しない。** 持続的な増加は
  期間が長く(実測で最大 30 日)、その間のあらゆるイベントと重なってしまうため、
  情報として意味を持たないからである。
* 重なる相手が無い場合は `(同じ時間帯に検知された他のアノマリーはありません)` と出る。

**複数ホストにまたがる同時発生は、`report_summary_{年月}.md` の 4 章にまとめられている。**

## 6. 閉域環境への配布(`vendor/` の準備)

本ツールの唯一の外部依存は **DuckDB** である。インターネットに接続できない環境へ配布する場合は、
**接続できる環境であらかじめ wheel を取得し、`app/vendor/` へ展開しておく。**

### 6.1 ディレクトリ名の規則

```
app/vendor/{os}-{arch}-cp{major}{minor}/
```

| 要素 | 値 |
| --- | --- |
| `{os}` | `linux` または `win` |
| `{arch}` | `x86_64`(Linux)または `amd64`(Windows) |
| `cp{major}{minor}` | 配布先の Python バージョン。例: Python 3.10 なら `cp310` |

例: `app/vendor/linux-x86_64-cp310/`、`app/vendor/win-amd64-cp314/`

### 6.2 準備手順(インターネット接続環境で実施)

1. **配布先の OS・アーキテクチャ・Python マイナーバージョンを確認する。**
   配布先で次を実行して確認するのが確実である。

   ```
   python -c "import sys,platform; print(platform.system(), platform.machine(), sys.version_info[:2])"
   ```

2. 対応する wheel をダウンロードする。**配布先の環境に合わせて `--platform` と `--python-version` を指定する。**

   ```
   # 例: Linux x86_64 / Python 3.10 向け
   pip download duckdb --only-binary=:all: \
       --platform manylinux2014_x86_64 --python-version 310 \
       --dest ./dl-linux

   # 例: Windows AMD64 / Python 3.14 向け
   pip download duckdb --only-binary=:all: \
       --platform win_amd64 --python-version 314 \
       --dest ./dl-win
   ```

3. wheel を展開する(`.whl` は zip である)。**インストールではなく展開**である。

   ```
   python -c "import zipfile,sys; zipfile.ZipFile(sys.argv[1]).extractall(sys.argv[2])" \
       ./dl-linux/duckdb-*.whl app/vendor/linux-x86_64-cp310
   ```

4. 展開後、そのディレクトリ直下に `duckdb/` パッケージがあることを確認する。

   ```
   app/vendor/linux-x86_64-cp310/duckdb/__init__.py
   ```

5. **配布先の複数環境に対応する場合は、環境ごとにディレクトリを作って並べてよい。**
   実行時は自動的に、実行環境に対応するディレクトリだけが選ばれる。

### 6.3 動作の確認

起動すると、進捗ログに読み込み元が出る。

* `vendor/` から読めた場合: その旨が INFO に出る
* `vendor/` が実行環境と一致しない場合: **環境にインストールされた DuckDB へフォールバックする**(これは意図された正しい挙動である)
* どちらからも読めない場合: **終了コード 7** で停止し、期待するプラットフォーム・Python 版と実際の値、および `vendor/` に存在するディレクトリ名の一覧を標準エラーに出す

★重要★ **`vendor/` 経路は実環境で未実証である。** 配布先の Python 版が未確認のため、
開発時は環境の DuckDB へのフォールバック経路で動作させている。
**閉域環境での初回実行時に必ず確認すること。**

## 9. 性能の目安

既定の `max_memory = 4GB` での実測値である(検証環境: Windows 11 / Python 3.14 / DuckDB)。

| 規模 | 入力ファイル数 | テーブル行数 | 所要時間 | うち検知(S6) | 出力ファイル数 |
| --- | --- | --- | --- | --- | --- |
| 30 日分(通常のユースケース) | 210 | 1,926,720 | **約 142 秒** | 約 37 秒 | 18(ホスト別 17 + サマリ 1)+ チャート 2,583 |
| 90 日分(大規模ケース) | 630 | 5,780,160 | **約 367 秒** | 約 106 秒 | 54(ホスト別 51 + サマリ 3)+ チャート |

(`disk` 2 デバイス / `network` 2 インタフェース)。**採取するホストが増えれば
その分だけ伸びる。** 実行時間が問題になる場合は `[sar] activities` で絞る(4.6)。

**版ごとの推移**

| 版 | 30 日分 | 90 日分 | 主な変更 |
| --- | --- | --- | --- |
| 0.1.0 | 151 秒 | 513 秒 | — |
| 0.2.0 | 71 秒 | 220 秒 | **相関の算出を廃止**(`metrics` への範囲結合をやめた) |
| 0.3.0 | 54 秒 | 178 秒 | **同一系列の読み直しを廃止**(検知が半減) |
| 0.4.0 | 53 秒 | 163 秒 | タイムゾーン対応(既定の全 UTC では変換が走らないため影響なし) |
| 0.5.0 | 95 秒 | 302 秒 | **SVG チャートの出力**(2,430 枚) |
| 0.6.0 | 132 秒 | 359 秒 | **sar(sysstat)の追加**。テーブル行が 79% 増えたが所要は 19% 増にとどまる |
| **0.7.0** | **142 秒** | **367 秒** | **sar の NFS / NFSD の追加**。ホスト単位の系列であり、行が 13% 増えて所要は 2% 増 |

0.3.0 では、**同じ系列のデータを検知器の数だけ読み直していた**のを止めた。
検知(S6)は 48 秒 → 25 秒(30 日分)になり、**1 系列あたりの単価は 1.2 秒 → 0.16 秒**である。

**0.5.0 で所要が増えたのはチャートの生成による**(30 日で +80%)。
`[chart]` の上限(4.5)で調整できる。**NFR-002 の目標 600 秒には収まっている**
(90 日で 302 秒 / 余裕 50%)。

**監視対象が増えた場合の目安**: S6 は系列数にほぼ比例する。
現在の 156 系列で 70 秒(90 日分)であり、**500 系列でも約 220 秒**と見込まれる。

### 検知の並列度

検知(S6)は**系列ごとにスレッドで並列実行**する。スレッド数は
`common.detect_threads` で変えられる(既定 0 = `min(8, 論理コア数)`)。

**11 個中 7 個のアルゴリズムが純 Python 実装であり、Python の GIL によりスレッドで
速くならない。** そのため並列化の効果は全体で約 1.13 倍にとどまる
(SQL 実装のアルゴリズムだけなら約 1.78 倍)。**スレッド数を増やしても大きくは変わらない。**

## 付録A. sar(sysstat)の前処理

> **★CR-010 で対応済みである。★** `sa-*.csv` を置けば読み込まれ、
> 他のログと同じ 11 アルゴリズムが適用される。**本節は前処理(CSV 化)の手順である。**

| パターン | 内容 |
| --- | --- |
| `sa-{ホスト名}-{yyyymmdd}.csv` | sysstat の日次データを `sadf -d` で CSV 化したもの |

### なぜ人手の前処理が要るのか

sysstat が `/var/log/sysstat/`(または `/var/log/sa/`)に残す `saDD` は
**バイナリ形式**であり、本ツールでは読めない。理由は 2 つある。

1. **本ツールは外部プロセスを起動しない**(2.1 参照)。`sar` や `sadf` を呼べない。
2. **バイナリ形式は sysstat の版に依存する。** 版が違うと本家の `sar` でさえ
   `Invalid system activity file` で読めない。自前で解析すると、環境ごとの
   sysstat の版に本ツールが追従し続けることになる。

したがって **変換は「データを採取したホスト上で」人が行い**、その出力を本ツールへ
渡す、という分担にする。同じホスト上なら sysstat の版とアーキテクチャが一致する。

### `sar` のテキストではなく `sadf -d` を使う理由

| 項目 | `sar -f` のテキスト | **`sadf -d`(採用)** |
| --- | --- | --- |
| 区切り | 空白の桁揃え(列幅がメトリクスで変わる) | **`;` 固定** |
| 日付 | **ロケール依存。`06/01/2026` は 6 月 1 日か 1 月 6 日か判別できない** | `YYYY-MM-DD` 固定 |
| ホスト名 | 先頭 1 行のヘッダのみ | **全行の第 1 列** |
| 余分な行 | `Average:` 行、再掲ヘッダ、`LINUX RESTART` | 無し |
| 列名 | 無し | **`#` で始まる見出し行が種別ごとに付く** |

### 変換スクリプトの例

**`/var/log/sysstat/` と `/var/log/sa/` の `saDD` / `saYYYYMMDD` を、
カレントディレクトリの `sa-{ホスト名}-{yyyymmdd}.csv` へ変換する。**

```
sh sa2csv.sh [ホスト名]
```

| 引数 | 挙動 |
| --- | --- |
| **指定した場合** | **そのホスト名をそのまま使う**(切り詰めない) |
| 省略した場合 | sa ファイルに記録されているホスト名(`uname -n`)を使う。**FQDN なら最初のドットまでに切り詰める** |

**ホスト名を指定できるようにしてあるのは、`uname -n` が他のログのホスト名と
食い違う場合があるため。** 本ツールはホスト名で系列を突き合わせるので
(レポートの分割、「同時に発生したアノマリー」の同一ホスト優先)、
**`DBConnection_*.csv` や `*_gc_*.txt` で使われている名前に揃える**必要がある。

> **★注意★ 名前を揃えるのは前処理の責任である。アプリ側では吸収しない。**
> 名前が食い違っていても**エラーにはならず、同じサーバが黙って別ホストとして扱われる。**
> レポートがホストごとに割れ、「同時に発生したアノマリー」の同一ホスト優先も効かなくなる。
> **`uname -n` と他のログの名前が違う環境では、引数での指定を運用手順に組み込むこと。**

```sh
#!/bin/sh
# sa2csv.sh -- sysstat のバイナリ日次ファイルを sa-{host}-{yyyymmdd}.csv へ変換する。
#
# 使い方: 出力したいディレクトリへ cd してから、データを採取したホスト上で実行する。
#   cd /var/tmp/anomaly && sh sa2csv.sh [ホスト名]
#
#   ホスト名を指定した場合 : そのホスト名をそのまま使う
#   省略した場合           : sa ファイルに記録されているホスト名 (uname -n) を使い、
#                            FQDN なら最初のドットまでに切り詰める
set -eu

# 引数のホスト名。出力ファイル名に使うので、使える文字だけかを検査する。
HOST_ARG="${1:-}"
case "$HOST_ARG" in
    "") ;;
    *[!A-Za-z0-9._-]*)
        echo "ホスト名に使えない文字が含まれています: $HOST_ARG" >&2
        exit 2 ;;
esac

SRC_DIRS="/var/log/sysstat /var/log/sa"

# 取り出す活動種別。1 ファイルに種別ごとのブロックとして並ぶ。
#   -u CPU / -r メモリ / -S スワップ領域 / -b I/O / -q 実行待ち
#   -W スワップイン・アウト / -d -p ブロックデバイス(%util) / -n DEV ネットワーク
#   -n NFS NFS クライアント / -n NFSD NFS サーバ
# ★1 つずつ呼ぶ。まとめて渡すと、採取されていない種別が 1 つあるだけで
#   ファイル全体の変換が失敗することがあるため。
#
# ★NFS / NFSD も本ツールの分析対象である(※CR-011。下記「NFS / NFSD について」)。
#   LSF 計算グリッドが NFS でファイルを共有するため、NFS の詰まりが
#   ジョブ滞留の原因になりうる。
ACTS="-u
-r
-S
-b
-q
-W
-d -p
-n DEV
-n NFS
-n NFSD"

work=$(mktemp); plain=$(mktemp)
trap 'rm -f "$work" "$plain"' EXIT
ok=0; ng=0

for dir in $SRC_DIRS; do
    [ -d "$dir" ] || continue

    # sa[0-9]* は saDD と saYYYYMMDD の両方に一致する。
    # sarDD はテキストなので 3 文字目が数字でなく、この glob には一致しない。
    for src in "$dir"/sa[0-9]*; do
        [ -f "$src" ] || continue

        # sysstat の設定によっては古いファイルが圧縮されている
        case "$src" in
            *.gz)  gzip  -dc "$src" > "$plain" || { ng=$((ng+1)); continue; }; bin=$plain ;;
            *.bz2) bzip2 -dc "$src" > "$plain" || { ng=$((ng+1)); continue; }; bin=$plain ;;
            *.xz)  xz    -dc "$src" > "$plain" || { ng=$((ng+1)); continue; }; bin=$plain ;;
            *)     bin=$src ;;
        esac

        # -d データベース向け形式(';' 区切り)
        #    ★時刻は sadf の既定である UTC で出す(-t / -T を付けない)。
        #      本ツールの既定の入力タイムゾーンが UTC のため、揃えておくと
        #      投入時の変換が発生しない([timezone] の設定。README 4.4)。
        : > "$work"
        echo "$ACTS" | while IFS= read -r act; do
            sadf -d "$bin" -- $act 2>/dev/null || true
        done >> "$work"

        # ホスト名と日付は「ファイル名ではなくデータ自身」から取る。
        # ★saDD の DD は日しか持たず年月が分からないため、
        #   ファイル名から yyyymmdd を組み立てることはできない。
        row=$(grep -v '^#' "$work" | head -n 1 || true)
        if [ -z "$row" ]; then
            echo "skip: 変換できません (sysstat の版違い等): $src" >&2
            ng=$((ng+1)); continue
        fi

        # ホスト名は、引数があればそれを使い、無ければデータ自身から取る。
        # ★引数を用意しているのは、他のログ(DBConnection / jstat / bqueues)の
        #   ホスト名と uname -n が食い違う場合があるため。名前が揃っていないと、
        #   同じサーバが別ホストとして扱われる。
        # ★自動で取る場合、FQDN は最初のドットまでに切り詰める(他のログに合わせる)。
        #   引数で指定された場合は、指定どおりに使う(切り詰めない)。
        if [ -n "$HOST_ARG" ]; then
            host=$HOST_ARG
        else
            host=$(printf '%s' "$row" | cut -d';' -f1 | cut -d'.' -f1)
        fi
        day=$( printf '%s' "$row" | cut -d';' -f3 | cut -d' ' -f1 | tr -d '-')
        if [ -z "$host" ] || [ -z "$day" ]; then
            echo "skip: ホスト名か日付を取り出せません: $src" >&2
            ng=$((ng+1)); continue
        fi

        cp "$work" "./sa-${host}-${day}.csv"
        echo "$src -> ./sa-${host}-${day}.csv"
        ok=$((ok+1))
    done

    # sarDD(テキスト)しか残っていない日を知らせる。
    # sadf はバイナリしか読めないため、テキストからは変換できない。
    for txt in "$dir"/sar[0-9]*; do
        [ -f "$txt" ] || continue
        mate="$dir/$(basename "$txt" | sed 's/^sar/sa/')"
        [ -f "$mate" ] || echo "注意: $txt はテキストのため変換できません" >&2
    done
done

echo "変換 ${ok} 件 / 不可 ${ng} 件"
```

### NFS / NFSD について

**変換スクリプトは `-n NFS`(NFS クライアント)と `-n NFSD`(NFS サーバ)を出力し、
本ツールはこれを分析対象として読み込む**(※CR-011)。

**対象システムでは LSF 計算グリッドが NFS でファイルを共有している。**
**NFS の詰まりは、LSF のジョブ滞留(`bqueues` の `pend` 増加)の直接の原因になりうる。**
両方を同じレポートで突き合わせられることが、この対応の狙いである。

#### 取り込むメトリクス

| 活動 | metric | 意味 |
| --- | --- | --- |
| `nfs` | `call_s` | クライアントが出した RPC 要求(回/秒) |
| | **`retrans_s`** | **再送(回/秒)。NFS の不調が最初に現れる指標である** |
| | `read_s` / `write_s` | 読み書き要求 |
| | `access_s` / `getatt_s` | アクセス権確認・属性取得(メタデータ操作) |
| `nfsd` | `scall_s` | サーバが受けた RPC 要求 |
| | **`badcall_s`** | **不正な要求。エラーの直接の指標** |
| | `hit_s` / **`miss_s`** | 応答キャッシュの命中・失敗。**`miss_s` の上昇はサーバ側の逼迫を示す** |
| | `sread_s` / `swrite_s` | サーバ側の読み書き |
| | `saccess_s` / `sgetatt_s` | サーバ側のメタデータ操作 |

**`-n NFSD` の `packet/s` / `udp/s` / `tcp/s` は取り込まない。**
`scall/s` と重複した情報であり、トランスポートの内訳は不調の指標にならないためである。

#### 読み方

* **`retrans_s` が増えているときは、NFS サーバかネットワークが応答できていない。**
  同じ時間帯に `bqueues` の `pend` が増えていれば、**ジョブ滞留の原因が
  NFS 側にある可能性が高い。** レポートは同じホストのイベントを並べて出すため、
  時刻で突き合わせられる。
* **`nfsd` の系列は NFS サーバでのみ意味を持つ。** サーバでないホストでは
  すべて 0 になる。**0 が続く系列からは検知が出ない**(分散が 0 のため)。
* **上限への張り付き(ALG-C1)の対象外である。** いずれも毎秒のレート値であり、
  上限が自明でないためである。

### 実行前に 1 ファイルで確かめること

**`sadf` の出力書式は sysstat の版によって差がある。** 全件を流す前に、
1 ファイルだけ手で確認すること。

```sh
sadf --version                          # 版を控える
sadf -d /var/log/sa/sa01 -- -u | head -3
```

期待する形は次のとおり。**第 1 列がホスト名、第 3 列が `YYYY-MM-DD HH:MM:SS`** で
あることが要点である。

```
# hostname;interval;timestamp;CPU;%user;%nice;%system;%iowait;%steal;%idle
host01;600;2026-06-01 00:10:00 UTC;-1;1.23;0.00;0.45;0.02;0.00;98.30
```

**時刻が UTC であること**も確認する。`sadf` の既定は UTC だが、
版によっては表示が異なる。**ローカル時刻で出てしまう場合は、
`[timezone]` の `sar` の値を実際のタイムゾーンに合わせること**(4.4 節)。

食い違う場合は、スクリプトの `cut -f` の位置を実際の出力に合わせること。
