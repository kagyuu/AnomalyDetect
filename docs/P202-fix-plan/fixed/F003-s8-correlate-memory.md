## 【障害記録】

* **原因区分: アプリケーションコードの欠陥**
* **症状(2 つある)**:

  1. **既定の `max_memory = 4GB` で、S8(相関の集計)が終了コード 6 で異常終了する。`report.md` が生成されない。**
     **通常のユースケース(30 日分 / テーブル 950,400 行 / 120 ファイル)でも発生する。**
  2. **メモリを 16GB にして完走させても、大規模ケース(90 日分)で 876.2 秒かかり NFR-002(600 秒)に届かない。S8 だけで 635 秒であり、S8 単独で目標を超える。**

* **エラーメッセージ**:

  ```
  2026-09-04 03:07:57 [INFO] [S7] 検知点 43872 点を 7229 件のイベントに統合しました
  2026-09-04 03:12:47 [ERROR] [--] error: データストアの処理に失敗しました
    理由: Out of Memory Error: failed to pin block of size 256.0 KiB (3.7 GiB/3.7 GiB used)
  ```

* **根本原因**: `app/src/s_anomaly/correlate.py` の `_aggregate_baseline`(および同型の `_aggregate_current`)が、
  **全イベントの窓を 1 回の結合で処理しており、中間結果の大きさが入力規模に対して有界でない。**

  ```sql
  SELECT w.event_id, m.series_id, m.metric,
         avg(m.value), stddev_samp(m.value), count(DISTINCT d.offset_day)
  FROM _event_windows w
  CROSS JOIN (SELECT unnest(range(1, ?)) AS offset_day) d
  JOIN metrics m
    ON m.ts BETWEEN w.t_from - to_days(CAST(d.offset_day AS INTEGER))
                AND w.t_to   - to_days(CAST(d.offset_day AS INTEGER))
  GROUP BY 1, 2, 3
  ```

  計算量は **O(イベント数 × 基準日数 × 系列数 × 窓内の点数)** である。
  窓幅は `events.merge_gap_minutes`(既定 60 分)の前後 ±1 時間なので 2 時間以上、5 分間隔で 25 点以上になる。
  通常 30 日分の概算で

  ```
  7,229 イベント × 7 日 × 156 系列 × 25 点 ≒ 1.97 億行
  ```

  を範囲結合で突き合わせ、`GROUP BY` の組は 7,229 × 156 ≒ 113 万になる。

* **切り分けの根拠**(すべて P203/P205 で実測済み。`docs/test-records/20260904-0335-test-record.md` 参照):

  | ケース | max_memory | 終了コード | 所要 | S8 の占める割合 |
  | --- | --- | --- | --- | --- |
  | 通常 30 日(950,400 行) | **4GB(既定)** | **6** | 363.6s で異常終了 | S8 の実行中に OOM |
  | 通常 30 日 | 16GB | 0 | 191.3s | 114s(60%) |
  | 通常 30 日 | 32GB | 0 | 192.0s | 114s 相当(60%) |
  | 大規模 90 日(2,851,200 行) | **4GB(既定)** | **6** | 828.7s / 847.2s で異常終了 | S8 の実行中に OOM |
  | 大規模 90 日 | 16GB | 0 | **876.2s** | **635s(72%)** |

  * **イベント数 7,229 → 21,307(2.95 倍)に対し、S8 は 114s → 635s(5.6 倍)と超線形に伸びる。**
  * 16GB と 32GB が同値であることから、16GB あれば足りている(= 必要量は青天井ではないが、既定の 4GB では足りない)。
  * **環境要因ではない。** マシンの物理メモリは 51.2GB あり、当たったのはアプリ自身の既定値である。
    終了コード 6 は正規のメモリ不足コードで、進捗ログ・エラーメッセージとも正常に出力されている
    (ネイティブクラッシュや無出力終了ではないため、CLAUDE.md の「まず実行環境を疑う」条件には該当しない)。
  * **4 回とも同じ箇所・同じメッセージで再現した。**

* **なぜ前ループ(F001)で見つからなかったか**: 修正前は ALG-B4 が支配的で、**S8 に到達する前に打ち切られていた**ためである。
  F001 が ALG-B4 を直したことで、はじめて S8 に到達し露呈した。**F001 が作り出した欠陥ではない**(`docs/P204-impact-analysis.md`)。

## 【修正方針】

**S8 の集計をイベントのバッチに分割し、1 回の結合の中間結果を有界にする。**

前ループが実測付きで整理した 5 案(`docs/P202-fix-plan/P202-fix-unresolved.md`)のうち、**案 1 を採る。**

* `_event_windows` へ全イベントを一度に入れるのをやめ、**一定件数ずつ(例: 500 件)入れ替えて集計し、結果を Python 側の辞書に積み上げる。**
* `GROUP BY` の単位が `event_id` ごとに閉じているため、**バッチに分けても結果は変わらない。**
  これは `_aggregate_current` / `_aggregate_baseline` の双方に当てはまる。
* バッチサイズは定数でよい。**`settings.properties` の設定項目を増やさない**(項目を増やす判断は人間に委ねる領域である)。
* `_aggregate_current` も同型の範囲結合であるため、**同じタスクの中で同じ方式に揃える**(同一の根本原因である)。

**採らない案とその理由**(いずれも前ループで実測・検討済み):

| 案 | 採らない理由 |
| --- | --- |
| 案 2 `CROSS JOIN` をやめて 1 本の範囲条件にする | `count(DISTINCT d.offset_day)` を別の形で求める必要があり、FR-075 の意味を変えないことの確認が別途要る。**案 1 と併用可能だが、まず案 1 だけで完了条件を満たすかを測る**(一度にひとつずつ修正する原則) |
| 案 3 既定の `max_memory` を引き上げる | **回避策であり、NFR-003 の「あふれたら退避して継続」を満たさない。**規模が伸びれば再発する。既定値の変更は仕様判断でもある |
| 案 4 `threads` を設定可能にする | 中間結果の大きさ自体は変わらず、本質的な解決にならない。設定項目を増やす判断は人間に委ねる |
| 案 5 検知点を減らす | **検知力を落とす判断であり人間の承認が要る。** `docs/ADR.md` ADR-013 が「遅いことを理由に検知力を落とす判断は範囲外」としている |

**案 1 で症状 1(OOM)は解消する見込みだが、症状 2(NFR-002 の 600 秒)には届かない可能性が高い。**
その場合の扱いは【未解決時の扱い】を参照。**時間が足りないことを理由に案 5 へ踏み込まないこと。**

## 4. 完了条件 2 が評価不能である理由(重要)

**修正前のコード自体が、同一入力・同一設定で実行するたびに異なる `report.md` を出力する。**
したがって「修正前と完全一致する」という完了条件は、**修正の成否にかかわらず原理的に満たせない。**

### 4.1 実測した証拠

**同一ツリー(F003 修正前)・同一設定(30 日分 / `max_memory` 16GB)・同一データで 2 回実行した結果:**

```
1 回目: exit=0 / 201.5s / report 14,393,736 バイト
2 回目: exit=0 / 187.4s / report 14,393,778 バイト
NG: **同一入力・同一設定で 2 回の結果が異なる** (差分行 308 / 全 168,141 行)
```

修正前のコードは、別々の実行で **14,393,784 / 14,393,760 / 14,393,737 / 14,393,736 / 14,393,778 バイト**と、**5 回とも異なるサイズ**の `report.md` を出した。

### 4.2 原因

`app/src/s_anomaly/correlate.py` の `_build` にある `rank()` である。

```python
def rank(item):
    magnitude = abs(item.change_ratio) if item.change_ratio is not None else 0.0
    return (0 if item.significant else 1, -magnitude, item.series_id, item.metric)
```

* `mu` と `mu_pct`、`ou` と `ou_pct`、`eu` と `eu_pct` は、**同じ量の絶対値と百分率であり互いに比例する**。したがって **`change_ratio` が数学的に同値**になる。
* ソートキーの第 2 要素 `-magnitude` が、DuckDB の `avg()` / `stddev_samp()` の並列集計に由来する**浮動小数点の下位ビットで揺れる**ため、同値ペアの順序が実行ごとに入れ替わる。
* さらに `[:MAX_CORRELATIONS]`(上位 10 件)の境界にかかると、**どちらが残るかも変わる。**

**観測された差分は、順序の入れ替わりと上位 10 件の入れ替わりのみである。** 相関の値そのもの(平常時・期間中・変化率・有意判定・注記)が変わった箇所は無い。

### 4.3 F003 が持ち込んだものではないことの確認

| ツリー | 規模 / 設定 | 同一条件 2 回実行の差 |
| --- | --- | --- |
| **修正前** | 30 日 / 16GB | **308 行**(バイト数も不一致) |
| **修正後** | 30 日 / 4GB | **34 行**(バイト数は 2 回とも 14,393,971 で一致) |

**F003 はこの揺れを 308 行から 34 行へ減らしたが、解消はしていない。**
バッチ分割で 1 回の集計が小さくなり並列パーティションのばらつきが減ったためと考えられる。

### 4.4 F003 の内容の同一性をどう確認したか

「完全一致」が使えないため、次の 2 つで代替した。

1. **14 日分のベースラインでの完全一致**: 退避物の修正前ツリーと現行ツリーを別々の一時ディレクトリへ展開し、同一入力(`app/tests/_work/normal/logs`)で実行したところ、`report.md` は**双方 477,751 バイト・9,107 行が実行日時の行を除いて完全一致**した。
   **ただしこの規模ではイベント数が `EVENT_BATCH`(500)を下回り、バッチ分割が発動しない。** したがって分割の正しさの証明にはならない。
2. **30 日分での差分の性質の確認**: 修正前後を同一データで実行して比較したところ、差分は **すべて `X` と `X_pct` の同値ペア**に関するものであり(順序の入れ替え 954 行、並び順を正規化しても残る上位 10 件の入れ替え 190 行)、**相関の値そのものが変わった箇所は 1 つも無かった。**
   同じ性質の差分が**修正前のコード同士の 2 回実行でも現れる**(4.1)ことから、**この差分は F003 の分割によるものではなく、既存の再現性欠陥によるものである。**

3. **理論的な裏づけ**: 集計は `GROUP BY` の第 1 キーが `event_id` でありイベントごとに閉じているため、バッチの切り方によらず各イベントの集計対象の行集合は同一である(ADR-014「理由」)。

## 6. 残課題

**NFR-009(再現性)を満たしていない。** 4 章に詳細を記した。
