## 4. PASS 以外の一覧(P202 への引き渡し)

### 4.1 A006 — 大規模データでの完走と実行時間

| 項目 | 内容 |
| --- | --- |
| 違反した要件 | **NFR-002**「1,000 万レコードで 10 分以内」 |
| 実施規模 | ★訂正★ **テーブル行 7,778,880 / ファイル上のデータ行 6,622,560** / 1,460 ファイル / 336 MB。**目標の 1,000 万レコードには到達していなかった**(当初 10,091,520 と記載していたが誤り。詳細は `docs/test-records/20260903-0010-test-record.md` の A006 末尾の訂正) |
| 実測 | **CPU 時間 101.3 分を消費した時点でも完了せず、中断した** |
| 超過率 | 目標 10 分に対して **10 倍以上**(完了していないため下限値)。**しかも目標より小さい規模での値である** |
| 完走の可否 | **未確認**(中断したため。`report.md` は生成されていない) |

**FAIL とした根拠**: A006【合否判定基準】の「CONDITIONAL FAIL(項目 3 のみ未達)」は項目 1(完走)が合格であることを条件とするが、本件は完走自体が未確認であるため、その区分には当たらない。

**P202 が切り分けるべき論点**(`docs/P009-acceptance-direction.md` 6章 #2):

1. **実装の問題か、目標値の問題か。** NFR-002 の「1,000 万レコードで 10 分以内」は ★FIXME★ が付された Agent の想定値であり、実運用の規模・許容時間の裏付けがない。
2. **どのステップが支配的か。** ★訂正★ 当初「S4 取り込みが約 2 秒」と記載したが、これは**最後の S4 ログ行から S5 の行までを測った誤りである**(S4 の開始点を取り違えていた)。P203 で測り直した正しい内訳は `docs/P202-fix-plan.md` 5 章および`docs/P202-fix-plan/P202-fix-unresolved.md` を参照。**91 日規模では S6(検知)が支配的だが、365 日規模では S4(取り込み)が最大になる**という、規模によって支配要因が入れ替わる関係にある。

3. **最初に疑うべき 2 つ**(A006【失敗時に記録する内容】の指示):
   * **`ALG-B2` の O(n²)**: `mann_kendall` は全ペア走査。`max_buckets = 2000` のとき 1 系列あたり約 200 万回の比較になる
   * **`ALG-A2` の窓ごとの全走査**: Hampel は窓ごとに中央値と MAD を求める

**あわせて申し送る測定手順の欠陥**: A006 は `time.monotonic()` で壁時計を測っているが、実行中にマシンがスリープすると休止時間が算入され測定値が使えなくなる(今回、経過 1,079.9 分に対し CPU は 101.3 分)。`subprocess.run(timeout=7200)` も発火しなかった。**再測定時は CPU 時間を測る必要がある。**
