本プロジェクトで現在有効な設計判断を管理する。過去に廃止された設計判断は `ADR_master.md` に移動する。

* 1 つの決定 = 1 つの ADR-NNN とする。
* 「決定内容」「理由」は、後続の AI(実装担当・修正担当)がそのまま読み込んで判断できる程度に簡潔にする。長い経緯や検討の過程そのものは書かず、結論とその根拠だけを残す。
* 状態が「廃止」になった ADR は、本文を `ADR_master.md` に移し、この `ADR.md` の一覧・本文からは削除する。

## ADR-001

### タイトル

DuckDB を `vendor/` に展開同梱して閉域配布する

### 状態

採用

### 日付

2026-09-02

### 関連要求

* FR-001(閉域環境にコピーするだけで動作する)
* FR-002(`vendor/` に同梱し `sys.path` で解決する)
* NFR-011(可搬性)

### 背景

配布先はインターネットに接続されていない閉域環境であり、`pip install` を実行できない。一方で `docs/P000-concept-analysis.md` 第2章はデータストアとして DuckDB を明示的に指定している。DuckDB は C++ で書かれたネイティブ拡張であり、「スクリプトそのまま」では動作しない。

### 決定内容

DuckDB の Python パッケージを、実行環境に対応したプラットフォーム別に `app/vendor/{os}-{arch}-cp{major}{minor}/` へ展開して同梱する。起動時に該当ディレクトリを `sys.path` の先頭へ挿入してから `import duckdb` する。実行時に `pip install` を行わない。

`vendor/` が実行環境と一致しない場合は、環境に導入済みの DuckDB へフォールバックする。この経路を通ったことは INFO ログと `report.md` の 1 章に必ず記録する。どちらも失敗した場合は終了コード 7 で、期待した `vendor` パス・実行環境・用意されている `vendor` の一覧を出して終了する。

### 理由

* `docs/P000-concept-analysis.md` が DuckDB を明示指定しており、人間に確認したうえで維持すると決定した(2026-09-02)
* DuckDB の分析向け窓関数・`quantile_cont`・列指向の集計性能が、アルゴリズム(現在 11 個)の実装コストと実行性能に直結する
* フォールバック経路が無いと、開発環境・CI でも毎回 `vendor/` の用意が必要になり、実装が進まない

### 検討した代替案

#### 標準ライブラリの `sqlite3` に切り替える

却下。理由: 同梱物ゼロで「スクリプトそのまま」を完全に満たせるが、`quantile_cont`(ALG-A3 が使う)を失って手書き実装になり、大規模データの集計性能も落ちるため。人間の判断を求め、DuckDB を維持する回答を得た。

#### `vendor/` を使わず、実行環境の DuckDB のみに依存する

却下。理由: 閉域環境に DuckDB が導入されている保証が無く、FR-001 を満たせないため。

### 残存リスク

★ACCEPTED★ 配布物が展開後 50〜80MB 増える。また `vendor/` の中身は Python マイナーバージョンと OS・アーキテクチャに 1 対 1 で対応するため、**配布先の Python 版が変わるたびに差し替えが必要**になる。配布先の版は本プロジェクトの時点では未確認であり、`vendor/` の実体整備は P302 に委ねている。フォールバック経路があるため、同梱漏れに気づかないまま動いてしまう危険があるが、これはログと `report.md` への必須記録で緩和する。

### 影響範囲

* `app/src/s_anomaly/bootstrap.py`
* `app/vendor/`
* 配布手順(README、P302)

### 関連成果物

* `docs/P001-requirement.md` 2.1
* `docs/P003-backend-spec.md` 2章
* `docs/P007-impl-direction/U001-foundation.md` U001-T1
* `docs/P009-acceptance-direction/A010-portability.md`

### 備考

`docs/P003-backend-spec.md` 16章で「ADR-001見込み」として参照されていたもの。

## ADR-002

### タイトル

外部パッケージを DuckDB のみに限定する

### 状態

採用

### 日付

2026-09-02

### 関連要求

* FR-003(外部パッケージは DuckDB のみ)
* NFR-008(ネットワーク通信を行わない)

### 背景

ADR-001 により、外部パッケージは 1 つ増えるごとに `vendor/` への同梱コストと配布物サイズが増える。統計処理を行うアプリでは numpy / scipy / scikit-learn / statsmodels を使いたくなるが、いずれもネイティブ拡張または大規模な依存ツリーを持つ。

### 決定内容

依存する外部パッケージは DuckDB のみとする。統計計算は **DuckDB の SQL 窓関数と Python 標準ライブラリ(`statistics` / `math`)** で行う。テストフレームワークも標準ライブラリの `unittest` を使い、pytest を使わない。カバレッジ計測ツールも導入しない。

`socket` / `urllib` / `http` / `requests` などネットワーク関連モジュールも import しない。DuckDB の拡張自動ダウンロードは初期化時に無効化する。

### 理由

* 同梱コストを最小に保つ(DuckDB 1 つで 50〜80MB。scikit-learn を加えると数倍になる)
* 「配布資産をコピーすればテストも走る」状態を保てる
* 閉域環境で拡張の自動ダウンロードが走ると、長時間のタイムアウト待ちで実行が止まる

### 検討した代替案

#### scikit-learn の Isolation Forest / One-Class SVM / LOF を使う

却下。理由: 依存ツリーが大きく、閉域配布のコストが DuckDB 1 つの比ではないため。

#### statsmodels の STL 分解を使う

却下。理由: 同上。周期性の考慮は ALG-A5(曜日・時刻別ベースライン)で簡易的に代替する。

#### 開発時のみ `coverage.py` を使う

却下。理由: テスト実行にも同じ制約を課すことで、配布資産の完結性を保てるため。行カバレッジの代わりに「対象の一覧に対する 1 対 1 のテスト」で網羅を担保する。

### 残存リスク

★ACCEPTED★ 多変量の異常検知(複数メトリクス間の相関崩れ)と、複数周期が重畳する季節性の残差分析は実装できない。ALG-A5 は STL の簡易代替であり、複数周期には対応しない。また行カバレッジの数値を示せない。

### 影響範囲

* `app/src/s_anomaly/detectors/` 全体
* `app/tests/` 全体
* `docs/P006-test-plan.md` のテスト方針

### 関連成果物

* `docs/P001-requirement.md` FR-003, 10.1 の ★ACCEPTED★
* `docs/P006-test-plan.md` 4.1, 4.5
* `docs/P009-acceptance-direction/A008-no-network.md`

### 備考

`docs/P003-backend-spec.md` 16章で「ADR-002見込み」として参照されていたもの。

## ADR-003

### タイトル

分散の下限(`effective_sigma`)を全アルゴリズムに共通適用する

### 状態

採用

### 日付

2026-09-02

### 関連要求

* FR-050〜FR-054(異常検知アルゴリズム)
* NFR-009(再現性)

### 背景

本アプリが扱うデータには、`active_connections` / `pend` / `susp` のように**小さな整数で、ほとんど一定**の系列が多い。標準偏差が 0 または極小のとき `|x − μ| / σ` は発散し、`0 → 1` のような些細な変化が FATAL として大量に検出される。これは本アプリで最も誤検知を生みやすい構造である。

### 決定内容

実効的なばらつきを次で定義し、σ・MAD・IQR を用いる**全アルゴリズムで共通に**使う。

```
effective_sigma = max(σ, sigma_floor_ratio × |μ|, sigma_floor_abs)
```

既定値は `sigma_floor_ratio = 0.02`、`sigma_floor_abs = 0.5`。いずれも `settings.properties` で上書きできる。実装は `detectors/base.py` の共通関数とし、各アルゴリズムで個別に実装しない。

### 理由

* ゼロ除算を構造的に防げる(1 箇所で担保できる)
* 微小分散の系列での誤検知を、閾値を系列ごとに調整することなく抑えられる
* 1 つの機構でゼロ分散と微小分散の両方に対応でき、説明が容易である

### 検討した代替案

#### アルゴリズムごとに個別のガードを書く

却下。理由: 10 個すべてに同じ考慮を漏れなく入れる必要があり、抜けが生じやすいため。

#### σ = 0 の系列を検知対象から除外する

却下。理由: 「常に 0 だった `susp` が突然 5 になった」という運用上重要な変化を見逃すため。

#### 絶対値の下限だけを設ける

却下。理由: 平均が大きい系列(ヒープ使用量 KB など)では絶対値の下限が効かず、微小分散の問題が残るため。相対と絶対の両方を取る。

### 残存リスク

★ACCEPTED★ 既定値 0.02 / 0.5 は実データでの検証を経ていない Agent の想定である。実運用で誤検知が多い/少ない場合は最初に調整すべきパラメータになる。また、この下限により**本当に微小な変動しか持たない系列での真の異常**は検知しづらくなる。

### 影響範囲

* `app/src/s_anomaly/detectors/base.py` および全検知器(現在 11 個)
* `settings.properties` の `common.sigma_floor_ratio` / `common.sigma_floor_abs`

### 関連成果物

* `docs/P003-backend-spec.md` DS-08-03
* `docs/P006-test-plan.md` F-10
* `docs/P007-impl-direction/U005-detectors-a.md` U005-T1

### 備考

`docs/P003-backend-spec.md` 16章で「ADR-003見込み」として参照されていたもの。

## ADR-004

### タイトル

jstat の形式判別はデータ行の列数を見出しより優先する

### 状態

採用

### 日付

2026-09-02

### 関連要求

* FR-012(jstat の 2 形式を判別して受け付ける)
* FR-014(解析できない行は読み飛ばす)

### 背景

`docs/P000-concept-analysis.md` 第3章に示された jstat のサンプルは、**見出し行が `-gc` 系の列名(17 列)、データ行が `-gcutil` の値(12 個)**という食い違いを持つ。見出しを信じて解析すると、全データ行が「列数不一致」となり、ファイルが丸ごと失われる。

### 決定内容

形式判別は次の順で行う。

1. **最初のデータ行の値の個数**で判定する。12 なら `-gcutil`、17 または 18 なら `-gc`。
2. 1 で決まらない場合のみ、見出しの列名集合で判定する。
3. どちらでも決まらなければ `見出し不明` としてファイル全体を読み飛ばす。

### 理由

* 実データの形状(値の個数)は、見出しの記載よりも確実な情報である
* 見出しを優先すると、P000 に示された実サンプル形状のファイルを 1 行も読めない
* 誤って読み飛ばすより、誤って読み込むほうが被害が小さい(値の範囲でおかしさに気づける)

### 検討した代替案

#### `-gcutil` に決め打ちする

却下。理由: `-gc` 形式のファイルが実環境に混在する可能性を排除できないため。

#### 見出しを優先する

却下。理由: P000 の実サンプル形状でファイルが丸ごと失われるため。

### 残存リスク

★ACCEPTED★ 「見出しだけ `-gc`」というファイルが実在するのか、それとも P000 への転記時に生じた混在なのかは未確認である(`docs/P001-requirement.md` 20章の確認では列名の綴りのみが確定した)。前者であれば本決定は正しく、後者であれば実データは常に一方の形式である。いずれの場合も本決定は安全側に働くが、**列数が 12/17/18 のいずれでもない未知の形式**は読み飛ばされる。

### 影響範囲

* `app/src/s_anomaly/loaders/jstat.py`

### 関連成果物

* `docs/P002-frontend-spec.md` 7.2, UI-07-01
* `docs/P003-backend-spec.md` DS-05-01, DS-05-02
* `docs/P007-impl-direction/U002-ingest.md` U002-T4

## ADR-005

### タイトル

使用率メトリクス(`*_pct`)を導出し、脅威度判定にのみ用いる

### 状態

採用

### 日付

2026-09-02

### 関連要求

* FR-022, FR-023(統一ビュー `metrics` と監視対象メトリクス)
* FR-060(脅威度の判定)

### 背景

jstat の `-gc` 形式は使用量を KB で、`-gcutil` 形式は使用率を % で出力する。同じ `ou`(Old 世代)というメトリクス名でも単位が異なる。一方、脅威度 SEVERE の判定条件は「使用率が 90% を超える」という**割合に依存する規則**である。

### 決定内容

`metrics` に `ou_pct` / `eu_pct` / `mu_pct` を導出列として持つ。`-gcutil` 形式ではそのまま、`-gc` 形式では `使用量 / 容量 × 100` で算出し、容量が NULL または 0 なら NULL とする。

**`*_pct` は検知アルゴリズムの入力から除外し、脅威度判定と原因候補の材料としてのみ用いる。** 検知は常に `ou` / `eu` / `mu` に対して行う。

### 理由

* 検知アルゴリズムを形式ごとに分岐させずに済む(`expected.json` による結合テストの期待値が形式で分岐しない)
* `ou` と `ou_pct` の両方を検知対象にすると、`-gcutil` 形式では同じ異常が 2 件出る
* 上限が取得できない場合(`-gc` 形式で容量列が無い)に SEVERE を出さない、という安全側の判定ができる

### 検討した代替案

#### 形式ごとに検知対象のメトリクス名を切り替える

却下。理由: 同じメトリクス名の系列が環境によって別物になり、テストの期待値が形式ごとに分岐して複雑になるため。

#### KB 値のまま 90 と比較する

却下。理由: KB 値は常に 90 を超えるため、全件が SEVERE になる。単位を無視した比較は判定を無意味にする。

### 残存リスク

★ACCEPTED★ `-gc` 形式のホストでは、ヒープ最大量が変更された前後をまたぐ期間で `ou`(KB)の傾向が実態とずれる(容量が増えれば使用量も自然に増えるため)。この場合 `ou_pct` のほうが正しいが、検知は `ou` で行われる。また `db_connection` にはプール上限の情報が無いため、使用率による SEVERE 判定ができず、「増加が止まっていない」ことで代替している。

### 影響範囲

* `app/src/s_anomaly/metrics.py`
* `app/src/s_anomaly/events.py`(SEVERE 判定)
* `app/src/s_anomaly/causes.py`(CR-06 が `ou_pct` を参照)

### 関連成果物

* `docs/P002-frontend-spec.md` 9.1 #3, #4
* `docs/P003-backend-spec.md` DS-07-05 〜 DS-07-07, DS-09-05
* `docs/P007-impl-direction/U004-metrics.md` U004-T2

### 備考

`docs/P003-backend-spec.md` 16章で「ADR-005見込み」として参照されていたもの。

## ADR-006

### タイトル

単一プロセスの CLI とし、クロスオリジンの論点は該当なしとする

### 状態

採用

### 日付

2026-09-02

### 関連要求

* FR-030(コマンドは 1 つ)
* NFR-008(ネットワーク通信を行わない)

### 背景

`SKILL-P003-backend-spec.md` は、クライアントとサーバを別プロセス/別ポートで開発・テストする構成の場合に、クロスオリジンの対処方針を決めて記録することを求めている。この方針は、P009 がテストハーネスを組む際の前提になる。

### 決定内容

本アプリは **HTTP を持たない単一プロセスの CLI** であり、クロスオリジンの論点は**該当しない**。テストハーネスは、サブプロセスとしてアプリを起動し、終了コード・標準出力・標準エラー・`report.md` を検証する形とする。ネットワークを介さない。

各テストは `tempfile.TemporaryDirectory` で自分専用の作業ディレクトリを作り、そこを `cwd` として起動する(`report.md` がカレントディレクトリに出力されるため)。

### 理由

* 該当しないことを明示的に記録しないと、後続フェーズが「決定が漏れている」と誤解する

* ルールを宣言的な表として持つことで、実データにもとづく追加・調整が容易になる

#### 確度を百分率で表現する

却下。理由: 統計的な裏付けが無い数値であり、「70%」と書くと確からしさを過大に伝えるため。

#### 原因候補を出さず、検知結果だけを出す

却下。理由: `docs/P000-concept-analysis.md` が明示的に求めている項目であるため。

### 残存リスク

★ACCEPTED★ ルール表は Agent が一般的な運用知識から作成したものであり、**対象システム固有の事情**(特定バッチの実行、定例メンテナンス)を反映していない。実運用で頻出する原因を人間から追加してもらう必要がある。また 9 ルールのいずれにも該当しないイベントでは「該当する候補なし」となり、後段の LLM が推論の手がかりを得られない。

## ADR-011

### タイトル

一括挿入は `executemany` ではなく一時 CSV + `read_csv` で行う

### 状態

採用

### 日付

2026-09-02

### 関連要求

* NFR-001(最大 1 万ファイル / 1 億レコード)
* NFR-002(1,000 万レコードで 10 分以内)

### 背景

`docs/P003-backend-spec.md` DS-LD-04 は「10,000 行ごとの `executemany`」で挿入することを定めていた。P102(実装)でこの方式を実装し、生成テストデータ(約 44,000 レコード、56 ファイル)に対して実行したところ、**通し実行に 123.8 秒**を要した。

原因を切り分けるため、DuckDB 単体で挿入方式を計測した。

| 方式 | 実測 |
| --- | --- |
| `executemany`(Windows, Python 3.14.2) | **約 500 行/秒** |
| `executemany`(Linux WSL2, Python 3.10.12) | **約 119 行/秒** |
| `BEGIN TRANSACTION` + `executemany` | 約 593 行/秒 |
| 複数行 `VALUES` 句(500 行/文) | 約 873 行/秒 |
| **一時 CSV へ書き出して `read_csv` で投入** | **約 143,000 行/秒** |

DuckDB 自体は高速である(100 万行の `CREATE TABLE AS SELECT` が 0.04 秒、パラメータ付き `SELECT ?` が 0.5 ミリ秒)。遅いのは **`executemany` が 1 行ずつ prepared statement を実行する経路**に限られる。この方式では 1,000 万レコードの投入だけで 5 時間以上かかり、NFR-002 を満たせない。

### 決定内容

`BatchInserter` は、バッファした行を**一時 CSV ファイルへ書き出し、`INSERT INTO t SELECT * FROM read_csv(path, header=false, columns={...}, nullstr='\N')` で一括投入する**。一時ファイルは投入後に必ず削除する(`try/finally`)。

NULL は CSV 上で番兵 `\N` として表現し、`nullstr` で指定する(空文字と NULL を区別するため)。時刻は `%Y-%m-%d %H:%M:%S`、浮動小数点は `repr()` で往復可能な精度で書き出す。

### 理由

* 240 倍の高速化により、NFR-002 の達成が現実的になる(実測で通し実行 123.8 秒 → 7.3 秒)
* 追加の依存パッケージを必要としない(`csv` / `tempfile` は標準ライブラリ。ADR-002 と両立する)
* 列型を `columns={...}` で明示するため、型推論のぶれが入らない

### 検討した代替案

#### `BEGIN TRANSACTION` で囲む

却下。理由: 593 行/秒にしかならず、桁が変わらないため。

#### 複数行 `VALUES` 句をまとめて発行する

却下。理由: 873 行/秒にとどまるうえ、SQL 文が巨大になりパース時間が支配的になるため。

#### pandas / pyarrow 経由で投入する

却下。理由: ADR-002(外部パッケージは DuckDB のみ)に反するため。

### 残存リスク

★ACCEPTED★ 一時ファイルの書き込みが発生するため、**ディスク I/O が使えない環境や、一時領域の容量が逼迫した環境では失敗しうる**。検討: メモリ上の擬似ファイルを使う案。**不採用**: DuckDB の `read_csv` はファイルパスを要求し、Python のファイルライクオブジェクトを受け付けないため。残存リスク: 一時ファイルの作成に失敗した場合は例外となり、`cli` が終了コード 6(`StorageError`)へ変換する。また、CSV 経由であるため**値に含まれる改行・引用符は `csv` モジュールのエスケープに依存する**。本アプリの入力(ホスト名・データソース名・QUEUE 名)にこれらが含まれることは想定していないが、含まれた場合も `csv.writer` と `read_csv` の既定の引用規則で往復する。

### 影響範囲

* `app/src/s_anomaly/loaders/__init__.py`(`BatchInserter`)
* `app/src/s_anomaly/schema.py`(`COLUMN_TYPES` を追加)

### 関連成果物

* `docs/P003-backend-spec.md` DS-LD-04(**本 ADR により方式が変更されている**)
* `docs/P001-requirement.md` NFR-002
* `docs/P009-acceptance-direction/A006-performance.md`

### 備考

本 ADR は P102(実装)の実測にもとづき、設計フェーズの決定(DS-LD-04)を上書きするものである。P021 の実行後に追加したため、`docs/P003-backend-spec.md` 16章の表にも追記した。

## ADR-012

### タイトル

観点1 は「移動平均からの残差」を残差自身の σ で正規化し、持続性規則を課す

### 状態

採用

### 日付

2026-09-02

### 関連要求

* ALG-A1(移動平均乖離率)、ALG-A2(Hampel)、ALG-A4(EWMA)
* FR-050(代表的なアルゴリズムを実装する)

### 背景

`docs/P003-backend-spec.md` DS-08-A1-01 は「`|x − μ_window| / σ_window`」で判定することを定めていた。P102 で実装し、生成テストデータ(日次の周期を持つ運用ログ相当)に対して実行したところ、**異常を埋め込んでいない系列でも検知率が 15%(4,032 点中 600 点超)** となった。

原因は 2 つある。

1. **移動平均は系列の傾き・周期に対して系統的に遅れる。** 日次の周期を持つ系列では、周期の立ち上がり・立ち下がりで `x − μ_window` に決定的な成分が乗る。窓内の値の σ で割ると、この決定的な成分が毎日「異常」として検出される。
2. **4,000 点の系列に 2σ の判定を素朴に当てると、正規分布のノイズだけでも統計的に約 180 点が閾値を超える。** 単発の 2σ 超えを 1 件ずつ報告すると、レポートが偶然のゆらぎで埋まる。

実測値は次のとおり(`lsf_queue/lsfhost01/short` は異常を埋め込んでいない系列)。

| 方式 | 異常なし系列の検知率 |
| --- | --- |
| 窓内の σ で正規化(当初の設計) | **15%** |
| 残差の σ で正規化 | 4.4%(2σ) / 0.1%(3σ) |
| 残差の σ + 持続性規則 | **0.7%** |

### 決定内容

**(1) 残差ベースの正規化。** ALG-A1 / A2 / A4 は、移動平均(A2 は移動中央値)からの残差 `e_t = x_t − μ_window(t)` を求め、**残差そのものの分布の σ(A2 は MAD)で正規化する**。窓内の値の σ で割らない。

**(2) EWMA の対象を残差にする。** ALG-A4 は生値ではなく残差を平滑化する。EWMA 管理図は定常過程を前提としており、周期を持つ系列に生値を当てると周期そのものが管理限界外になるため。

**(3) 持続性規則。** 観点1 の検知点は、次のいずれかを満たすものだけを残す(`detectors/base.py` の `apply_persistence_rule` に 1 箇所で実装)。

* `score >= 2.0`(= FATAL 閾値相当。仕様上の `k_fatal` に対応)の単発点
* 連続する 2 点以上が同時に閾値を超えている(持続している)

これは管理図の標準的な判定規則(Western Electric rules)の考え方である。

### 理由

* 「移動平均乖離率が 2σ/3σ」という P000 の表現に、残差の σ で測るほうが忠実である(「乖離率」の分布に対する σ)
* 決定的な周期成分を基準に織り込めるため、系列ごとに閾値を調整せずに済む
* 単発の 2σ 超えを信号としないのは管理図の標準的な運用であり、統計的に妥当である
* 実測で検知率が 15% → 0.7% に下がり、かつ埋め込んだ異常の最大スコアは 5〜85(異常なし系列の最大 2.82)と、明確に分離する

### 検討した代替案

#### 閾値 k を大きくする

却下。理由: P000 が「2σ、3σ」を明示しており、閾値の変更は要求の解釈を変えてしまう。また周期成分による系統的なずれは閾値を上げても消えない(見逃しが増えるだけ)。

#### ALG-A3 の「5% 超過で全破棄」規則を A1/A2/A4 にも広げる

却下(単独では)。理由: 破棄しても「検知できない」だけで、周期成分を基準に織り込む問題は解決しないため。ただし A3 の 5% 規則自体は維持している。

#### 中央化した窓(未来の点を含む)を使う

却下。理由: 遅れは消えるが、`docs/P003-backend-spec.md` DS-08-A1-01 が定める「直前 N 分」の窓の定義から外れ、リアルタイム適用の余地も失うため。

#### 異常なし系列の周期性を弱めてテストデータを易しくする

却下。理由: アルゴリズムをテストデータに合わせることになり、実データで同じ問題が再発するため。実運用ログは日次の周期を持つのが普通である。

### 残存リスク

★ACCEPTED★ **異常を埋め込んでいない系列でも、検知点は 0 にはならない**(実測 0.7%)。統計的な判定である以上、4,000 点の系列で閾値超えが 1 件も出ないことは期待できない。検討: さらに閾値を上げる、または観点1 の結果を FATAL 以上に限って報告する案。**不採用**: 前者は見逃しを増やし、後者は P000 が求める 4 段階の脅威度(INFO/WARN も報告対象)と矛盾するため。**この結果として、受け入れ判定の「誤検知 0 件」という基準は達成不能であることが判明したため、基準を「検知率 1% 未満、かつ SEVERE 0 件」へ改めた**(`docs/P002-frontend-spec.md` UI-08-03、`docs/P006-test-plan.md` TP-15)。この基準の妥当性は実データでの確認が必要であり、**P302 で CR の起票候補として人間に引き渡す**。

### 影響範囲

* `app/src/s_anomaly/detectors/base.py`(`apply_persistence_rule`, `WINDOW_MIN_POINTS`)
* `app/src/s_anomaly/detectors/a1_ma_sigma.py`, `a2_hampel.py`, `a4_ewma.py`
* `docs/P002-frontend-spec.md` UI-08-03、`docs/P006-test-plan.md` TP-15(判定基準)

### 関連成果物

* `docs/P003-backend-spec.md` DS-08-A1-01 / DS-08-A2-02 / DS-08-A4-01(**本 ADR により方式が変更されている**)
* `docs/ADR.md` ADR-003(`effective_sigma`。本 ADR と併用する)

### 備考

あわせて `WINDOW_MIN_POINTS = 5` を導入した。`common.min_points`(既定 30)は FR-053 が定める**系列**レベルの下限であり、これを窓内の点数へ適用すると、既定値の組み合わせ(窓 60 分 × サンプリング間隔 5 分 = 窓内 12 点)では**窓内の点数が 30 に到達しえず、A1/A2 が永久に何も検知しない**。窓内の最小点数は別に定める必要がある。

## ADR-013

### タイトル

時刻窓の集計は、時刻昇順を利用した二分探索で範囲を絞ってから走査する

### 状態

採用

### 日付

2026-09-03

### 関連要求

* NFR-002(1,000 万レコードで 10 分以内)
* ALG-B4(CUSUM。シフト前後の水準を窓平均で求める)

### 背景

P201(受け入れ結合テスト)の A006 で、**1,009 万レコードに対する解析が CPU 時間 101.3 分を消費しても完了しなかった**。

規模別に S6(検知)のアルゴリズム別所要時間を実測したところ、**ALG-B4 だけが全体の 53%(S6 の 75%)を占めていた**。

| アルゴリズム | 44K レコード | 288K レコード | 524K レコード |
| --- | --- | --- | --- |
| ALG-B4 | 1.5s | 65.9s | **132.8s** |
| 他 9 個の合計 | 4.0s | 21.4s | 37.3s |

原因は `b4_cusum.py` の `_mean_after` / `_mean_before` にあった。

```python
values = [v for ts, v in points[index:]                      # index から末尾まで全走査
          if (ts - start_ts).total_seconds() <= window_sec]  # そのうち窓内だけを残す
```

窓幅は `baseline_minutes = 1440`(5 分間隔で 288 点)だが、91 日の系列は 26,208 点ある。**必要な 288 点を得るために毎回 26,000 点を走査していた。** 計算量は O(検知件数 × 系列長) である。

### 決定内容

**時刻で区切る窓の集計は、系列が時刻昇順であることを利用して、`bisect` で窓の境界を求めてからその範囲だけを走査する。**

* 系列あたり 1 度だけ「先頭からの経過秒」の配列を作る。**検知ごとに作り直さない**(作り直すと元の計算量に戻る)。
* 経過秒は `datetime.timestamp()` ではなく **先頭との `timedelta` 差**で求める。`timestamp()` の差は夏時間の切り替えをまたぐと壁時計の差と一致しないため、境界の判定が変わりうる。
* `bisect_right` / `bisect_left` の選択は、置き換え前の比較演算子(`<=` / `>=`)に対応させる。

### 理由

* **計算量が O(検知件数 × 系列長) から O(検知件数 × 窓幅) になる。** 窓幅は設定値であり系列長に依存しない。
* **戻り値が変わらない。** 実測条件(系列長 26,208 点 / 1 組あたり検知 143 件 / 窓 1440 分)で置き換え前後の値が完全に一致することを確認した。
* `bisect` は Python 標準ライブラリであり、FR-003(DuckDB 以外の外部依存を持たない)に抵触しない。

### 実測した効果

| | 修正前 | 修正後 |
| --- | --- | --- |
| ALG-B4(524K レコード) | 132.8s | **4.0s** |
| 全体(524K レコード) | 249.3s | **114.8s** |
| 全体(288K レコード) | 156.4s | **94.4s** |

検知点数は 3 規模とも修正前と同一(1,902 / 17,107 / 31,676)であり、14 日データの `report.md` は実行日時の行を除いてバイト単位で一致した。

### 検討したが採らなかった案

#### 2 ポインタ走査(`base.py` の `seasonal_diffs` と同じ書き方)

却下。理由: `seasonal_diffs` は先頭から順に 1 度だけ走査するため 2 ポインタで足りるが、CUSUM の窓平均は**検知が起きた位置から前後に広げる**ため、走査位置が単調に進まない。二分探索のほうが素直である。

#### 累積和を事前計算して O(1) で窓平均を求める

却下。理由: 計算量はさらに下がるが、**サンプリング間隔が一定でない系列**(欠測・採取停止。FR-054)では窓内の点数が可変であり、点数も別途求める必要がある。二分探索なら点数も同時に得られ、実測でも既に十分速い(4.0s)。複雑さに見合う利益がない。

#### ALG-B4 を既定で無効にする

却下。理由: `settings.properties` で ON/OFF できるが、既定で切ると FR-050(観点2 に代表的なアルゴリズムを複数実装する)を満たさなくなる。**遅いことを理由に検知力を落とす判断は本 ADR の範囲外**であり、実装の欠陥を直すのが先である。

### 残存リスク

★ACCEPTED★ **本 ADR の修正だけでは A006 は PASS にならない。** ただし **2026-09-04 に確定した規模で測り直した結果、残る障害は本 ADR が想定していた「実行時間」ではなく、S8(相関の集計)の別の欠陥であった。**

★訂正 2026-09-04 / P203★ 当初ここには「524K レコードでの実測 114.8 秒から目標規模(19.3 倍)へ外挿すると約 37 分」と書いていたが、**この外挿は前提が失効している**。(a) 解析対象の期間が人間により 365 日から 90 日へ確定したこと、(b) 規模を伸ばすと支配要因が S6 から S8 へ入れ替わり線形にならないこと、の 2 点による。確定規模での実測は次のとおりである。

| ケース | max_memory | 終了コード | 所要 | S8 の占める割合 |
| --- | --- | --- | --- | --- |
| 通常 30 日(950,400 行) | **4GB(既定)** | **6** | 363.6s で異常終了 | S8 の実行中に OOM |
| 通常 30 日 | 16GB | 0 | 191.3s | 114s(60%) |
| **大規模 90 日(2,851,200 行)** | **4GB(既定)** | **6** | 828.7s / 847.2s で異常終了 | S8 の実行中に OOM |
| **大規模 90 日** | 16GB | 0 | **876.2s** | **635s(72%)** |

**本 ADR の修正後、ALG-B4 は S6 45 秒のうち 6.3 秒(14%)にすぎず、支配要因ではない。** 支配しているのは S8 である。

検討: さらなる最適化(S8 の集計をイベントのバッチに分割する、`_aggregate_baseline` の CROSS JOIN をやめる)。**本 ADR では採らない**: S8 は本 ADR の対象(時刻窓の集計を二分探索で絞る)とは別の箇所であり、DS-11-05「1 回の結合で集計する」の見直しという設計判断を伴うため。**実測値と対処案を添えて人間の判断を仰ぐ**(`docs/P202-fix-plan/P202-fix-unresolved.md`、`docs/P302-deliver.md`)。

### 影響範囲

* `app/src/s_anomaly/detectors/b4_cusum.py`(`_scan`, `_mean_after`, `_mean_before`)

**同種の全走査が他に存在しないことを確認した**(`points[index:]` / `points[:index]` 形の走査は `b4_cusum.py` の 2 箇所のみ)。今後、時刻窓の集計を追加する際は本 ADR に従うこと。

### 関連成果物

* `docs/P202-fix-plan/fixed/F001-alg-b4-window-scan.md`(修正の詳細)
* `docs/P009-acceptance-direction/A006-performance.md`(判定基準)
* `docs/test-records/20260903-0010-test-record.md` の A006(修正前の実測)

## ADR-015

### タイトル

レポートは「列挙」と「集計」の 2 層で出力し、ホスト × 年月に分割する

### 状態

採用

### 日付

2026-09-05

### 関連要求

* FR-070(レポートの出力)、FR-077(ホスト別レポートの構成)、**FR-078(サマリの構成)**
* CR-001 / CR-004

### 背景

**単一の `report.md` は、コンテキスト長 4K トークンのローカル LLM で扱えなかった。**
確定した規模での実測は次のとおりである。

| 規模 | サイズ | 行数 | イベント数 | 概算トークン |
| --- | --- | --- | --- | --- |
| 通常 30 日 | 14,393,965 バイト | 168,142 | 7,229 | 約 1,150 万 |
| 大規模 90 日 | 41,214,032 バイト | — | 21,307 | 約 3,300 万 |

**4K の約 2,900 倍**である。

**絞り込みでは届かないことを実測で確認した。**

| 案 | サイズ | 4K 比 |
| --- | --- | --- |
| 相関を 10 → 3 行 | 8.0MB | 1,600 倍 |
| 相関欄ごと削除 | 5.0MB | 1,000 倍 |
| SEVERE のみ全文(416 件) | 927KB | 185 倍 |
| **SEVERE のみ + 相関 3 行** | **565KB** | **113 倍** |

**最も攻めた絞り込みでも 100 倍以上残る。**

原因は単純である。**1 イベントあたり約 728 バイト ≒ 582 トークン**あり、
4K のうち入力に使える 3,000 トークンに収まるのは**約 5 件**にすぎない。
**イベントを 1 件ずつ並べる形式である限り、どれだけ絞っても、また分割の粒度を細かくしても 4K には入らない**
(全 7,229 件を載せるには約 1,400 ファイルが必要になる)。

### 決定内容

**レポートを「列挙」と「集計」の 2 層で出力する。**

| 層 | ファイル | 内容 | 想定する読み手 |
| --- | --- | --- | --- |
| **集計** | `report_summary_{yyyymm}.md` | 全ホスト横断の集計。ホスト別・日別・複数ホスト同時発生 | **4K の LLM。まずこれを読む** |
| **集計** | 各 `report_{HOST}_{yyyymm}.md` の「1. このホストの集計」 | そのホストのメトリクス別集計 | **4K の LLM。注目したホストだけ読む** |
| **列挙** | 各 `report_{HOST}_{yyyymm}.md` の「4. 検知イベント」 | イベント本文 | 人間、または大きなコンテキストのモデル |

**あわせて、列挙の層をホスト × 年月に分割する。**

* 分割の単位を**ホスト**にしたのは、運用者が「どのサーバで何が起きたか」を軸に見るためである。
* 分割の単位に**年月**を加えたのは、期間が伸びてもファイルサイズが線形に伸び続けないようにするためである。

### 理由

* **集計はアプリが行う。LLM に数えさせない。** 4K の LLM は全イベントを読めないため、
  LLM 自身に集計させることは原理的に不可能である。
* **集計章はイベント数に比例しない。** ホスト別の集計章はメトリクスの種類数(最大 11)で行数が決まり、
  サマリのホスト別表はホスト数で決まる。**規模が伸びても 4K に収まり続ける。**
* **各ファイルから全体像へ辿れる。** ホスト別ファイルの「2. 実行サマリ」に、
  対応するサマリのファイル名を載せる(P002 UI-04-F08)。

### 実測した効果(30 日規模の実データで、集計表を実際に組み立てて計測した)

| 出力 | サイズ | 概算トークン | 4K |
| --- | --- | --- | --- |
| `report_summary_202606.md`(ホスト 17 行 + 日別 30 行) | 2,764 バイト | 約 2,211 | **○** |
| ホスト別「1. このホストの集計」(最大: host01) | 512 バイト | 約 409 | **○** |
| ホスト別「1. このホストの集計」(最小: host14) | 244 バイト | 約 195 | **○** |

**全 17 ファイルの集計章が 4K に収まる。** イベント数が最多の `lsfhost01`(2,183 件)でも 393 トークンである。

### 検討したが採らなかった案

#### 分割の粒度をさらに細かくして、本文ごと 4K に収める

却下。理由: 1 イベント約 582 トークンであるため、1 ファイルあたり約 5 件が上限になり、
**7,229 件では約 1,400 ファイル**になる。LLM を 1,400 回呼ぶ運用は現実的でない。

#### イベントを脅威度で絞って出力する(SEVERE のみなど)

却下。理由: 実測で 113 倍残る(上表)。**かつ、絞ると検知したものを捨てることになる。**
本アプリの目的は「膨大なログから異常な箇所を見つける」ことであり、
見つけたものを出力段階で捨てるのは目的に反する。**絞り込みは読み手が行えばよい。**

#### 出力を JSON / TSV にして装飾を削る

却下。理由: 削減率は 2〜3 割にとどまり、単独では足りない。
また P000 が Markdown の書式を明示的に指定している。

### 残存リスク

★FIXME★ **4K に収まることの判定を、バイト数(4,000 バイト)で代用している。**
トークナイザが配布資産に含まれないため(FR-003 により外部依存は DuckDB のみ)、
**厳密なトークン数の計測ができない。** 日本語混じり Markdown での「1 トークン ≒ 1.25 バイト」は
Agent の想定であり、実際のローカル LLM のトークナイザで確認が要る。

★FIXME★ **90 日規模ではサマリの日別表が 90 行になり、約 4,000 トークンに達する見込みである。**
そのため**対象期間が 31 日を超える場合は週単位に切り替える**(P003 DS-12-08)。
**閾値を 31 日としたのは Agent の想定である。**

★ACCEPTED★ **ファイル数が増える。** 30 日規模で 18 ファイル(ホスト別 17 + サマリ 1)、
90 日規模では最大 3 か月分に分かれるため 52 ファイルになりうる。
検討: 1 ファイルにまとめて章で分ける案。**不採用**: それでは 1 ファイルが再び巨大になり、
4K の LLM が「必要な部分だけ読む」ことができない。**残存リスク**: 出力先ディレクトリが
ファイルで埋まる。依頼者は「ファイル数が多くなって構わない」と明示している(CR-001)。

### 影響範囲

* `app/src/s_anomaly/reporter.py`(M12。分割・集計・サマリの生成)
* `app/src/s_anomaly/cli.py`(S9 の呼び出し)
* `app/tests/integration/report_parser.py`、`app/tests/acceptance/_harness.py`(**レポートの読み取り側**)

**ADR-009 が予告していた依存が現実化した。** レポートの書式・ファイル構成を変えるときは、
**テスト側の解析処理を必ず同時に直す。**

### 関連成果物

* `docs/P901-cr-direction/CR-001.md`、`docs/P901-cr-direction/CR-004.md`
* `docs/P002-frontend-spec.md` 4.1(UI-04-F01〜F10)
* `docs/P003-backend-spec.md` DS-12-05〜DS-12-08

## ADR-016 — 上限値は入力に無ければ解析期間中の実測最大値から推定する

* 状態: 採用
* 決定日: 2026-09-05(CR-005)

### 背景

依頼者の目的は「**DBConnection や Java のメモリが上限値に張りついていることを知りたい**」で
ある。しかし**入力にコネクションプールの上限値が無い。** 上限が分からなければ
「上限に張り付いている」は判定できない。

### 検討した選択肢

| 案 | 内容 | 判断 |
| --- | --- | --- |
| A | 入力(`DBConnection*.csv`)に上限値の列を足してもらう | **不採用** |
| B | `settings.properties` に系列ごとの上限を書く | **不採用** |
| **C** | **解析期間中の実測最大値を推定上限とする** | **採用** |

### 決定と理由

**案 C を採る。依頼者の明示の判断による**(2026-09-05:
「**残念ながら、運用管理側には、設定値の変更が伝えられない場合が多いので C でお願いします**」)。

**案 A・B はいずれも「運用側が上限値を教えてくれる」ことを前提にしており、
その前提が成り立たない。** これは技術的な優劣ではなく運用上の制約であり、
**コードからは決して読み取れない。** それがこの ADR を書く理由である。

**ただし実際の容量が取れる場合はそちらを優先する。** `-gc` 形式の jstat では
`ou_pct` / `eu_pct` / `mu_pct` が導出済みであり、その上限は 100 と分かる。
推定を使うのは、実測しかない系列に限る。

### 残存リスクと緩和

★ACCEPTED★ **推定上限は真の上限とは限らない。**
残存リスク: 実際には上限に達していないのに張り付きと判定する。

緩和として 2 段のガードを置く(P003 DS-08-C1-03)。

1. `count(DISTINCT value) >= 10` — 0/1 のフラグ系列は推定上限が 1 になり必ず成立するため
2. `max / quantile_cont(value, 0.05) >= 1.5` — 常時ほぼ一定の系列を弾くため

**2 で最小値ではなく 5 パーセンタイルを使う。** 一度でも 0 を取ると比が無限大になり、
ガードが素通りする。**実際に誤検知して直した経緯がある。**

さらに、レポートには「**推定上限**」と明記し、運用者が値の出どころを判断できるようにする。

### 影響範囲

* `app/src/s_anomaly/detectors/c1_saturation.py`
* `docs/P001-requirement.md` 10.2a / FR-055〜FR-058
* `docs/P003-backend-spec.md` 7.14

## ADR-017 — 検知の計算を系列単位の SQL 窓関数へは移さない

* 状態: 採用
* 決定日: 2026-09-05(CR-006)

### 背景

**この決定は、後任が必ず再検討する類のものである。** CR-006 の起票文にも
「DuckDB は 1 クエリの中で自動的に複数コアを使う。仕事を SQL 側へ渡すことが
並列度を上げる前提条件である」と書いてある。**実測を知らなければ同じ道を辿る。**

### 検討した選択肢と実測

**ALG-A1 を SQL(窓関数)へ移す実装を完成させ、出力が完全一致することを確認したうえで
差し戻した。** 30 日規模の全 18 ファイルが「実行日時」の 1 行を除いてバイト単位で一致し、
検知点 6,673 点も一致した。**正しさは問題ではない。速度である。**

| 方式 | 156 系列 × 8,640 点 |
| --- | --- |
| **系列ごとに SQL 窓関数(156 クエリ)** | RANGE **7.59s** / ROWS 5.31s |
| 純 Python の逐次走査 | **1.54s** |
| **全系列を 1 クエリ**(`PARTITION BY series_id, metric, segment`) | **0.88s** |

アプリ全体での実測でも ALG-A1 は **4.6 秒 → 8.9 秒**(1.9 倍遅く)になった。

### 決定と理由

**系列単位では SQL へ移さない。**

**1 系列 8,640 点という粒度では、DuckDB の 1 クエリあたりの固定費が窓計算そのものより
大きい。** 156 回に分けて呼ぶかぎり、窓関数がいくら速くても固定費に負ける。

**代わりに、同じ系列を検知器の数だけ読み直していた問題を直した。**
これが実際の支配要因であり(S6 の 52%)、**S6 は 48.0 秒から 24.5 秒になった。**

### 残存リスクと緩和

★ACCEPTED★ **「全系列を 1 クエリ」であれば SQL が最速である**(0.88s。純 Python の 1.75 倍)。
検討したが本CRでは採らなかった。理由は
(a) 検知器の実行方式を「系列ごと」から「全系列一括の前処理 + 系列ごとの判定」へ変える
    設計変更であり、**ADR-018(系列ごとのスレッド並列)と真正面から衝突する**、
(b) 全系列分の中間結果を保持するためメモリ要求が増え、**過去に S8 で OOM(終了コード 6)を
    起こした経緯がある**以上 90 日規模での実測なしには入れられない、
(c) 現状 90 日で 178 秒 / 目標 600 秒と余裕が大きい、の 3 点による。

**残存リスク**: 系列数が桁で増えた場合(sar の追加など)に再検討が要る。
`docs/P302-deliver.md` 10章へ申し送る。

### 影響範囲

* `app/src/s_anomaly/detectors/base.py`(`fetch_series` / `fetch_segments` / `seasonal_diffs`)
* `app/src/s_anomaly/detectors/a1_ma_sigma.py`(冒頭に理由を記録)
* `docs/P001-requirement.md` FR-059、`docs/P003-backend-spec.md` 7.1a / 7.1b

## ADR-018 — S6 は系列ごとにスレッド並列で実行し、各スレッドが `con.cursor()` を持つ

* 状態: 採用
* 決定日: 2026-09-05(CR-007)

### 背景

依頼者の明示の指示による(2026-09-05:「系列ごとにスレッドを起こして並列実行するの
変更を入れてください」)。背景は**監視対象ホストの増加と sar の追加**であり、
S6 は系列数に比例するため予防的に手を打つ。

### 決定

1. **S6 のループの向きを「検知器ごと」から「系列ごと」に変える。**
   系列がスレッドに割り当てる単位になる。
2. **各スレッドは `con.cursor()` で自分のカーソルを持つ。**
3. **スレッド数の上限は既定 `min(8, 論理コア数)`。** `common.detect_threads` で変更できる。

### なぜカーソルを配るのか — 共有接続に戻してはいけない

| 構成 | 156 系列 × 8,640 点の SQL 処理 | 速度比 |
| --- | --- | --- |
| 1 スレッド | 3.42s | 1.00x |
| 8 スレッド + **共有 `con`** | 2.51s | **1.36x** |
| 8 スレッド + **`con.cursor()`** | **0.60s** | **5.68x** |

**共有接続のままだと DuckDB 側で直列化され、並列化の効果がほとんど出ない。**
コードを読んでもこの差は分からず、**共有接続へ戻しても動いてしまう**(遅くなるだけ)。
それがこの ADR を書く理由である。

### なぜ 8 なのか

実測で 8 が頭打ちである(16 にしても 5.68x → 5.78x)。論理コアは 16 だが、
**DuckDB は 1 クエリの中でも複数コアを使う**ため、スレッドを増やしても
同じコアを取り合うだけになる。

### 実際の効果 — 想定の 5.68 倍には届かない

★ACCEPTED★ **本アプリでの実効は 1.13 倍である。**

| 構成(30 日規模 / S6 の壁時計) | 1 スレッド | 8 スレッド | 速度比 |
| --- | --- | --- | --- |
| SQL 実装の検知器のみ(A3 / A5 / B5 / C1) | 10.5s | 5.9s(4 スレッド) | **1.78x** |
| 全 11 検知器 | 26.3s | 23.2s | **1.13x** |

**11 検知器のうち 7 つが純 Python であり、GIL によりスレッドで速くならない。**
それらを SQL へ移す前提が ADR-017 で崩れたため、効果が限定された。

検討したのは (a) 全系列 1 クエリ方式(ADR-017 のとおり衝突する)、
(b) `multiprocessing`(DuckDB 接続をプロセス間で共有できず、Windows の `spawn` で
閉域環境の `vendor/` 経路が子プロセスにも要る。ワーカー数 × `max_memory` でメモリが跳ねる)。
**残存リスクは無い。** 遅くはならず、SQL 主体の検知器が増えるほど効きが増す。

### 再現性(NFR-009)

**対処が要ったのは `failures` の整列 1 箇所だけであった。** `detections` と `skips` は
もともと整列済みで、偶然ではなく意図的にそうしてあった(ADR-013 / ADR-015 の系譜)。

**確認**: 30 日規模で 1 スレッドと 8 スレッドの出力を突き合わせ、
全 18 ファイルが「実行日時」の行を除いて完全一致した。

### メモリ

**`con.cursor()` は接続を複製しない。** `max_memory` はデータベース単位の設定であり、
90 日規模・既定 4GB・8 スレッドで終了コード 0 を確認した。

### 影響範囲

* `app/src/s_anomaly/cli.py`(`detect` / `_detect_workers`)
* `app/src/s_anomaly/detectors/base.py`(スレッドローカルのキャッシュ)
* `docs/P003-backend-spec.md` DS-12-09 / DS-12-10

## ADR-019 — タイムゾーンは投入時に変換して格納し、`ts` は `TIMESTAMP` のまま保つ

* 状態: 採用
* 決定日: 2026-09-06(CR-008)

### 背景

入力ごとに採取時のタイムゾーンが違うと、**実際にはずれた時刻同士を突き合わせてしまう。**
本アプリはイベントの区間の重なりで「同時に発生したアノマリー」を判定する(ADR-015 の系譜)
ため、これは表示の問題ではなく**解析結果そのものの問題**である。

とくに sar(次バージョン)は `sadf` の既定出力が UTC であり、
**他のログがローカル時刻の環境では時差ぶんずれる。**

### 検討した選択肢

| 案 | 内容 | 判断 |
| --- | --- | --- |
| A | `ts` を **`TIMESTAMPTZ`** にして、瞬時を保持する | **不採用** |
| B | 素朴な時刻のまま格納し、**レポート生成時に変換**する | **不採用** |
| **C** | **投入時に格納タイムゾーンへ変換し、`ts` は `TIMESTAMP` のまま** | **採用** |

**案 A を採らない理由**: `TIMESTAMPTZ` の表示は **DuckDB のセッションタイムゾーンに
依存する。** 同じデータでも実行環境によってレポートが変わり、**NFR-009(再現性)を
壊す。** 本アプリは「同一入力・同一設定なら常に同一の出力」を要件にしている。

**案 B を採らない理由**: 変換が出力のたびに走る。また `events` の統合・
`co_anomaly` の重なり判定は**格納された値で行われる**ため、
**レポートだけ変換しても解析は元のずれたままになる。** 直す場所が違う。

**案 C の帰結**: 格納後の `ts` は「格納タイムゾーンにおける素朴な時刻」という
意味を持つ。**レポートはそれをそのまま出し、どのタイムゾーンかを併記するだけでよい。**

### 変換しない条件(2026-09-06 の依頼者の指示)

**読み込み元と格納先が同じなら、`AT TIME ZONE` を発行しない。**
`BatchInserter._build_select()` が `"*"` を返し、投入 SQL は本CR適用前と同一になる。

**既定はすべて `UTC` であるため、通常の構成では変換の SQL が一度も現れない。**
これは性能上の配慮であると同時に、**ICU(タイムゾーン DB)への依存を通常経路から
外す**という意味を持つ。

### 固定オフセットは使えない(実測)

| 書き方 | 結果 |
| --- | --- |
| `AT TIME ZONE 'Asia/Tokyo'` | **使える。** 拡張の自動読み込みを無効化(NFR-008)していても動く |
| `AT TIME ZONE '+09:00'` | **使えない。** `Unknown TimeZone '+09:00'` |
| `utc`(小文字) | **使えない。** 大文字小文字を区別する |

**したがって設定値は IANA の名前付きタイムゾーンに限り、`pg_timezone_names()` で
実在を検証する。** 検証は**接続を開いたあと**に行う(設定読み込みの時点では接続が無い)。

### 残存リスク

★ACCEPTED★ **夏時間(DST)の妥当性は検証しない。**
検討したのは DST 切り替え時刻の重複・欠落を検出して警告する案。
**採らなかった理由**: 想定システムはすべて UTC であり DST が存在しない。
**残存リスク**: DST のある地域を設定した場合、切り替え時刻付近の 1 時間で
時刻の重複または欠落が起きうる。その区間の検知結果は信用できない。

### 影響範囲

* `app/src/s_anomaly/config.py`(`[timezone]` と `validate_timezones`)
* `app/src/s_anomaly/loaders/__init__.py`(`BatchInserter._build_select`)
* `app/src/s_anomaly/reporter.py`(`format_ts` の併記)
* `docs/P001-requirement.md` 13.1(FR-120〜125)、`docs/P003-backend-spec.md` DS-12-11〜14

## ADR-020 — チャートは SVG を自前生成する。作図ライブラリを追加しない

* 状態: 採用
* 決定日: 2026-09-06(CR-009)

### 背景

**依頼者は「チャート作成ライブラリを追加してもよい」と明示した**(2026-09-06)。
そのうえで検討し、**自前生成を選んだ。** 後任は「なぜ matplotlib を使わないのか」を
必ず疑問に思うため、理由を残す。

### 決定的な事実 — `vendor/` 経路がまだ実証されていない

```
$ ls app/vendor/
(空)
```

`docs/P302-deliver.md` の **FR-002-実環境 は BLOCKED** である。理由は
「**配布先の Python 版が未確認のため、同梱すべき wheel を確定できない**」。
**DuckDB ですら同梱できていない。**

**C 拡張を持つライブラリを足すと、この未解決問題が 1 個から数個に増える。**

### 検討した選択肢

| 案 | 判断 | 理由 |
| --- | --- | --- |
| **自前生成の SVG** | **採用** | 下記 |
| 純 Python ライブラリ(pygal 等) | 不採用 | wheel は 1 つ(`py3-none-any`)で済むが、自前生成に対する利得が小さい |
| matplotlib | **不採用** | 下記 5 点 |

### matplotlib を採らなかった 5 つの理由

| # | 内容 |
| --- | --- |
| 1 | wheel が **OS × アーキ × Python マイナー版**ごとに要る(matplotlib + numpy + pillow ほかで 1 組み合わせ 35〜50MB)。**配布先の Python 版が未確定な現状では、何を同梱すべきか決められない** |
| 2 | **日本語が豆腐になる。** 既定フォントに CJK が無く、CJK フォントの同梱とライセンス確認が要る |
| 3 | **ホームディレクトリにフォントキャッシュを書く。** 「書き込み先はカレントディレクトリと `temp_directory` のみ」(README 2.1)を壊しかける |
| 4 | SVG に日付メタデータと可変の要素 ID を埋めるため、**そのままでは実行ごとにバイト列が変わる**(NFR-009) |
| 5 | **FR-003 の改訂と A008(import 許可リスト)の緩和**が要る。要件を緩める判断は人間のものである |

**2 は SVG の構造的な利点の裏返しである。** SVG の文字は**閲覧側のフォントで
描画される**ため、こちらでフォントを同梱しなくても日本語が出る。
ラスタライズする方式では、生成時にフォントが必要になる。

### 自前生成の代償

★ACCEPTED★ **描画コードを自分で保守することになる。**
目盛りの自動調整・対数軸・日付軸の書式などは、必要になった時点で手で足す。
**残存リスク**: 凝った図が要求されたときに実装コストがかかる。
**現状の要求(折れ線・軸・凡例・異常区間の網掛け)は約 300 行で満たせている。**

### 影響範囲

* `app/src/s_anomaly/charts.py`(新規)
* `docs/P001-requirement.md` 13.2(FR-130〜136)、`docs/P003-backend-spec.md` 11a章
* `app/tests/unit/test_charts.py`、`app/tests/acceptance/test_a013_charts.py`
