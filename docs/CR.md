状態は次のいずれかを取る。更新するフェーズもあわせて示す。

```text

```

優先度は次のいずれかを取る。

```text
高    次のRefactor実行で最優先に対応する
中    通常どおり対応する
低    他の対応に余裕があれば対応する
N/A   却下されたCRに用いる(Not Applicable)
```

* 状態を `却下` に更新するときは、**同時に優先度列も `N/A` に更新する**。

## 本回の起票にあたっての補足(2026-09-05)

**4 件は一体で適用することを前提としている。** いずれも「`report.md` が 4K トークンの
ローカル LLM で扱えない」という同一の課題に対するものであり、**単独では目的を達成しない。**

* **CR-001**(ホスト分割)単独では、1 ファイルあたりのサイズが下がりきらない。
* **CR-002**(相関の置き換え)単独では、ファイルが 1 つのままである。
* **CR-003**(イベント ID)は、CR-001 で分割したファイル間を CR-002 の「同時に発生したアノマリー」欄が
  相互参照するために必要になる。
* **CR-004**(集計サマリ)が、**4K の目標を実際に達成する部分**である。CR-001 と CR-002 を適用しても
  1 ファイルあたり約 31 万トークンが残るため、集計した形式の出力が別途要る。

### 実測にもとづく見込み(30 日規模)

| | 現状 | CR-001〜004 適用後の見込み |
| --- | --- | --- |
| ファイル数 | 1 | **18**(ホスト別 17 + サマリ 1) |
| 総サイズ | 14,393,965 バイト | **約 660 万バイト(-54%)** |
| ホスト別ファイルの平均 | — | 約 39 万バイト(約 31 万トークン) |
| S8 の所要(90 日規模) | 299 秒 | **ほぼ 0 秒** |
| **`report_summary_202606.md`** | — | **2,764 バイト ≒ 約 2,211 token(4K に収まる)** |
| **ホスト別ファイル先頭の集計表** | — | **244〜512 バイト ≒ 195〜409 token(全 17 件が 4K に収まる)** |

### 4K トークンの目標をどう達成するか

**1 イベントあたり約 728 バイト ≒ 582 トークン**であり、3,000 トークンに収まるのは約 5 件にすぎない。
**イベントを 1 件ずつ並べる形式である限り、分割の粒度を細かくしても 4K には入らない。**

そこで **CR-004 が、集計した形式の出力を追加する**。想定する使い方は次のとおりである。

1. LLM はまず `report_summary_{yyyymm}.md`(約 2,211 token)を読み、全体像と注目すべきホストを掴む
2. 次に `report_{HOST}_{yyyymm}.md` の**先頭の集計表**(195〜409 token)を読む
3. 個々のイベントの詳細が要るときだけ、人間または大きなコンテキストのモデルが本文を読む

## 第 3 回の起票と結果(2026-09-06)

**CR-008 — タイムゾーン。** sar 対応(次バージョン)の前提として先に整備した。
`sadf` の既定出力は UTC であり、他のログがローカル時刻の環境では、
**時差ぶんずれた突き合わせが無言で行われる**ためである。

| 決めたこと | 内容 |
| --- | --- |
| 設定 | `[timezone]` セクション。`storage` と、入力種別ごとに 1 つずつ |
| 変換の場所 | **S4(取り込み)で 1 回だけ。** レポート側では変換しない |
| **変換しない条件** | **読み込み元と `storage` が同じなら変換しない**(依頼者の指示) |
| 既定値 | **すべて `UTC`。** 想定システムがすべて UTC のため、通常は変換が発生しない |
| 表示 | レポートの全時刻に `(UTC)` のように併記する |
| 受け付ける値 | **IANA の名前付きタイムゾーンのみ。** 固定オフセットは DuckDB が解釈できない |

**試験の範囲は依頼者が明示的に狭めた**(2026-09-06)。
性能・エラー系は UTC のみ、非 UTC 構成は疎通確認のみとする(`A012`)。
