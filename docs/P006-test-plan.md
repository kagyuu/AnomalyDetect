## 3. テストデータのライフサイクル方針

`SKILL-P006-test-plan.md` が明記を求める 2 点を決める。

### 3.1 ベースラインへ復元する単位

**TP-03: 「テストスイートの実行ごと」とする**(SKILL の既定に従う)。

本アプリは永続化されたデータストアを持たないため、「累積して 2 回目だけ失敗する」典型的な問題は DB については起こらない。しかし**ファイルシステム上の 3 つの状態**が累積しうるため、それを復元の対象とする。

| 累積しうるもの | 場所 | 復元方法 |
| --- | --- | --- |
| 前回実行の `report_*.md` | テスト実行時のカレントディレクトリ | スイート開始時に削除 ※CR-001によりパターンを変更 |
| 前回実行の `report_*.md.tmp` | 同上 | スイート開始時に削除 |
| DuckDB の一時ファイル | `temp_directory`(既定 `./tmp`) | スイート開始時にディレクトリごと削除して作り直す |
| 生成済みのテストデータ | `tests/_work/` | スイート開始時に削除し、`gen_testdata.py` で作り直す |

**TP-04**: 個々のテストは、`tempfile.TemporaryDirectory` で自分専用の作業ディレクトリを作り、その中で `s_anomaly.py` を実行する。したがって**テスト間でカレントディレクトリを共有しない**。上記の復元は、スイート全体の入口と、テストが誤って共有領域を汚した場合の保険として行う。

★ACCEPTED★ 検討: 「テスト 1 件ごとに復元する」案。**採らない**(SKILL が既定としない理由と同じ)。ただし本アプリでは TP-04 のとおり各テストが独立した一時ディレクトリを使うため、実質的にはテスト 1 件ごとの分離が達成されている。スイート単位の復元は、`tests/_work/` に置く**共有の生成データ**(サイズが大きく毎テスト再生成すると遅い)にのみ効く。残存リスク: あるテストが `tests/_work/` の内容を書き換えると後続テストに影響する。これを防ぐため、**`tests/_work/` は読み取り専用として扱う規約**とし、書き込みが必要なテストは自分の一時ディレクトリへコピーしてから使う。

### 3.2 「ベースライン」が指すもの

**TP-05**: 本アプリのベースラインは次の状態を指す。

1. `tests/_work/normal/` に `gen_testdata.py` が生成した**正常系のテストデータ一式**(`logs/` と `expected.json`)が存在する
2. `tests/_work/broken/` に `gen_testdata.py --broken` が生成した**破損データ一式**が存在する
3. カレントディレクトリに `report_*.md` / `report_*.md.tmp` が存在しない ※CR-001
4. `temp_directory` が空である

**「単なる全行削除」ではなく、生成ツールを実行した直後の状態**を指す点が重要である。生成データを消しただけの状態から始めると、テストが入力を持たない。

**TP-06**: ベースラインの構築は `tests/conftest.py` 相当の**スイート初期化処理**(`unittest` では `tests/__init__.py` または専用のランナースクリプト)で行う。生成は決定的(P002 UI-08-02、シード固定)であるため、再構築しても同じデータが得られる。

### 3.3 テスト間のデータ依存

**TP-07**: テスト間のデータ依存を**許容しない**。各テストは TP-04 の一時ディレクトリと、TP-05 の読み取り専用ベースラインのみを入力とする。あるテストの実行結果を別のテストが入力にすることはしない。

**TP-08**: したがって本スイートは、**スイート単位でも個別実行でも同じ結果になる**。`SKILL.md` 共通指示が求めるのは前者(スイートを 2 回続けて実行して同じ結果)のみだが、本アプリの構成では後者も自然に満たされる。

## 4. テストの技術的な決め事

### 4.1 テストフレームワーク

**TP-09**: **標準ライブラリの `unittest` を使う。** pytest を使わない理由は P001 FR-003(外部パッケージは DuckDB のみ)。テスト実行は次のコマンドとする。

コードの格納先は `app/` である(`docs/P003-backend-spec.md` DS-01-00)。**リポジトリルートから、`-t app` を指定して実行する。**

```
# 全テスト
python -m unittest discover -s app/tests -t app -v

# 単体テストのみ
python -m unittest discover -s app/tests/unit -t app -v

# 結合テストのみ
python -m unittest discover -s app/tests/integration -t app -v

# 受け入れテストのみ
python -m unittest discover -s app/tests/acceptance -t app -v

# 単一のテストモジュール
python -m unittest discover -s app/tests/unit -t app -p "test_jstat_loader.py" -v

# 単一のテストクラス / メソッド(app/ をカレントにして実行する)
cd app && python -m unittest tests.unit.test_jstat_loader.TestGcutilFormat -v
cd app && python -m unittest tests.unit.test_jstat_loader.TestGcutilFormat.test_header_data_mismatch -v
```

**TP-09a**: テストから `app/src/s_anomaly` を import できるようにするため、**`app/tests/__init__.py` に `sys.path` へ `app/src` を追加する処理を置く**。`tests` パッケージが import された時点で必ず実行されるため、上記のどの実行形でも確実に効く。この処理は**テスト専用**であり、アプリ本体(`app/s_anomaly.py` → `app/src/`)は `app/tests/` に依存しない。

★FIXME★ **上記コマンドは、実際に実行して意図したテストが走ることを確認してから最終版とする**(`SKILL.md` 共通指示「実行して確認していないコマンドを、動作確認済みであるかのように記載しない」)。特に `-t app` の指定が無いと `tests` パッケージを import できず 0 件で静かに成功する事故が起きやすい。P102 の実装時に確認し、確認できた時点で本 ★FIXME★ を外す。

### 4.2 モック方針

**TP-10**: **外部 API を呼ばないアプリケーションであるため、外部 API のモックは不要である。** モックが必要になるのは次の 3 箇所に限る。

| 対象 | モックするか | 方法 |
| --- | --- | --- |
| DuckDB | **しない** | インメモリで即座に作れるため、本物を使う。モックすると SQL の正しさを検証できなくなる |
| ファイルシステム | **しない** | `tempfile` で本物の一時ディレクトリを使う。レポートの書き込みや権限エラーの再現は実ファイルで行う |
| 現在時刻 | **する** | レポートの「実行日時」欄。再現性の検証(N-08)で差分が出ないよう、テスト時は固定値を注入できるようにする |
| 書き込み失敗(終了コード 5) | **する** | 実際に権限を落とすのは OS 依存が大きいため、`reporter` の書き込み関数に例外を注入する。加えて受け入れテストでは**存在しないディレクトリをカレントにする**など OS 非依存の方法で 1 件だけ実地確認する |
| DuckDB のメモリ不足(終了コード 6) | **する** | 実際に 4GB を使い切るテストは現実的でないため、`duckdb.OutOfMemoryException` を注入して `StorageError` への変換を確認する。加えて `max_memory` を極端に小さく(例 `1KB`)して実地でも 1 件確認する |
| `vendor/` 不一致(終了コード 7) | **する** | 存在しないプラットフォームタグを注入する |

**TP-11**: 時刻の注入は、`reporter` が `now: datetime` を引数で受け取る形にする(グローバルなパッチを当てない)。P003 DS-12-01 の生成関数のシグネチャに反映する。

### 4.3 テストデータの準備方法

**TP-12**: 3 層に分ける。

| 層 | 置き場所 | 内容 | 用途 |
| --- | --- | --- | --- |
| **固定フィクスチャ** | `tests/fixtures/` | 手書きの極小ファイル(各形式 3〜10 行)。Git で管理する | 単体テスト。解析の正常系・異常系を 1 ケース 1 ファイルで表現する |
| **生成データ(正常)** | `tests/_work/normal/` | `gen_testdata.py` の出力。14 日 × 5 分間隔 | 結合・システムテスト。検知の正しさを `expected.json` と突き合わせる |
| **生成データ(破損)** | `tests/_work/broken/` | `gen_testdata.py --broken` の出力 | 結合テスト。FR-014 の読み飛ばしと集計 |
| **インライン系列** | テストコード内 | `metrics` テーブルへ直接 INSERT する数十点の人工系列 | アルゴリズムの単体テスト。理論値と突き合わせる |

**TP-13**: `tests/_work/` は Git 管理しない(生成物であるため)。スイート初期化処理が毎回生成する。生成は決定的であるため、再生成しても結果は変わらない。

**TP-14**: アルゴリズムの単体テスト(F-09)は、**理論値が計算できる系列**を使う。例:

| アルゴリズム | 人工系列 | 期待する結果 |
| --- | --- | --- |
| ALG-A1 | 平均 10・標準偏差 1 の一定系列の 50 番目だけ 20 | 50 番目のみを検知。σ 倍率が約 10 |
| ALG-A2 | 同上に、外れ値を 3 点連続で入れたもの | A1 がマスキングで見落とす一方、A2 は検知する(頑健性の実証) |
| ALG-A3 | 一様分布の系列に 1 点だけ大きな値 | Q3 + 1.5IQR を超える点のみ |
| ALG-A4 | 途中から平均が 0.5σ ずれる系列 | ずれ始めてから数点後に検知(A1 は検知しない) |
| ALG-A5 | 平日と週末で水準が異なる系列の、平日に週末相当の値を 1 点 | その 1 点のみ |
| ALG-B1 | 前半横ばい・後半右肩上がり | 後半のみ、`min_run` 以上の区間として |
| ALG-B2 | 傾き既知の直線 + 小ノイズ | Sen 勾配が理論値の ±10% 以内、p < 0.01 |
| ALG-B2 | 傾向のない乱数系列(固定シード) | p > 0.05(検知しない) |
| ALG-B3 | 鋸歯状で下限だけ上昇(メモリリーク模擬) | 全区間を 1 件として検知 |
| ALG-B3 | 鋸歯状で下限が一定 | 検知しない |
| ALG-B4 | ある点で水準が 3σ 上がる階段 | シフト点の近傍で検知 |
| ALG-B5 | 傾き既知の直線 | `slope × 86400` が理論値と一致、R² ≈ 1.0 |

★FIXME★ 上表の各系列の具体的なパラメータ(点数、ノイズの大きさ、許容誤差)は P007・P008 が確定する。ここでは「何を確認するか」までを定める。

### 4.4 検知の正しさの判定 (FR-113)

**TP-15**: 結合・システムテストでは、**レポート群を機械的に解析して** `expected.json` と突き合わせる(P002 UI-08-03)。**判定は全ファイルを合わせた集合に対して行う** ※CR-001。判定は 3 種。

| 判定 | 合格条件 | 不合格のときの意味 |
| --- | --- | --- |
| 検知漏れ | `injected` の全件について、`expect_algorithms` のいずれかを含むイベントが期間の重なりを持って存在する | アルゴリズムの感度不足、またはパラメータ既定値が不適切 |
| 誤検知 | `clean_series` に属する検知点が総点数の **1% 未満**、かつ **SEVERE が 0 件** ★FIXME★ (当初は「0 件」としていたが達成不能であることが P102 で判明したため改めた。`docs/ADR.md` ADR-012) | `effective_sigma` の下限設定が不十分、または残差ベースの正規化・持続性規則が効いていない |
| 脅威度 | 各 `injected` に対応するイベントの脅威度が `expect_min_severity` 以上 | 脅威度の判定規則(P003 DS-09-05)の不備 |

**TP-16**: レポートの解析は、P002 4.2 の項目書式に依存する。**レポート書式を変更した場合、この解析処理も同時に直す必要がある**ことを P008 の該当テストに明記する。

★ACCEPTED★ 検討: レポートを解析せず、内部の `Event` オブジェクトを直接検証する案。**不採用**。それでは「レポートに正しく出ているか」を確認できず、P001 の最終成果物(`report.md`)の品質を保証できないため。残存リスク: レポート書式の変更でテストが壊れやすい(TP-16 で明示した)。

### 4.5 カバレッジ

**TP-17**: カバレッジ計測ツール(`coverage.py`)は**外部パッケージであるため使わない**。代わりに、次を機械的に確認できる形で担保する。

## 6. スイートの再実行可能性

**TP-19**: `SKILL.md` 共通指示に従い、**テストスイート全体を 2 回続けて実行して同じ結果になること**を確認する。確認は実際に 2 回実行して行う(記述による主張で代替しない)。

本アプリで 2 回目が失敗しうる要因と、その対処は次のとおり。

| 要因 | 対処 |
| --- | --- |
| 前回の `report_*.md` が残る | TP-04(各テストが専用の一時ディレクトリを使う)+ TP-03(スイート開始時に削除)。**※CR-001により、前回はイベントがあったホストが今回 0 件だと前回のファイルが残る**(P002 UI-04-05)。テストは専用の一時ディレクトリを使うため影響を受けないが、**A-04 はこの点を確認する** |
| `tests/_work/` の生成データが前回のまま残り、生成ロジックの変更が反映されない | スイート開始時に削除して再生成する(TP-06) |
| `temp_directory` の残骸 | スイート開始時に削除(TP-03) |
| 生成データに現在時刻が混ざり、日付が変わると期待値がずれる | **生成する期間を固定日付(2026-06-01〜2026-06-14)にする**(P002 8.3 `expected.json` の `period`)。実行日に依存させない |

**TP-20**: この確認は、テストを新規作成または変更したフェーズ(P103・P201・P203・P205)が行う。

## 7. 合格条件

| レベル | 合格条件 |
| --- | --- |
| 単体テスト | **全件合格**。スプリント内で合格させてから次スプリントへ進む(`SKILL.md` Executor の規定) |
| 結合テスト | P103 では失敗があってもよい(記録のみ)。P201 の時点で全件合格 |
| システム・受け入れテスト | P201 の時点で全件合格 |
| 検知の正しさ(TP-15) | 検知漏れ 0 件、誤検知 0 件、脅威度の下限を全件満たす |

★FIXME★ 誤検知の基準は `expected.json` の `clean_series` に対してのみ適用し、**埋め込んだ異常の周辺で追加のイベントが出ることは誤検知としない**(統計手法である以上、境界付近で複数の区間が検知されるのは正常な振る舞いであるため)。

**基準の改訂(P102 の実測による)**: 当初は「誤検知 0 件」としていたが、**4,000 点の系列に 2σ の判定を当てると正規分布のノイズだけで約 180 点が閾値を超える**ため、統計的手法である以上「0 件」は原理的に達成できない。基準を **「検知点が総点数の 1% 未満、かつ SEVERE が 0 件」** へ改めた。改訂の経緯・実測値・代替案の検討は `docs/ADR.md` ADR-012 を参照。**この基準の妥当性は実データでの確認が必要であり、P302 で CR の起票候補として人間に引き渡す。**
