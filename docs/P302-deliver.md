## 0. 2026-09-06 第 4 次改訂の要旨(CR-009)

**アノマリーの状況を SVG の折れ線チャートにした。**

| 段 | 内容 |
| --- | --- |
| 上 | そのイベントの系列を**実単位**で描き、異常区間を網掛けする |
| 下 | **同時に発生したアノマリー**を重ねる。各系列を 0〜100% に正規化する |

`charts/{イベントID}.svg` に出力し、ホスト別レポートから**相対パスの画像リンク**で参照する。

### 作図ライブラリは追加していない(ADR-020)

**依頼者は「追加してもよい」と明示したが、検討のうえ自前生成を選んだ。**
決定的だったのは **`app/vendor/` が空であり、同梱経路そのものが未実証**
(FR-002-実環境 = BLOCKED)であることである。**DuckDB ですら同梱できていない。**
C 拡張を持つ依存を足すと、この未解決問題が 1 個から数個に増える。

**SVG なら日本語が閲覧側のフォントで描画される**ため、CJK フォントの同梱も要らない。

### 達成した結果

| 項目 | 0.4.0 | **0.5.0** |
| --- | --- | --- |
| チャート | **無し** | **SVG。単一 + 重ね合わせの 2 段** |
| 30 日規模の出力 | レポート 18 ファイル | + **チャート 2,430 枚 / 17.8MB** |
| 通常 30 日の実行時間 | 53.1s | **95.3s(+80%)** |
| 大規模 90 日の実行時間 | 162.8s | **302.4s(+86%)** |
| テスト | 単体 451 / 結合 115 / 受け入れ 143 | **単体 495 / 結合 115 / 受け入れ 159** |

**チャートの生成が所要時間を大きく押し上げている。** `[chart]` の上限
(既定 ホストあたり 100 + 100)で調整できる。**NFR-002(600 秒)には
収まっている**(90 日で 302 秒 / 余裕 50%)が、**上限を上げるほど余裕が減る。**

**チャートが無いイベントには `[NO CHART]` の画像を出す**(2026-09-06 の指示)。
図が無いと「ツールの不備」と誤解されるためである。
**画像は 1 つだけ作り、全イベントが同じものを参照する。**

**4K トークンの目標(CR-004)は維持している。** チャートはサマリに入らず、
ホスト別レポートに入るのも 1 行のリンクだけである。

### 実装中に見つけた重要な欠陥

**重ね合わせが構造的に一度も描かれない状態になっていた。**
`SEVERE` は定義上「観点2 の検知」であり、観点2 には同時アノマリーが付かない
(CR-002)。**依頼者の要求の半分が、エラーなしに消えていた。**
選別の枠を 2 つに分けて是正し、回帰試験を置いた。
**CR-002 の「原因候補ルールが無言で発火しなくなった」と同じ型の欠陥である。**

## 0a. 2026-09-06 第 3 次改訂の要旨(CR-008)

**タイムゾーンを扱えるようにした。** **sar 対応(次バージョン)の前提**である。
`sadf` の既定出力は UTC であり、他のログがローカル時刻の環境では
**時差ぶんずれた突き合わせが無言で行われる。**

| 決めたこと | 内容 |
| --- | --- |
| 設定 | `[timezone]` セクション。`storage` と、入力種別ごとに 1 つずつ |
| 変換の場所 | **S4(取り込み)で 1 回だけ。** レポート側では変換しない |
| **変換しない条件** | **読み込み元と `storage` が同じなら変換しない**(依頼者の指示) |
| 既定値 | **すべて `UTC`。** 想定システムがすべて UTC のため、通常は変換が発生しない |
| 表示 | レポートの全時刻に `(UTC)` のように併記する |
| 受け付ける値 | **IANA の名前付きタイムゾーンのみ**(固定オフセットは DuckDB が解釈できない) |

### 達成した結果

| 項目 | 0.3.0 | **0.4.0** |
| --- | --- | --- |
| タイムゾーン | **概念が無い** | **入力種別ごとに設定でき、投入時に変換する** |
| レポートの時刻 | `2026-06-01 00:00:00` | **`2026-06-01 00:00:00 (UTC)`** |
| 通常 30 日の実行時間 | 55.1s | **53.1s**(変換が発生しないため影響なし) |
| 大規模 90 日の実行時間 | 173.6s | **162.8s** |
| テスト | 単体 426 / 結合 113 / 受け入れ 131 | **単体 451 / 結合 115 / 受け入れ 143**(全件 PASS) |

**`ts` の型は `TIMESTAMP` のまま変えていない**(`docs/ADR.md` **ADR-019**)。
`TIMESTAMPTZ` にすると表示が DuckDB のセッションタイムゾーンに依存し、
**同じデータでも実行環境によってレポートが変わって NFR-009(再現性)を壊す**ためである。

### 試験の範囲は依頼者が明示的に狭めた

**性能・エラー系は入力 UTC / レポート UTC のみ。非 UTC 構成は疎通確認のみ**
(2026-09-06 の指示。`docs/P009-acceptance-direction/A012-timezone.md`)。
根拠は、想定システムがすべて UTC であり、非 UTC 構成は「設定できる」ことに意味が
あるのであって、その構成で運用されるわけではないためである。

## 3. アプリケーション種別と配布方針

### 3.1 種別の判定: **CLI コマンド**

根拠:

* エントリポイントは `app/s_anomaly.py` であり、コマンドラインから引数(解析対象ディレクトリ)を 1 つ受け取り、**`report.md` というファイルを生成して終了する**(`docs/P002-frontend-spec.md` UI-01)。
* 常駐しない。ポートを開かない。**HTTP サーバも画面も持たない**(P002 冒頭が「本アプリは CLI アプリであり、画面を持たない」と明記)。
* DB・キューなどの依存ミドルウェアを持たない。DuckDB は**インプロセスの組み込みライブラリ**であり、別サービスとして起動するものではない。

### 3.2 Docker Compose を作らない理由

**サービス提供型システムではないため、`SKILL-P302-deliver.md` がいう「Docker Compose から起動できる資産一式」は該当しない。**

さらに、コンテナ化は本アプリの要求と積極的に矛盾する。

| 要求 | 内容 | コンテナ化との関係 |
| --- | --- | --- |
| NFR-011 | 配布資産をコピーするだけで動作すること。**インストーラを要求しない** | Docker の導入自体がインストーラの要求にあたる |
| FR-002 | 閉域環境へ `vendor/` 同梱で配布する | 閉域環境では Docker イメージの取得経路も無い |
| NFR-008 | ネットワーク通信を一切行わない | イメージの pull が通信を伴う |

**したがって Docker 関連資産は作成しない。** これは未整備ではなく、要求にもとづく判断である。

### 3.3 実行前チェックの結果

`SKILL-P302-deliver.md`「実行前チェック」の 8 項目。

#### #2 NFR-002 の目標時間(1,000 万レコードで 10 分)が実態と合っていない

#### #3 入力の文字コードが UTF-8 想定である(NFR-007)

* **状況**: 入力ファイルを UTF-8(BOM 付きも可)と想定している。★FIXME★ が「日本語のホスト名・データソース名が含まれるなら Shift_JIS の可能性がある」と指摘している。

* **CR 起票候補**: **○**(入力仕様の確定)

#### #4 NFR-009(再現性)を規模を上げて検証できていない ★訂正 2026-09-05★

* **従来の状況**: 同一入力・同一設定で 2 回実行しても `report.md` が一致しなかった(30 日規模で 34 行差)。

* **CR-002 による変化**: **相関の算出そのものを廃止したため、この原因は取り除かれた。**

* **それでも `要対応` に残す理由**: **解消を検証できていない。**
  A003(再現性)は 14 日分のベースラインでしか確認しておらず、その規模では現象が現れない。
  **「直ったはず」であって「直ったことを確認した」ではない。**
* **確認してほしいこと**: A003 を規模を上げて実行するか(30 日規模で 2 回実行して一致を見る)、

* **CR 起票候補**: **○**(テストの強化)

#### #5 4K トークンの判定をバイト数で代用している ※CR-004 により追加

* **状況**: 「4K トークンに収まること」の判定を、**UTF-8 で 4,000 バイト以下**という基準で代用している。
* **理由**: トークナイザが配布資産に含まれない。FR-003 により外部依存は DuckDB のみであり、

* **CR 起票候補**: **○**(基準の確定)

#### #6 原因候補の判定条件が変わった ※CR-002 により追加

* **状況**: 原因候補 9 ルールのうち 5 件(CR-01 / CR-02 / CR-04 / CR-06 / CR-07)の判定条件を、

  1. 原因候補ルール専用の入力 `concurrent_by_metric` を設けた(同一ホストで区間が重なるイベント。

  2. 否定条件(「変化なし」)の判定を**持続的な上昇(`trend_up` / `floor_rise`)が無いこと**に限定した

* **確認してほしいこと**: 実データで、原因候補が妥当に出ているかを確認していただきたい。

#### #8 ALG-C1 の「推定上限」が実運用で妥当かどうか(※CR-005)

* **状況**: 入力にコネクションプールの上限値が無いため、**解析期間中の実測最大値を上限と推定している**(`docs/ADR.md` ADR-016)。依頼者の判断による選択であり、「運用管理側には設定値の変更が伝えられない場合が多い」という事情にもとづく。
* **確認してほしいこと**: **推定した上限が、実際の設定値とどれだけ離れているか。** 期間中ずっと上限の半分までしか使われていない系列では、その半分が「上限」と推定され、**張り付きと誤判定される**。実データで 1 系列でも突き合わせられれば、`ALG-C1.min_spread`(既定 1.5)の調整指針が得られる。
* **あわせて**: 使用率(`ou_pct` / `eu_pct` / `mu_pct`)が導出できる系列では実際の上限 100% を使っており、推定は使っていない。**問題になるのは `active_connections` と `pend` である。**
* **CR 起票候補**: **○**(実データでの検証後、上限の与え方を見直す可能性がある)

#### sar(sysstat)の分析対象への追加

**依頼者より「次バージョンで実施する」と明示されている**(2026-09-05)。本版の範囲外である。
**本版で決まっているのは入力形式と前処理の方法だけ**であり、実装は一切無い
(`discovery` / ローダ / テーブル定義のいずれにも sar は存在しない)。

##### 決まっていること

| 項目 | 内容 |
| --- | --- |
| 入力ファイル名 | **`sa-{ホスト名}-{yyyymmdd}.csv`** |
| 前処理 | **人が採取ホスト上で `sadf -d -t` を実行して CSV 化する**(`README.md` 1.5) |
| 前処理をアプリでやらない理由 | 本アプリは外部プロセスを起動しない(NFR-008 / A008)。また `sa` のバイナリ形式は sysstat の版に依存し、版が違うと本家の `sar` でさえ読めない |

##### ★ACCEPTED★ ホスト名の正規化はアプリ側で行わない(2026-09-06 / 依頼者の判断)

**`uname -n` が他のログのホスト名と食い違う場合、揃えるのは前処理の責任とする。**
変換スクリプトは**ホスト名を引数で指定できる**ようにしてあり、指定が無ければ
sa ファイルの記録(FQDN なら最初のドットまで)を使う。

* **検討したこと**: `events.extract_host` に正規化(FQDN を短縮する、別名表を持つ等)を
  入れて、アプリ側で吸収する案。
* **採らなかった理由**: **依頼者の明示の判断**(2026-09-06「アプリ側で吸収する必要はありません」)。
  前処理で正しい名前を渡せる以上、アプリに名前の対応表という運用知識を持ち込む必要がない。
* **残存リスク**: **変換時にホスト名を指定し忘れると、静かに別ホストとして扱われる。**
  レポートがホストごとに割れ、「同時に発生したアノマリー」の同一ホスト優先も効かなくなる。
  **エラーにはならないため気付きにくい。** 運用手順書で担保すること。

##### まだ決まっていないこと(実装時に判断が要る)

| # | 論点 |
| --- | --- |
| 1 | **タイムゾーン。** `sadf` の既定は UTC である。変換スクリプトは `-t`(採取ホストのローカル時刻)を付けて他のログに揃えているが、**アプリ側で時刻の整合を検証するかは未決**。ずれると区間の重なり判定が全て外れる |

* したがって `0.1.0` → **`0.2.0`** とした。`1.0.0` への移行は人間の明示の指示があった場合にのみ行う。
