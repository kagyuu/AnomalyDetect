## 5. P202 で行った原因調査(P203 への引き継ぎ)

### 5.1 規模別の実測(S6 のアルゴリズム別内訳)

### 5.2 ALG-B4 が遅い理由

`app/src/s_anomaly/detectors/b4_cusum.py` の `_mean_after` / `_mean_before` が、
**検知 1 件ごとに系列全体を走査している。**

```python
def _mean_after(points, index, window_sec):
    start_ts = points[index][0]
    values = [v for ts, v in points[index:]                      # <- index から末尾まで全走査
              if (ts - start_ts).total_seconds() <= window_sec]  #    そのうち窓内だけを残す
```

`_mean_before` も同様に `points[:index + 1]`(先頭から index まで)を全走査する。
窓幅は `baseline_minutes = 1440`(5 分間隔で 288 点)であるのに対し、
91 日の系列は 26,208 点ある。**必要な 288 点を得るために毎回 26,000 点を走査している。**

計算量は **O(検知件数 × 系列長)** である。524K レコードでは検知が 22,033 点あり、
系列・メトリクスの組は 154 なので、1 組あたり約 143 件 × 26,208 点 × 2 関数となる。

### 5.3 切り分けの裏付け(分離ベンチマーク)

実測値(系列長 26,208 点 / 1 組あたり検知 143 件 / 窓 1440 分)で、
現行実装と `bisect` で窓の範囲だけを走査する案を比較した。

| 実装 | 1 組あたり | 154 組に換算 |
| --- | --- | --- |
| 現行(全走査) | 0.734 秒 | **113.1 秒** |
| `bisect` で窓の範囲のみ | 0.000 秒 | **0.0 秒** |

**両者の戻り値が完全に一致することも確認した。**
換算値 113.1 秒は、実測の ALG-B4 132.8 秒とよく一致する。
**ALG-B4 の所要時間の約 85% がこの 2 関数の全走査で説明できる。**

### 5.4 F001 だけでは NFR-002 に届かない見込み

★訂正 2026-09-03 / P203★ **本節の当初の見積もり(約 44 分)は誤っていた。**
524K レコードからの単純な線形外挿だったが、**規模を伸ばすと支配要因が入れ替わる**ため
線形にはならない。P203 で測り直した結果を以下に示す。

| 規模 | 系列長 | ファイル | S4 取り込み | S6 検知 | S7〜S9 | 全体 |

| 91 日 / 20 系列(52 万行) | 26,208 点 | 364 | — | 176s | — | 249.3s |
| **365 日 / 30 系列(116 万行)** | **105,120 点** | **1,460** | **391s (55%)** | **241s (34%)** | **79s (11%)** | **712s** |
