# CR-006 — 純 Python 実装の検知器を SQL(DuckDB の窓関数)へ移す

## 起票日

2026-09-05

## 起票者

本アプリの依頼者(会話による指示。2026-09-05)

## 背景・課題

**現状**: S6(検知)は**実効並列度 1.51**で動いており、16 論理コア / 12 物理コアの
マシンでほぼ 1 コア分しか使えていない。

**実測(30 日分 / テーブル 950,400 行 / 論理コア 16)**

| ステップ | 壁時計 | 実効並列度 |
| --- | --- | --- |
| S4 取り込み | 26s | 0.79 |
| **S6 検知** | **48s(全体の 63%)** | **1.51** |
| その他 | 各 1 秒未満 | — |
| **全体** | **76.7s** | **1.29** |

**原因**: **10 アルゴリズム中 7 個が純 Python 実装**であり、DuckDB に仕事が渡っていない。

| 実装 | アルゴリズム | 30 日での所要 |
| --- | --- | --- |
| **純 Python** | ALG-A1(3.7s)/ A2(5.2s)/ A4(5.0s)/ B1(5.5s)/ B2(6.0s)/ B3(2.4s)/ B4(4.9s) | **合計 32.7s** |
| SQL | ALG-A3(2.6s)/ A5(4.7s)/ B5(2.4s) | 合計 9.7s |

**スレッドでは解決しない。** CPython 3.14.2(GIL 有効)で純 Python の重い処理を
4 スレッドに分けて測ったところ、**実効並列度 0.84**(むしろ遅い)であった。

**これから起きること**: 依頼者より、**監視対象ホストが増える可能性**と、
**sar(sysstat)を分析対象に加える予定**が示された。S6 は系列数に比例するため、
現在 110 系列で 129 秒(90 日)= 1 系列あたり約 1.2 秒である。
**500 系列になれば S6 だけで約 590 秒**となり、NFR-002 の目標 600 秒を超える。

## 変更要求の内容

**純 Python で実装されている検知器を、DuckDB の窓関数を使う SQL 実装へ移す。**

* **DuckDB は 1 クエリの中で自動的に複数コアを使う。** 仕事を SQL 側へ渡せば、
  アプリ側にスレッドを持ち込まなくても並列化される。
* **既に ALG-A3 / A5 / B5 が SQL 実装であり、前例がある。**
* 対応する既存の仕様箇所:
  * `docs/P003-backend-spec.md` **7章**(各アルゴリズムの内部仕様。DS-08-A1 〜 DS-08-B5)
  * `docs/P001-requirement.md` **10章**(アルゴリズムの定義)

### 移行の優先順位

**所要時間の大きい順に、SQL で素直に書けるものから移す。**

| 優先 | アルゴリズム | SQL 化の見通し |
| --- | --- | --- |
| 1 | **ALG-A1** 移動平均 ± kσ | **容易。** `avg() OVER (ROWS BETWEEN n PRECEDING AND 1 PRECEDING)` と `stddev_samp() OVER (...)` で書ける |
| 2 | **ALG-A4** EWMA 管理図 | **要検討。** 指数加重移動平均は再帰的であり、窓関数では素直に書けない。近似で置き換えるか、Python のまま残すかの判断が要る |
| 3 | **ALG-B3** ローリング最小値 | **容易。** `min() OVER (...)` と連続増加回数の判定 |
| 4 | **ALG-B1** 短期/長期移動平均のクロス | **容易。** 2 つの `avg() OVER` の比較と連続回数 |
| 5 | **ALG-B4** CUSUM | **困難。** 累積和は前の値に依存する再帰であり、窓関数で書けない。**移さない判断もありうる** |
| 6 | **ALG-B2** Mann-Kendall | **困難。** 全ペアの符号和は O(n²) であり SQL 化すると重くなる恐れがある |
| 7 | **ALG-A2** Hampel(移動中央値 + MAD) | **要検討。** `median() OVER` は DuckDB にあるが MAD は 2 段階の中央値が要る |

**全部を移す必要はない。** 費用対効果で判断し、**移さないものはその理由を記録する。**

## 期待する振る舞い

* **検知結果が SQL 化の前後で変わらない。** 各アルゴリズムについて、移行前後で
  同一入力に対する検知点(系列・メトリクス・時刻・スコア)が一致すること。
* SQL 化したアルゴリズムの所要時間が短くなる。
* **S6 全体の実効並列度が 1.51 より上がる。**
* 検知結果の順序が決定的である(NFR-009)。
* 1 つのアルゴリズムが失敗しても他は続行する(FR-032)。既存の振る舞いを保つこと。
* 移さなかったアルゴリズムについて、**移さない理由が設計書に記録されている。**

## 影響が想定される範囲

* 画面: 該当なし
* API: 該当なし
* データモデル: 変更なし
* モジュール: `app/src/s_anomaly/detectors/` の該当ファイル、`detectors/base.py`(共通の取得処理)
* テスト: **各アルゴリズムの単体テスト**(`test_detectors_a.py` / `test_detectors_b.py`)。
  **期待値は変えない。** 検知結果が変わらないことが本 CR の要件である
* 関連ADR: **ADR-013**(時刻窓の集計は二分探索で範囲を絞る)は **ALG-B4 に対する決定**である。
  B4 を SQL 化しない判断なら影響なし。**SQL 化する場合は ADR-013 の見直しが要る**

## 優先度の判断理由

**影響度: 高 / 緊急度: 中 → 優先度: 中**

* 影響度: 全アルゴリズムの実装方式に関わる。
* 緊急度: **現時点では性能に問題がない**(90 日で 231 秒 / 目標 600 秒)。
  ただし**系列数が増えると問題になる**ことが予測されている。**予防的な対応である。**

## 備考

**CR-007(系列ごとのスレッド並列)と対で効果を発揮する。**

実測(156 系列 × 8,640 点の SQL 処理):

| 構成 | 所要 | 速度比 |
| --- | --- | --- |
| 1 スレッド | 3.42s | 1.00x |
| 4 スレッド + `con.cursor()` | 1.13s | 3.03x |
| **8 スレッド + `con.cursor()`** | **0.60s** | **5.68x** |
| 16 スレッド + `con.cursor()` | 0.59s | 5.78x(頭打ち) |
| 8 スレッド + **共有 `con`** | 2.51s | 1.36x |

**SQL 化しただけでも DuckDB の内部並列で速くなるが、CR-007 と組み合わせると 5.68 倍になる。**
逆に、**CR-006 なしに CR-007 だけを入れても GIL により効果がない。**
