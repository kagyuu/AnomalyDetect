# CR-005 — 上限値を実測から推定し、「上限への張り付き」を検知する

## 起票日

2026-09-05

## 起票者

本アプリの依頼者(会話による指示。2026-09-05)

## 背景・課題

**依頼者が知りたいこと**: 「**DBConnection や Java のメモリが、上限値に張りついている**」こと。

**現状**: 「上限に接近しているか」の判定(SEVERE)は、データ源によって**質が大きく異なる**。

| データ源 | メトリクス | 上限の判定方法 | 妥当性 |
| --- | --- | --- | --- |
| `jvm_gc` | `ou` / `eu` / `mu` | **容量列から `ou_pct` 等を導出し、使用率 > `severe_pct`(既定 90%)** | **真の上限比較。妥当** |
| `db_connection` | `active_connections` | **末尾 10% の最大値 > それ以前の最大値**(`TAIL_MAX_METRICS`) | **上限比較ではない。「過去最大を更新中」の近似** |
| `lsf_queue` | `pend` / `susp` | 同上 | 同上 |

**困りごと**: **「上限に張り付いている」という、依頼者が最も知りたい状態が最も検知しづらい。**

| 状況 | 現状の検知 |
| --- | --- |
| コネクションが増え続けている | ○(末尾で最大値を更新するため) |
| **上限 100 に達し、期間の後半ずっと 100 で頭打ち** | **✕** 末尾最大 = 以前の最大 = 100 となり `tail > earlier` が偽になる |
| **解析期間の最初から上限に張り付いている** | **✕** 平坦なため観点2 の形状すら出ず、SEVERE 判定に到達しない |

**根本原因**: `DBConnection_{yyyymmdd}.csv` に**コネクションプールの上限値(maxCapacity)が含まれていない**
(`docs/P001-requirement.md` 4.1。列は `日付,ホスト名,ポート番号,データソース,activeConnectionsCurrentCount` の 5 列のみ)。
したがって `active_connections_pct` に相当するメトリクスを作れない。

**あわせて**: 現在の 10 アルゴリズムは、いずれも「**変化**」を捉えるものである
(外れ値・傾向・水準シフト)。「**変化しないまま高い値で止まっている**」という状態を
直接見るアルゴリズムが**無い**。

## 変更要求の内容

**上限値を実測から推定し、「上限への張り付き」を検知する。**

依頼者の指示: **「運用管理側には、設定値の変更が伝えられない場合が多いので C(実測値から推定)でお願いします」**
(入力に列を追加する案 A、設定で与える案 B は不採用)。

### (1) 上限値の推定

* **系列 × メトリクスごとに、解析期間中の最大値を「上限」とみなす。**
* 対象は**上限の概念があるメトリクス**に限る。`fgc_delta` のような累積回数には上限が無い。

### (2) 「張り付き」の検知

* 値が推定上限の一定割合(既定 `severe_pct` = 90%)以上である状態が、**一定時間継続していること**を検知する。
* **これは既存の 10 アルゴリズムとは別の観点である。** 変化ではなく状態を見る。

### (3) 誤検知への対処

**案 C には原理的な弱点がある。** 一度も真の上限に達していない系列でも、
「期間中の最大値」を上限とみなすため、その 90% 付近にいるだけで検知されうる。
例: 常時 0〜10 で推移する系列の最大が 10 のとき、9〜10 が続けば「張り付き」になる。

**この弱点を緩和する条件を設けること。** 具体案は詳細設計で決めるが、少なくとも次を検討する。

* 上限に張り付いている**時間の長さ**の下限(短時間の接近は除く)
* 値の**ばらつきの小ささ**(頭打ちなら分散が小さくなる)
* 系列の**変動幅**が小さすぎる場合は対象外にする(上記の 0〜10 のような例を除く)

### (4) 対応する既存の仕様箇所

* `docs/P001-requirement.md` **11章**(脅威度の判定。SEVERE の条件)、**10章**(アルゴリズム一覧)
* `docs/P003-backend-spec.md` **DS-09-05**(SEVERE の実装)、**7章**(検知器の内部仕様)
* `app/src/s_anomaly/events.py`(`TAIL_MAX_METRICS` / `_is_severe`)

## 期待する振る舞い

* 系列 × メトリクスごとに、解析期間中の最大値から上限が推定される。
* **値が推定上限の 90% 以上で一定時間継続している系列が検知される。**
* **上限に達したあと平坦なまま(増加していない)系列も検知される。** これが現状の主な取りこぼしである。
* **解析期間の最初から上限に張り付いている系列も検知される。**
* 変動幅が小さすぎる系列(誤検知の温床)は対象から除外され、その旨が分かる。
* 上限の概念が無いメトリクス(`fgc_delta` / `fgct_delta` / `ygct_delta` / `njobs` / `run`)は対象外である。
* **推定した上限値がレポートに出る。** 利用者が「その上限は妥当か」を判断できること。
* **JVM メモリで容量列がある場合(`-gc` 形式)は、推定上限ではなく実際の容量を使う。** 推定は容量が得られない場合の代替である。
* 検知結果は既存のイベントと同じ書式でレポートに出る。
* 同一入力に対して同一の結果になる(NFR-009)。

## 影響が想定される範囲

* 画面: 該当なし
* API: 該当なし
* データモデル: **上限の推定値を保持する必要がある。** `metrics` への列追加か、検知時の算出かは詳細設計で決める
* モジュール: `app/src/s_anomaly/detectors/`(**新規アルゴリズムの追加**)、`app/src/s_anomaly/events.py`(SEVERE 判定)、`app/src/s_anomaly/metrics.py`(上限の導出)、`app/src/s_anomaly/reporter.py`(推定上限の表示)
* 設定: **新しいアルゴリズム ID が増える**ため `[algorithms]` に 1 行増える。パラメータも増える
* テスト: **単体テストの新設**(新アルゴリズム)、`test_events.py`(SEVERE 判定)、`test_gen_testdata.py`(**張り付きの異常を生成データに埋め込む必要がある**)、A001(正解突き合わせ)、`expected.json`
* **関連ADR**: 抵触するものは無い。**新規 ADR の候補**である(「上限が入力に無い場合、実測の最大値を上限として推定する」という判断)

**★重要★ `app/tests/_work/normal/expected.json` に「張り付き」の異常が埋め込まれていない。**
新しい検知観点を追加するなら、**それを検証するテストデータが要る**。
`gen_testdata.py` に「上限に張り付く系列」を追加し、`expected.json` に正解として記載する必要がある。

## 優先度の判断理由

**影響度: 高 / 緊急度: 高 → 優先度: 高**

* 影響度: **依頼者が最も知りたい状態**であり、検知の目的そのものに関わる。
* 緊急度: 現状は**回避策なしに取りこぼしている**。

## 備考

★FIXME★ **推定上限は「真の上限」ではない。** 期間中に一度も上限に達していない系列では、
推定値は実際の上限より小さくなり、「張り付き」と判定されても実際には余裕がある可能性がある。
**レポートに推定上限を明記し、利用者が判断できるようにすること**が最低限の担保である。
将来的に入力へ `maxCapacity` 列を追加できるなら、そちらが本筋である(案 A)。

★FIXME★ **sar(sysstat)を分析対象に加える場合、同じ論点が再燃する。**
CPU 使用率は 0〜100% で上限が自明だが、メモリ・ディスクは容量情報が要る。
本 CR の設計は、その拡張を見据えたものにすることが望ましい。
