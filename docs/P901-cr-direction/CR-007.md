# CR-007 — S6(検知)を系列ごとにスレッドで並列実行する

## 起票日

2026-09-05

## 起票者

本アプリの依頼者(会話による指示。2026-09-05)

## 背景・課題

**現状**: S6 は二重の逐次ループである(`app/src/s_anomaly/cli.py::detect`)。

```python
for detector in active:            # 10 アルゴリズム
    for index, meta in enumerate(series):   # 156 系列
        detections, skips = detector.run(con, cfg, meta, progress)
```

**アプリのソース全体に `Thread` / `Pool` / `multiprocessing` / `asyncio` の使用は 0 箇所である。**

**実測(30 日分 / 論理コア 16)**: S6 は壁時計 48 秒・実効並列度 1.51。全体では 1.29。
**16 コアのうち実質 1.3 個分(約 8%)しか使えていない。**

**これから起きること**: **監視対象ホストの増加**と **sar(sysstat)の追加**が予定されている。
S6 は系列数に比例するため、500 系列で S6 だけが約 590 秒となり NFR-002(600 秒)を超える。

## 変更要求の内容

**S6 の検知処理を、系列ごとにスレッドを起こして並列実行する。**

### 必須の実装条件(いずれも実測にもとづく)

1. **各スレッドは `con.cursor()` で自分の接続を持つこと。**
   共有接続のままだと DuckDB 側で直列化され、8 スレッドでも **1.36 倍**にしかならない。
   `con.cursor()` を配れば **5.68 倍**になる。**ここが本 CR の成否を分ける。**
2. **CR-006(SQL 化)と対で行うこと。**
   CPython 3.14.2 は GIL が有効であり、**純 Python の処理はスレッドで速くならない**
   (実測: 4 スレッドで実効並列度 0.84)。DuckDB 実行中は GIL が解放されるため、
   **SQL 化した部分にだけスレッド並列が効く。**
3. **スレッド数の上限を設けること。** 実測では 8 が最適で、16 にしても伸びない(5.68x → 5.78x)。

### 対応する既存の仕様箇所

* `docs/P003-backend-spec.md` **7.1**(検知器の共通インタフェース)、**12章**(cli の全体制御)
* `docs/P001-requirement.md` **FR-032**(1 つの検知器が失敗しても他は続行する)、**NFR-009**(再現性)、**NFR-003**(メモリ)

## 期待する振る舞い

* **検知結果が並列化の前後で変わらない。** 同一入力に対する検知点の集合が一致すること。
* **同一入力に対して常に同一の結果になる**(NFR-009)。スレッドの実行順に依存しないこと。
* **1 つの系列・アルゴリズムで例外が起きても、他は続行する**(FR-032)。
  失敗は `failures` に記録され、レポートの「実行時の注意事項」に出ること。
* **S6 の実効並列度が上がる。** 目安として 4 以上。
* **スレッド数に上限があり、設定できること。** 既定値は実測にもとづく値とする。
* **メモリ使用量が既定の `max_memory`(4GB)を超えないこと。** 終了コード 6 が出ないこと。
* 進捗ログ(S6)が引き続き出ること。**順序は変わってよい**が、各アルゴリズムの
  「完了: 検知 N 点, スキップ M 系列, 所要 X 秒」は正しい値であること。

## 影響が想定される範囲

* 画面: 該当なし
* API: 該当なし
* データモデル: 変更なし
* モジュール: `app/src/s_anomaly/cli.py`(`detect`)、`app/src/s_anomaly/detectors/base.py`(`fetch_series` が受け取る接続)
* 設定: **スレッド数の設定キーを追加するか**の判断が要る。追加するなら `config.py` の `PARAMS` に登録する
  (現状 `threads` は未知キーとして無視される。`docs/P302-deliver.md` 10.3 #13)
* テスト: `test_detectors_*.py`、**結合テスト T004**(検知器の一括実行と失敗耐性)、**A003(再現性)**
* 関連ADR: 抵触するものは無い。**新規 ADR の候補**(「S6 は系列ごとにスレッド並列で実行し、各スレッドが `con.cursor()` を持つ」)

### 再現性(NFR-009)への影響 — 最大のリスク

**現状の実装には、既に再現性の担保が入っている。**

| 出力 | 現状 | 並列化後 |
| --- | --- | --- |
| `all_detections` | **`sort(key=(series_id, metric, algorithm, start_ts))` 済み** | **順序が変わっても結果は同じ。担保されている** |
| `all_skips` | `_skip_rows` が集約して `sorted()` 済み | **担保されている** |
| **`failures`** | **ソートしていない。追加順のまま** | **✕ 並列化で順序が変わる。ソートが要る** |
| 進捗ログ | 逐次順 | 順序が変わる。**NFR-009 の対象外**(対象は `report.md` のみ) |

**したがって、対処が要るのは `failures` の 1 箇所だけである。** 現状の設計が
**偶然ではなく意図的に**並列化しやすい形になっている(`docs/ADR.md` ADR-013 / ADR-015 の系譜)。

### メモリへの影響

★FIXME★ **スレッドごとに `con.cursor()` を持つと、DuckDB のメモリ使用がどう変わるかを実測すること。**
`max_memory`(既定 4GB)は接続単位ではなくデータベース単位の設定と考えられるが、
**前回 S8 で OOM(終了コード 6)を起こしたばかりであり、確認せずに進めない。**

## 優先度の判断理由

**影響度: 高 / 緊急度: 中 → 優先度: 中**

* 影響度: 検知処理全体の実行方式が変わる。再現性・失敗耐性という要件に直接触れる。
* 緊急度: **現時点では性能に問題がない**(90 日で 231 秒 / 目標 600 秒)。
  系列数の増加に備えた**予防的な対応**である。

## 備考

**CR-006 を先に完了させること。** 順序が逆だと効果が出ない。

**実測にもとづく設計値**(156 系列 × 8,640 点の SQL 処理):

| スレッド数 | 接続 | 所要 | 速度比 | エラー |
| --- | --- | --- | --- | --- |
| 1 | 共有 | 3.42s | 1.00x | 0 |
| 2 | `cursor()` | 2.04s | 1.68x | 0 |
| 4 | `cursor()` | 1.13s | 3.03x | 0 |
| **8** | **`cursor()`** | **0.60s** | **5.68x** | 0 |
| 16 | `cursor()` | 0.59s | 5.78x | 0 |
| 8 | **共有** | 2.51s | 1.36x | 0 |

★ACCEPTED★ **`multiprocessing` は採らない。** 検討したが、
(a) DuckDB 接続をプロセス間で共有できず、子プロセスが独立に DB を開く設計が要る、
(b) Windows の `spawn` によりモジュールの再 import が起き、**閉域環境で未実証の `vendor/` 経路が
子プロセスでも必要になる**、(c) ワーカー数 × `max_memory` でメモリ要求が跳ね上がる、
の 3 点により、複雑さとリスクが利得に見合わない。**スレッド + SQL 化で 5.68 倍が得られる以上、
プロセス並列を採る理由がない。**
