# CR-008 — 入力ファイル種別ごとのタイムゾーンを設定し、投入時に変換する

## 起票日

2026-09-06

## 起票者

本アプリの依頼者(会話による指示。2026-09-06)

## 背景・課題

**現状、タイムゾーンの概念がどこにも無い。**

* 入力の時刻文字列を、そのまま素朴な `TIMESTAMP`(タイムゾーンを持たない値)として
  `db_connection` / `jvm_gc` / `lsf_queue` に投入している。
* レポートも素朴な時刻をそのまま出しており、**それがどのタイムゾーンの時刻なのかが
  読み手に分からない。**

**これが問題になる場面は具体的である。**

| 場面 | 起きること |
| --- | --- |
| 入力ごとに採取時のタイムゾーンが違う | **同一時刻として突き合わせてしまう。** 「同時に発生したアノマリー」(CR-002)の区間の重なり判定が、実際にはずれた時刻同士で行われる |
| **sar(sysstat)の追加**(次バージョン) | **`sadf` の既定出力は UTC** である。他のログがローカル時刻なら、sar だけが時差ぶんずれる |
| レポートを人が読む / LLM に読ませる | `2026-09-06 01:01` がどの地域の時刻か判断できない |

**とくに 2 番目が差し迫っている。** sar 対応は次バージョンで実施することが決まっており
(`docs/P302-deliver.md` 10.5)、その時点でタイムゾーンの扱いが未整備だと、
**時差ぶんずれた突き合わせが無言で行われる。**

## 変更要求の内容

### 1. ファイル種別ごとに、読み込むデータのタイムゾーンを設定できるようにする

`settings.properties` で、入力ファイルの種別ごとに指定する。

### 2. DuckDB へ投入するときのタイムゾーンを設定できるようにする

投入先(格納)のタイムゾーンを 1 つ指定する。

### 3. 投入時に時刻を変換する

**S4(取り込み)で、読み込み元のタイムゾーンから格納タイムゾーンへ変換して投入する。**

**ただし、読み込み元と格納のタイムゾーンが同じ場合は変換を行わない**
(2026-09-06 の追加指示)。

### 4. レポートは投入された時刻をそのまま使う

**レポート生成時に再変換しない。** DuckDB に格納された時刻がそのままレポートに出る。

### 5. レポートの時刻にタイムゾーンを併記する

```
2026-09-06 01:01:00 (UTC)
```

### 6. 既定値はすべて UTC とする

**本アプリが使われることが想定されているシステムは、すべて UTC である**(依頼者の明示)。
配布する `settings.properties` の既定値をすべて `UTC` にする。

**この結果、既定の構成では 3 の変換は一度も発生しない**(読み込み元 = 格納 = UTC のため)。

### 7. README の sar 変換スクリプトも UTC を出力する

現在のスクリプトは `sadf -d -t`(採取ホストのローカル時刻)を使っている。
**`-t` を外して `sadf` の既定である UTC 出力にする。**

## 期待する振る舞い

* **タイムゾーン設定を変えても、同一設定なら結果は同一である**(NFR-009)。
* **読み込み元 = 格納のとき、変換に伴う処理が一切走らない**(要求 3 の但し書き)。
* **不正なタイムゾーン名は起動時に検出し、終了コード 3 で停止する。**
  他の設定値の検証(`docs/P002-frontend-spec.md` 2.2)と同じ扱いにすること。
* レポートの全ての時刻欄にタイムゾーンが併記される。
* **既定値のままなら、本CR適用前と同じ時刻がレポートに出る。**

## 影響が想定される範囲

* 画面: **レポートの全時刻欄**(`docs/P002-frontend-spec.md` 4章)
* API: 該当なし
* データモデル: **`ts` の型は `TIMESTAMP` のまま変えない。** 変換して格納するため、
  格納後は「格納タイムゾーンでの素朴な時刻」という意味になる
* モジュール:
  * `app/src/s_anomaly/config.py`(設定キーの追加)
  * `app/src/s_anomaly/loaders/__init__.py`(`BatchInserter` の投入 SQL)
  * `app/src/s_anomaly/reporter.py`(`format_ts`)
  * `app/src/s_anomaly/cli.py`(タイムゾーン名の検証と受け渡し)
* 設定: **新しいセクションを設ける**か、既存セクションに置くかの判断が要る
* テスト: `test_config` / `test_loaders` / `test_reporter` / 結合 T006 / 受け入れ A001・A003
* 関連ADR: **新規 ADR の候補**(タイムゾーンの変換方式と、変換しない条件)

### 技術的な制約(実測済み。2026-09-06)

**DuckDB の `AT TIME ZONE` を使う前提で確認した。**

| 確認したこと | 結果 |
| --- | --- |
| **名前付きタイムゾーン**(`UTC` / `Asia/Tokyo`)| **使える。** 拡張の自動読み込みを無効化(NFR-008)していても動く |
| **固定オフセット**(`+09:00`)| **使えない。** `Unknown TimeZone '+09:00'` になる |
| タイムゾーン名の一覧 | `pg_timezone_names()` で取得できる(638 件)。**検証に使える** |
| 大文字小文字 | **区別する。** `utc` は見つからない |

**したがって設定値は IANA の名前付きタイムゾーンに限る。**
固定オフセットは受け付けない旨を設定ファイルとドキュメントに明記すること。

## 優先度の判断理由

**影響度: 高 / 緊急度: 高 → 優先度: 高**

* 影響度: **全ての時刻に関わる。** レポートの表示だけでなく、イベントの統合・
  同時アノマリーの判定という**解析結果そのもの**に影響する。
* 緊急度: **sar 対応(次バージョン)の前提である。** 後回しにすると、
  sar を入れた時点で時差ぶんずれた突き合わせが無言で行われる。

## 備考

★ACCEPTED★ **夏時間(DST)の扱いは追わない。** 名前付きタイムゾーンを使うため
DuckDB 側が DST を解釈するが、**本アプリはそれが正しいかを検証しない。**
検討したのは、DST 切り替え時刻の重複・欠落を検出して警告する案。
**採らなかった理由**: 想定システムはすべて UTC であり(要求 6)、DST が存在しない。
**残存リスク**: DST のある地域を設定した場合、切り替え時刻付近の 1 時間で
時刻の重複または欠落が起きうる。その区間の検知結果は信用できない。
