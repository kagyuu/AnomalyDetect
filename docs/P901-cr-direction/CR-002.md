# CR-002 — 「同時刻のその他のデータ」を廃止し、観点1 の「同時に発生したアノマリー」に置き換える

## 起票日

2026-09-05

## 起票者

本アプリの依頼者(会話による指示。2026-09-05)

## 背景・課題

**現状**: 各イベントに「同時刻のその他のデータ」欄があり、**そのイベントの期間中に他の系列・
メトリクスがどのような値だったか**を出している。実装は `app/src/s_anomaly/correlate.py`(S8)で、
`metrics` テーブル(30 日規模で 135 万行)に対して**イベントの窓 × 基準 7 日 × 全系列**の
範囲結合を行い、平均・標準偏差を求めている。

**困りごとは 3 つある。**

1. **レポートの 63.4% をこの欄が占めている。** 実測(30 日分):

   | 行の種類 | バイト | 占有率 |
   | --- | --- | --- |
   | **相関の明細** | **9,132,755** | **63.4%** |
   | 原因候補 | 1,151,479 | 8.0% |
   | その他すべて | 4,109,731 | 28.6% |

2. **中身の多くが無意味である。** 上限 10 件が**全イベントで例外なく埋まっており**(平均ちょうど 10.0 行)、
   その大半が「— 平常時と有意差なし」である。**異常でないものを 10 件ずつ並べている。**

3. **処理時間の支配要因である。** 大規模 90 日での S8 は **299 秒**であり、全体 513 秒の **58%** を占める
   (`docs/ADR.md` ADR-014)。

**依頼者が本当に見たいもの**: 「DBConnection の高止まりと、利用メモリの高止まりが**同時に起きている**」
という、**アノマリー同士の同時発生**である。「他系列の平常時の平均値」ではない。

## 変更要求の内容

**「同時刻のその他のデータ」欄を廃止し、「同時に発生したアノマリー」欄に置き換える。**

1. **`metrics` を参照した相関の算出(S8)をやめる。** イベント検知時に他系列を調べない。
2. **全レポートを作る前に、検知済みイベント同士を突き合わせて「同時」を判定する。**
3. **「同時」の定義は、発生時間(開始〜終了)の区間に重なりがあること。**
4. **対象は観点1(瞬間的な外れ値)のイベントのみ。**
   * 観点2(持続的な数値の増加)のイベントは、**主体としても相手としても対象にしない**。
   * 「持続的な増加の期間中に瞬間的な外れ値が起きた」ことは**報告しない**(依頼者の明示)。
5. **1 イベントあたり最大 10 件。**
6. **並び順は「同一ホスト優先 → 脅威度の高い順 → 重なり時間の長い順」。**
7. **観点2 のみのイベントには、「同時に発生したアノマリー」欄を出さない**(欄ごと省略する)。

* 対応する既存の仕様箇所:
  * `docs/P001-requirement.md` **FR-074**(同時刻のその他のデータを付与する)、**FR-075**(基準期間は直前 7 日間の同時刻帯)、**FR-076**(相関先の上限と並び順)、**12.2 節**
  * `docs/P002-frontend-spec.md` **UI-04** 4.2(イベント本文の項目仕様)
  * `docs/P003-backend-spec.md` **DS-11**(M11 correlate)、**DS-11-02** / **DS-11-05**、**ADR-010**(S7 → S8 → S7' の実行順)

## 期待する振る舞い

* イベント本文の「同時刻のその他のデータ」欄が無くなり、「同時に発生したアノマリー」欄になる。
* 観点1 のアルゴリズム(ALG-A1〜A5)**だけ**で構成されたイベントに、この欄が出る。
* 観点2 のアルゴリズム(ALG-B1〜B5)を含むイベント(観点2 のみ・観点1 と観点2 の混在の両方)には、**この欄が出ない**。
* 各行には、相手のイベント ID・ホスト・メトリクス・脅威度が分かる情報が載る。
* 相手として挙がるのは、**発生区間が重なっている観点1 のイベント**だけである。
* 相手は最大 10 件であり、「同一ホスト優先 → 脅威度の高い順 → 重なり時間の長い順」に並ぶ。
* 重なる相手が 1 件も無いイベントでは、その旨が分かる(実測では観点1 のイベントの 10.4% が該当)。
* **`metrics` テーブルに対する相関用の集計クエリが実行されなくなる。**
* 検知の結果(どのイベントが出るか、脅威度、原因候補)は、本 CR によって変わらない。

## 影響が想定される範囲

* 画面: 該当なし
* API: 該当なし
* データモデル: **`_event_windows` 一時テーブルが不要になる**
* モジュール: `app/src/s_anomaly/correlate.py`(**大部分を置き換え**)、`app/src/s_anomaly/reporter.py`、`app/src/s_anomaly/cli.py`(S8 の位置づけ)
* **設定**: `events.merge_gap_minutes` は「同時」の判定に使わなくなる(区間の重なりで判定するため)。`correlate.BASELINE_DAYS` / `MAX_CORRELATIONS` / `SIGNIFICANT_RATIO` / `EVENT_BATCH` の扱いを見直す
* テスト: **T005**(S7 → S8 → S7' の実行順)、**T006**、**A001**、`app/tests/unit/test_events.py`(相関の選択)、`app/tests/_work/normal/expected.json` の期待値
* **関連ADR — 抵触するものが 2 件ある**:
  * **ADR-010**(原因候補の付与を相関情報の収集の後に行う: S7 → S8 → S7')。相関が原因候補ルールの入力であることを前提にした決定である。**「同時のアノマリー」が原因候補の入力になるのかを再検討する必要がある**
  * **ADR-014**(全イベントを 1 回の結合で集計せず、バッチに分けて中間結果を有界にする)。**S8 の集計そのものが無くなるため、この ADR は対象を失う**。ADR を「置き換え」または「一部撤回」として記録し直す必要がある
* **副次的な効果(実測にもとづく見込み)**:

  | | 現状 | 変更後の見込み |
  | --- | --- | --- |
  | 該当欄の行数 | 72,290 行 | **22,336 行**(上限 10 件・観点1 のみ) |
  | 該当欄のバイト | 9,132,755 | 約 130 万 |
  | レポート全体(30 日) | 14.39MB | **約 660 万バイト(-54%)** |
  | S8 の所要(90 日) | 299 秒 | **ほぼ 0 秒** |

## 優先度の判断理由

**影響度: 高 / 緊急度: 高 → 優先度: 高**

* 影響度: 全イベントの本文に現れる欄であり、レポートの過半を占める。
* 緊急度: レポートが読めない大きさである主因であり、かつ処理時間の 58% を占めている。**回避策が無い**。

## 備考

* **「同時」の判定方法として、区間の重なり以外も検討した**(いずれも実測にもとづく)。

  | 案 | 1 イベントあたりの相手 | 総行数 | 判断 |
  | --- | --- | --- | --- |
  | 区間の重なり / 全イベント対象 / 上限なし | 中央値 22・**最大 7,228** | 218,128 | **不採用**。解析期間全体(30 日)を覆うイベントが存在し、他の全件と「同時」になる |
  | 区間の重なり / 観点1 を含む(混在も) / 上限なし | 中央値 16・最大 6,275 | 326,542 | **不採用**。混在イベントが最大 719.9 時間の区間を持ち込む。**相手ゼロが 0 件**になり弁別力を失う |
  | **区間の重なり / 観点1 のみ / 上限 10** | 中央値 3・最大 165 | **22,336** | **採用** |

* 観点1 のみのイベントは 5,295 件(全体の 73.2%)、混在 981 件(13.6%)、観点2 のみ 953 件(13.2%)である。
