## 背景・課題

**本アプリは DB コネクション数・JVM GC・LSF キューの 3 種類しか読み込めない。**
OS レベルの資源(CPU・メモリ・スワップ・ディスク・ネットワーク・実行待ち)は
分析の対象外であり、次のことが起きている。

| 現状 | 内容 |
| --- | --- |
| **原因の切り分けができない** | 「DB コネクション数が張り付いた」ことは検知できるが、**そのとき CPU が飽和していたのか、スワップが始まっていたのか、ディスクが詰まっていたのかが分からない。** 原因候補ルール(S8)は 9 件あるが、いずれもアプリ層の指標だけで推定している |
| **「同時に発生したアノマリー」(CR-002)が痩せる** | 重ね合わせチャート(CR-009)も同様で、同一ホストで重ねられる系列がアプリ層の指標に限られる |
| **データは既に貯まっている** | `README.md` 付録A で入力形式と前処理スクリプトを先に確定してあり、依頼者はその形式で採取を進めている。**アプリ側だけが未対応である** |

**準備は済んでおり、実装だけが無い。** 実装が無いことは確認済みで、
`discovery` / ローダ / テーブル定義のいずれにも sar は存在しない
(`app/src/s_anomaly/config.py` の `SOURCE_KINDS` に「**sar を追加するときはここに 1 行足す**」
というコメントだけが置かれている)。

## 変更要求の内容

**`sadf -d` が出力した CSV を読み込み、既存の 11 アルゴリズムの検知対象に加える。**

### 既に確定している前提(本CRで蒸し返さない)

| 項目 | 内容 | 出典 |
| --- | --- | --- |
| 入力ファイル名 | **`sa-{ホスト名}-{yyyymmdd}.csv`** | `README.md` 付録A / `docs/P302-deliver.md` 10.5 |
| 前処理 | **人が採取ホスト上で `sadf -d` を実行して CSV 化する。** 変換スクリプトは `README.md` 付録A にある | 同上 |

| **ホスト名の正規化** | ★ACCEPTED★ **アプリ側では行わない**(2026-09-06 依頼者の判断)。揃えるのは前処理の責任とする。検討: `events.extract_host` に別名表を持たせる案。不採用: 前処理で正しい名前を渡せる以上、アプリに運用知識を持ち込む必要がないため。**残存リスク**: 変換時にホスト名を指定し忘れると静かに別ホストとして扱われる(エラーにならない) | `docs/P302-deliver.md` 10.5 |

### 本CRで確定した事項(2026-09-08 の回答)

`docs/P302-deliver.md` 10.5 が「まだ決まっていないこと」として残していた 3 件のうち、
2 件について依頼者の回答を得た。

| # | 論点 | **確定した内容** |
| --- | --- | --- |
| 1 | 時刻の整合をアプリ側で検証するか | **検証する。** `sadf -d` は時刻列に `2026-06-01 00:10:00 UTC` のようにタイムゾーン表記を付ける。**この表記と `[timezone]` の `sar` 設定が食い違う場合は警告を出す。** ただし**設定値を正とし、表記で自動変換はしない**(CR-008 の設計思想「設定が正」を維持する) |
| 2 | 取り込む活動種別の範囲 | **まず変換スクリプトと同じ 8 種類(`-u -r -S -b -q -W -d -p -n DEV`)すべてを取り込む。** そのうえで**設定で絞れるようにする**。実測(A006)を見て運用側で狭められる状態にしておく |
| 3 | `series_id` の形 | 既存の 3 書式(`db_connection/{host}:{port}/{source}` / `jvm_gc/{container}@{host}` / `lsf_queue/{host}/{queue}`)と揃え、**`sar/{host}/{活動}/{デバイス}`** とする(`docs/P302-deliver.md` 10.5 が示した案をそのまま採る)。デバイスを持たない活動は `sar/{host}/{活動}/-` のように占位子を置く |

### 変更が関わる箇所

* **入力仕様**(`docs/P001-requirement.md` 4章) — 入力ファイル種別が 3 → 4 になる
* **S3 探索**(`discovery`) — `sa-*.csv` の認識、`KIND_SAR` の追加、件数ログの表示
* **S4 取り込み** — sar 用ローダの新設(`loaders/sar.py`)。`#` 見出し行から列名を取り、活動種別ごとにメトリクスへ展開する
* **設定**(`settings.properties` / `config.py`) — `SOURCE_KINDS` への追加、`[timezone] sar`、活動種別の絞り込み
* **S7/S8** — `events.extract_host` の書式追加、原因候補ルール(sar の指標を根拠に使えるようにするか)
* **レポート・チャート** — メトリクスの和名、単位、脅威度判定の対象

## 期待する振る舞い

* 解析対象ディレクトリに `sa-{host}-{yyyymmdd}.csv` があると、S3 が **sar 種別として認識**し、起動ログの件数内訳に sar の件数が出る。
* `#` で始まる見出し行から列名を取り、**活動種別ごとに異なる列構成**を正しく解釈して `metrics` テーブルへ投入する。
* `series_id` は **`sar/{host}/{活動}/{デバイス}`** の形になり、`events.extract_host` がその `series_id` からホスト名を返す(`unknown` にならない)。
* **デバイス・インタフェース単位で 1 時刻に複数行が出る活動**(`-d -p` / `-n DEV`)を、デバイスごとの**別系列**として取り込む。
* **8 種類の活動**(`-u` CPU / `-r` メモリ / `-S` スワップ領域 / `-b` I/O / `-q` 実行待ち / `-W` スワップイン・アウト / `-d -p` ブロックデバイス / `-n DEV` ネットワーク)から、それぞれ 1 つ以上のメトリクスが取り込まれる。
* **取り込む活動種別を設定で絞れる**。既定は 8 種類すべてを取り込む。
* 既存の **11 アルゴリズムが sar の系列にも適用**され、埋め込んだ異常が sar 由来のイベントとして検知される。
* **`%memused` / `%util` / `%swpused` は上限 100 の比率**として ALG-C1(観点3)の判定に載り、**ADR-016 の推定上限を使わない**。
* sar 由来のイベントが、**同一ホストの他のログ(DB コネクション / JVM GC / LSF)のイベントと「同時に発生したアノマリー」で結び付く**。
* レポートに sar 由来のイベントが**他のログと同じ書式**で出力され、ホスト × 年月のファイル分割にも従う。
* **時刻列のタイムゾーン表記が `[timezone]` の `sar` 設定と食い違う場合、警告を出す**(処理は続行する。設定値を正として変換する)。
* **未知の活動種別・想定外の列構成の見出し行に出会っても実行を止めず**、その活動をスキップして理由を記録する(FR-072 と同じ扱い)。
* **`sa-*.csv` が 1 件も無い場合、従来どおり動作する**(後方互換。既存の受け入れテストがすべて合格する)。
* **`sadf` の版差で列が増減しても、列名で解釈するため落ちない**(位置ではなく見出し行の列名で対応付ける)。

## 影響が想定される範囲

P901時点での見積もりであり、確定した対応範囲ではない(確定は P903 が `docs/P903-cr-records/CR-010.md` に記録する)。

* **画面(CLI)**: 起動ログの件数内訳に sar が増える。`README.md` 付録A の「次バージョンで対応予定」の注記を外す
* **API**: 該当なし(単一プロセスの CLI。ADR-006)
* **データモデル**: `metrics` テーブルの構造は変えない(`series_id` / `metric` / `ts` / `value`)。**増えるのは行と系列であってテーブルではない**
* **モジュール**: `discovery`(M03) / `loaders/sar.py`(新設) / `config`(M02) / `events`(M09) / `causes`(M10) / `reporter`(M12) / `charts`(M15)
* **設定**: `settings.properties` に `[timezone] sar` と活動種別の絞り込みキーを追加
* **テスト**: `gen_testdata` に sar の生成を追加(既存の埋め込み異常と時刻を揃える必要がある)。単体 / 結合 / 受け入れの各層に追加
* **文書**: `README.md`(付録A・入力仕様・メトリクス一覧)、`docs/P001-requirement.md` 4章、`docs/P003-backend-spec.md`

### 関連ADR

| ADR | 関係 |
| --- | --- |
| **ADR-016**(実測最大値からの上限推定) | **抵触しない。** sar は比率を直接出すため推定経路を通らない。**ADR-016 を「使わない系列がある」ことを明記する必要がある** |
| **ADR-018**(S6 は系列ごとにスレッド並列) | **系列数が大きく増える。** 現在 110 系列で S6 は 90 日 21.1 秒。sar の 8 種類はデバイス・NIC 単位で増えるため、**A006(性能)で実測して NFR-002(600 秒)に収まることを確認する必要がある** |
| **ADR-019**(`ts` は `TIMESTAMP` のまま保つ) | **抵触しない。** sar の時刻列に付く TZ 表記は取り込み時に解釈して落とす |
| **ADR-002**(外部パッケージを DuckDB のみに限定) | **抵触しない。** CSV の解析は標準ライブラリで行う |
| **ADR-011**(一括挿入は一時 CSV + `read_csv`) | 同じ経路に載せる |
| **CR-008**(タイムゾーン) | **前提として使う。** `[timezone]` に `sar` を追加する |

## 優先度の判断理由

**優先度: 高。**

* **影響度: 高** — 入力仕様(P001 4章)の拡張であり、S3 から S12 まで全ステップに関わる。分析できる範囲そのものが広がるため、主要機能への影響が大きい。
* **緊急度: 高** — 依頼者が明示的に依頼しており、**回避策が無い**(前処理で CSV にしても、アプリが読まない限り分析できない)。データは既に採取が進んでおり、対応が遅れるほど「読めないデータ」が積み上がる。

ルーブリック(影響度: 高 × 緊急度: 高)より **優先度: 高**。
