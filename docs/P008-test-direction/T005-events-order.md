# 【テストID】T005 — イベント処理の実行順序

## 【目的】

* `events`(統合・脅威度)→ `correlate`(相関)→ `causes`(原因候補)の **3 モジュールが、S7 → S8 → S7' の順序で正しく連携する**ことを確認する。
* **この順序は本アプリで最も間違えやすい箇所である。** `docs/P001-requirement.md` 7章の処理フロー図は S7 → S8 の順に描かれているが、原因候補の判定には相関情報が必要であり、実装順序は `docs/P003-backend-spec.md` DS-10-02 のとおり S7 → S8 → S7' でなければならない。順序を誤ると、相関を参照するルール(CR-01 / CR-02 / CR-04 / CR-06)が**永久に発火しない**まま、エラーも出ずに動いてしまう。本テストはその事故を検出する。

## 【実行手順】

**手順 A: 正しい順序での実行**

1. `events.merge_detections(detections, cfg)` を呼び、`Event` のリストを得る。
2. `events.assign_severity(events, con, cfg)` を呼ぶ。
3. `correlate.collect(events, con, cfg)` を呼ぶ。
4. `causes.assign_causes(events, cfg)` を呼ぶ。
5. `events.sort_for_report(events)` を呼ぶ。
6. 結果を検証する。

**手順 B: 順序を誤った場合の検出**

7. 手順 1〜2 まで実行した状態から、**`correlate.collect` を呼ばずに** `causes.assign_causes` を呼ぶ。
8. **相関を参照するルール(CR-01 / CR-02 / CR-04 / CR-06)が 1 件も発火しない**ことを確認する。
9. これにより、手順 A と手順 B の結果が異なることを示す。**両者が同じ結果になる場合、`causes` が相関情報を使っていない(仕様違反)ことを意味するため FAIL とする。**

# 【CR-001〜CR-004 による改訂】2026-09-05

**本テスト指示は、CR-001〜CR-004 の適用にともない次のとおり変更する。**
上記の本文のうち、下記と矛盾する記述は本節を正とする。

## 変更点(CR-002・CR-003)

**実行順が S7 → S8 → S7' から、S7 → S7'(採番)→ S8 → S8' に変わる。**

| ステップ | 内容 | 検証すること |
| --- | --- | --- |
| S7 | 検知点をイベントへ統合し脅威度を決める | 従来どおり |
| **S7'** | **イベント ID を採番する** | **S8 より前に全イベントの `event_id` が確定していること** |
| S8 | **同時に発生したアノマリーを突き合わせる**(`co_anomaly`) | `metrics` へのクエリが発行されないこと |
| S8' | 原因候補を付与する(`causes`) | 入力が `co_anomalies` になっていること |

### 追加する確認項目

1. **`co_anomaly.collect()` の呼び出し時点で、全イベントの `event_id` が空でないこと。**
   同時アノマリー欄は相手の ID を出力するため、採番が先に確定していなければならない。
2. **`co_anomaly` が DuckDB コネクションを受け取らないこと。** シグネチャが `collect(events)` であること。
3. **S8 の実行中に `metrics` テーブルへのクエリが 1 本も発行されないこと。**
   確認方法: DuckDB コネクションをラップして `execute` の呼び出しを記録し、S8 の区間で 0 件であることを見る。
4. `causes` が `co_anomalies` を参照していること(`correlations` という属性が存在しないこと)。

### 削除する確認項目

* 「`correlate` が `_event_windows` 一時テーブルを作ること」— **CR-002 により廃止された**(P003 DS-11-08)。
