* 実施日: 2026-09-05

## 1. スコープの判断

**受け入れる。** 依頼者の目的「DBConnection や Java のメモリが上限値に張りついている
ことを知りたい」に対し、**既存の 10 アルゴリズムでは最も知りたい状態を取りこぼしていた。**

| 状況 | 観点1(外れ値) | 観点2(増加) | **観点3(本CR)** |
| --- | --- | --- | --- |
| 一時的に跳ねた | ○ | ✕ | ✕ |
| 増え続けている | ✕ | ○ | ✕ |
| **上限に達して頭打ち** | ✕ | **✕** | **○** |
| **期間の最初から張り付き** | ✕ | **✕** | **○** |

観点2 が取りこぼす理由は明確である。**上限に達すると増加が止まる**ため、
「末尾の最大 > 以前の最大」も「短期移動平均 > 長期移動平均」も偽になる。
**張り付きは「変化」ではなく「状態」であり、変化を見るアルゴリズムでは原理的に捉えられない。**

### 上限値の決め方 — 依頼者が案 C を選択

入力(`DBConnection*.csv`)にコネクションプールの上限値の列が無い。3 案を提示した。

| 案 | 内容 | 依頼者の判断 |
| --- | --- | --- |
| A | 入力に上限値の列を足してもらう | ✕ |
| B | 設定ファイルに系列ごとの上限を書く | ✕ |
| **C** | **解析期間中の実測最大値から推定する** | **採用** |

理由: 「**運用管理側には、設定値の変更が伝えられない場合が多い**」(2026-09-05)。
A・B はいずれも運用側が上限値を教えてくれることを前提にしており、成り立たない。

★ACCEPTED★ **推定上限は真の上限とは限らない。** 検討したのは案 A・B だが上記の理由で
採らなかった。残存リスクは「**実際には上限に達していないのに張り付きと判定する**」ことであり、
これを 3 章のガードで抑えている。レポートには `推定上限` と明記し、実際の容量が
取れる場合(`*_pct` が導出済み)はそちらを優先する。

## 3. 事前のスコープ想定と実際の差異

**2 件の誤検知を、実データ規模の試行で発見して是正した。**

### 3.1 0/1 のフラグ系列を必ず誤検知する

`lsf_queue` の `susp`(0 または 1)に対し、推定上限が 1 になり
「**推定上限 1 の 90% 以上が続いた**」が常に成立していた。

**最初に採った対策は失敗した。** 中央値に対する最大値の比でガードしたところ、
検知したい INJ-004(最大/中央値 = 1.44)まで弾いてしまった。

**採った対策は 2 段構えである。**

| # | ガード | 効く相手 |
| --- | --- | --- |
| 1 | `count(DISTINCT value) >= 10` | 値の種類が少ない系列(フラグ)を**構造的に**弾く |
| 2 | `max / quantile_cont(value, 0.05) >= 1.5` | 常時ほぼ一定の系列を弾く |

**2 で最小値ではなく 5 パーセンタイルを使う。** 一度でも 0 を取ると比が無限大になり、
ガードが素通りするためである(`test_zero_floor_does_not_bypass_the_guard` が回帰試験)。

### 3.2 レポートにアルゴリズム名と説明が出なかった

`reporter._ALGORITHM_NAMES` と `_explain_one` に ALG-C1 を足し忘れており、
名称が空欄・説明行なしで出力されていた。**新しいアルゴリズムを足すときは、
検知器・設定・レポートの 3 箇所を揃えて変える必要がある**(P010 の観点に追加)。
