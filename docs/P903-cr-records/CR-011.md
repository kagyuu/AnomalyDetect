### スコープの妥当性

**着手前のスコープ決定と実際が完全に一致した。**
とくに **P005(実装計画)と P020(実装構造)を「対象外」とした判断が正しかった**ことが、
実作業で裏づけられた。新規ファイル・新規モジュール・テーブル定義の変更が
1 つも発生しなかったためである。

**これは ADR-023(`sar` を縦持ちにする)の直接の帰結である。**

### 既存 ADR との関係

| ADR | 関係 | 判定 |
| --- | --- | --- |
| **ADR-023**(`sar` は縦持ち) | **本CRがその利点を実証した。** 活動を 2 つ・メトリクスを 14 増やしても、**テーブル定義・論理 PK・列型のいずれも変更していない。** 横持ち設計なら 2 テーブルとローダ分岐が増えていた | **有効。追記も不要**(ADR-023 の「代償」節が既に「活動をまたいだ横断 SQL は書きにくい」と記録しており、本CRはその判断を覆していない) |
| **ADR-022**(sar の比率は一次の検知対象) | **抵触しない。** NFS のメトリクスは比率ではなく毎秒のレートであり、`pct_` 接頭も付かない | 有効のまま |
| **ADR-016**(実測最大値からの推定上限) | **抵触しない。** 全 14 メトリクスを ALG-C1 の対象外とした | 有効のまま |
| **ADR-018**(S6 は系列ごとにスレッド並列) | **方式を変えていない。** 系列数が増えたが、A006 で NFR-002 に収まることを実測した(90 日 367.3s / 余裕 39%) | 有効のまま |
| **ADR-003**(`effective_sigma` の下限) | **覆していないが、2 箇所で効いた。** (1) INJ-013 / INJ-014 をスパイクではなく水準の変化にした理由。(2) 全て 0 の `nfsd` 系列から検知が出ない理由(FR-142c) | 有効のまま |
| **ADR-011**(一括挿入) | 同じ経路に載せた | 有効のまま |

### 新たな ADR を作らなかった理由

**本CRで行った判断は 4 つあるが、いずれも ADR の水準に達しない。**

| 判断 | なぜ ADR にしないか |
| --- | --- |
| 活動名を `nfs` / `nfsd` にした | `sadf` の指定(`-n NFS` / `-n NFSD`)をそのまま小文字にしただけであり、選択の余地が無い |
| 判別列に `retrans/s` / `scall/s` を選んだ | **DS-SAR-02a として P003 に記録した。** 実装上の注意であり、設計判断ではない |
| `packet_s` / `udp_s` / `tcp_s` を落とした | **FR-142b として P001 に記録し ★FIXME★ を付けた。** 取り込む範囲の選択であり、後から変えても他に影響しない |
| テストデータで `nfsd` を 1 ホストだけにした | **P001 18.1 に記録し ★FIXME★ を付けた。** テストデータの作り方であり、アプリの設計ではない |

**「知らずに触ると静かに壊れる」性質を持つ判断が無かった**ため、ADR を増やさない。
(ADR-022 はまさにその性質を持っていたため ADR にした。)
