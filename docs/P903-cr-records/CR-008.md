## 3. 設計上の判断

### 3.1 `ts` の型を変えなかった(ADR-019)

**`TIMESTAMPTZ` にすると、表示が DuckDB のセッションタイムゾーンに依存する。**
同じデータでも実行環境によってレポートが変わり、**NFR-009(再現性)を壊す。**
**投入時に変換して素朴な `TIMESTAMP` のまま格納すれば、格納後の値は環境に依存しない。**

### 3.2 レポート側で変換しなかった

`events` の統合も `co_anomaly` の重なり判定も**格納された値で行われる。**
**レポートだけ変換しても、解析は元のずれたままになる。** 直す場所が違う。

### 3.3 変換しない条件(2026-09-06 の追加指示)

**読み込み元と格納先が同じなら `AT TIME ZONE` を発行しない。**
`_build_select()` が `"*"` を返し、**投入 SQL は本CR適用前と同一になる。**

これは性能上の配慮であると同時に、**ICU(タイムゾーン DB)への依存を通常経路から
外す**という意味を持つ。既定はすべて UTC のため、通常の構成では変換が現れない。

## 4. 事前のスコープ想定と実際の差異

### 4.1 固定オフセットが使えなかった

**起票前の実測で判明していたが、影響が想定より大きかった。**

| 書き方 | 結果 |
| --- | --- |
| `AT TIME ZONE 'Asia/Tokyo'` | 使える(拡張の自動読み込みを無効化していても動く) |
| **`AT TIME ZONE '+09:00'`** | **使えない。`Unknown TimeZone '+09:00'`** |
| `utc`(小文字) | 使えない(大文字小文字を区別する) |

**設定を IANA の名前付きタイムゾーンに限る**ことにし、
`pg_timezone_names()`(638 件)で実在を検証する仕組みを入れた。

### 4.2 検証のタイミングを分けることになった

**設定を読み込む S2 の時点では DuckDB の接続がまだ無い**ため、
`pg_timezone_names()` を引けない。**接続を開いた直後(S3)で検証する**構成にした。
利用者から見た振る舞い(終了コード 3・全件まとめて報告)は他の設定値と同じである。

### 4.3 テスト側のパーサが壊れた

**結合テストの `report_parser._parse_ts` が併記に対応しておらず 2 件が失敗した。**
`docs/ADR.md` ADR-009 が予告していた依存(レポート書式を変えたら
テスト側の解析処理も直す)が、また現実化した。

## 5. 実行した確認

### 5.1 試験の範囲は依頼者が明示的に狭めた

> 性能やバリエーション、エラー系のテストなどは、入力 UTC、レポート UTC のみで構いません。
> その他に {入力JST、レポートUTC} および {入力UTC、レポートJST} の場合の疎通確認をお願いします。
> …当面 sar は分析対象にならないので、sar が無い場合の疎通テストもしてください。
> (2026-09-06)

**根拠**: 想定システムはすべて UTC であり、非 UTC 構成は「設定できる」ことに意味が
あるのであって、その構成で運用されるわけではない。

### 5.2 結果

| 区分 | 件数 | 結果 |
| --- | --- | --- |
| 単体 `test_timezone.py` | 25 | PASS |
| 受け入れ `A012` | 12 | PASS |
| 結合(併記の網羅) | 2 | PASS |

**A012 の疎通確認**

| 構成 | 確認できたこと |
| --- | --- |
| 入力 JST / レポート UTC | 完走。対象期間の開始が `2026-06-01 00:00:00` → **`2026-05-31 15:00:00`**。併記は `(UTC)` |
| 入力 UTC / レポート JST | 完走。開始が **`2026-06-01 09:00:00`**。併記は `(Asia/Tokyo)` |
| **sar が無い場合** | 完走。**`sa-*.csv` を置いても無視され、結果が変わらない** |
| 既定(全 UTC) | `変換は行いません` が出て、変換の SQL が発行されない |

**不正な設定値**(いずれも終了コード 3)

| 値 | 結果 |
| --- | --- |
| `+09:00` | 停止。「固定オフセット +09:00 は使えません」 |
| `utc` | 停止(大文字小文字を区別する) |
| `Asia/Nowhere` | 停止 |

## 7. P905(ADR 判定)の記録

**新規 ADR とした(ADR-019)。** 「なぜ `TIMESTAMPTZ` を使わないのか」は
**後任が必ず疑問に思う。** 一見すると型で表現するほうが素直に見えるが、
**表示がセッションタイムゾーンに依存して再現性を壊す**という理由はコードから読み取れない。
固定オフセットが使えないことも、実測しないと分からない。
