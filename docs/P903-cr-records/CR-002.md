### 事前のスコープ想定と実際の差異

**スコープの範囲そのものに差異は無かった。** 着手前に「対象」とした P002〜P009・P020〜P022・
P101〜P104・P201〜P205・P301・P302 はすべて実際に対象になり、「対象外」とした P000・P001 には
触れていない(P001 は P902 が更新済み)。

**ただし、設計の内容に 3 件の想定外があった。いずれも実測で発見し、その場で是正した。**

#### 差異 1: 原因候補ルールが構造的に発火しなくなった(設計の欠陥)

* **想定**: DS-10-06 の読み替えにより「条件が緩くなる」(CR-01 / CR-04 が成立しやすくなる)。
* **実際**: **まったく発火しなくなった。**
* **原因**: CR-01(メモリリーク)は「`ou` が floor_rise = **観点2**」を主体とするルールだが、
  観点2 のイベントには `co_anomalies` を設定しない設計にしたため、条件を評価できなかった。
  CR-02 / CR-04 / CR-06 も同じ理由で発火不能であった。
* **是正**: `co_anomaly` の出力を **2 系統**に分けた。
  * `co_anomalies` — **レポートに出す**もの。観点1 のみ(依頼者の指示どおり)
  * `concurrent_by_metric` — **原因候補ルール専用**。同一ホストで区間が重なるイベントを
    メトリクス別に 1 件。**観点を問わず、レポートには出さない**
* **判断の根拠**: 依頼者の指示は**レポートの表示**についてのものであり
  (「観点2 のみのイベントでは同時のアノマリーを出さなくていい」)、原因候補の内部推論を
  観点1 に限る趣旨とは読めない。メモリリークの原因候補が失われるのは P000 の主目的
  (観点2 = メモリリークの検出)に反する。

#### 差異 2: 「変化なし」の読み替えが厳しすぎた

* **実際**: 是正 1 のあとも CR-01 が発火しなかった。14 日間の `ou` イベントには
  期間中のあらゆるイベントが区間として重なるため、`eu` の `level_shift` が
  「eu に変化あり」と判定されていた。
* **是正**: 否定条件(「変化なし」「横ばい」)の判定を
  **持続的な上昇(`trend_up` / `floor_rise`)が無いこと**に限定した。
  単発のスパイクや水準シフトは阻害要因にしない。
* **根拠**: CR-01 の「eu に変化なし」は「若い世代も一緒に増え続けてはいない = 単なる負荷増ではない」
  という意図であり、eu の単発スパイクはこの判断を覆さない。

#### 差異 3: 破損データの読み飛ばし件数が失われた(FR-014 違反)

* **実際**: 検知 0 件だとホスト別ファイルが作られず、「実行時の注意事項」の記録先が消えていた。
* **是正**: サマリに「5. 実行時の注意事項」を追加した(P002 UI-04-F10 が定めていた
  「ホストに紐づけられないものはサマリ側に載せる」の実装漏れであった)。

#### 差異 4: 4K の上限設定が甘かった

* **想定**: サマリは 2,764 バイト(30 日規模の試算)で 4K に収まる。
* **実際**: **90 日規模で 7,254 バイト**になった。「4. 複数ホストで同時に発生したアノマリー」で
  16 ホスト分の名前を 1 行に列挙していたことが主因(3,683 バイト)。
* **是正**: **すべての表に行数上限を置き、規模が伸びても増えない構造にした**
  (`MAX_HOST_ROWS`=10 / `MAX_BUCKET_ROWS`=10 / `MAX_CROSS_HOST_ROWS`=8 /
  `MAX_LISTED_HOSTS`=3 / `MAX_LISTED_METRICS`=3)。DS-12-08 を実測値で更新した。

### #9 について — 原因候補は変わった

**変更要求では「検知の結果は変わらない」としていたが、原因候補は変わる。**

* イベントの集合・脅威度・検知アルゴリズムは**変わっていない**(21,307 件で一致)。
* しかし**原因候補ルール 9 件のうち 5 件の判定条件が変わった**(DS-10-06 の読み替え)。
  変更要求の「影響が想定される範囲」には ★FIXME★ 付きで記載していたが、
  「期待する振る舞い」の #9 の書き方と食い違っていた。
* **実装中に、素朴な読み替えでは CR-01(メモリリーク)が構造的に発火しなくなることが判明し、
  2 段階の是正を行った**(対処内容の「差異 1」「差異 2」)。
* **実データでの妥当性は未確認である。** `docs/P302-deliver.md` 10.1 #6 に申し送った。

## ADR更新判定(P905が記載)

**ADR 更新: 必要であった。3 件を処理した。**

| ADR | 処理 | 理由 |
| --- | --- | --- |
| **ADR-010**(原因候補の付与を相関情報の収集の後に行う) | **改訂**(状態は `採用` のまま) | **決定そのもの(M11 → M10 の順序)は有効である。**ただし M11 の役割が「相関の収集」から「同時アノマリーの突き合わせ」に変わり、M10 の入力も変わった。さらに **CR-003 により ID 採番が S8 より前に入った**ため、処理順が S7 → S8 → S7' から **S7 → S7'(採番)→ S8 → S8'** になった。確認方法も「`correlate.collect` を呼ばないと発火しない」から「`co_anomaly.collect` を呼ばないと発火しない」に変わった |
| **ADR-014**(全イベントを 1 回の結合で集計せず、バッチに分けて中間結果を有界にする) | **廃止**。本文を [`docs/ADR_master.md`](../ADR_master.md) へ移動 | **本 ADR が対象としていた「S8 の集計」そのものが無くなった。** `metrics` への範囲結合を廃止したため、「1 回の結合の中間結果を有界にする」という決定は適用対象を持たない。**ただし原則(入力規模に対して中間結果が有界であること)は、掃引法によりより強い形で満たされている** |
| **ADR-015**(レポートは「列挙」と「集計」の 2 層で出力し、ホスト × 年月に分割する) | **新設** | CR-001 / CR-004 と一体の決定として記録した(下記) |

**新たな技術的決定として ADR に記録しなかったもの**とその理由:

* **掃引法(sweep line)による重なり判定** — アルゴリズムの選択であり、
  「全ペア総当たりを避ける」ことは `docs/P003-backend-spec.md` DS-11-04 に実装方針として記載済み。
  ADR にするほどの分岐(他の案との比較で覆りうる判断)ではない。
* **原因候補ルール専用の入力を分けたこと**(`concurrent_by_metric`) —
  **これは記録に値する判断だが、ADR ではなく DS-10-06 と本記録の「差異 1」に残した。**
  理由: 決定の対象が「原因候補ルールの入力をどこから取るか」という**モジュール内部の設計**であり、
  ADR が扱う「プロジェクト全体に及ぶ技術的決定」の粒度ではないため。
  ★FIXME★ この粒度の判断は Agent の裁量である。ADR に格上げすべきかは人間の確認が望ましい。
