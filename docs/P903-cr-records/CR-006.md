# CR-006 対処記録 — 純 Python 実装の検知器を SQL(DuckDB の窓関数)へ移す

* 対象CR: [CR-006](../P901-cr-direction/CR-006.md)
* 実施フェーズ: P903(修正実施)
* 実施日: 2026-09-05

---

## 1. スコープの判断

**受け入れる。ただし手段は変えた。**

CR の要求は「純 Python の検知器を DuckDB の窓関数へ移す」であり、
その目的は「**S6 を速くし、系列数の増加に耐えられるようにする**」ことであった。

**実装と実測の結果、要求された手段(系列単位の SQL 化)では目的を達成できないと分かった。**
目的そのものは、別の手段で達成した。

| | 起票時の想定 | **実測で分かったこと** |
| --- | --- | --- |
| S6 の主因 | 純 Python の計算(32.7 秒 / 68%) | **同一データの読み直し(S6 の 52%)** |
| SQL 化の効果 | 速くなる | **系列単位では 1.9 倍遅くなる** |
| 目標 | 実効並列度 1.51 → 向上 | 達成(下記) |

---

## 2. 何をしたか

### 2.1 採った対策 — 系列単位のキャッシュ

**同じ系列のデータを、検知器の数だけ読み直していた。**

```
30 日規模 / 156 系列 / 11 検知器
  問い合わせ 1,716 回 のうち 1,560 回 (91%) が同内容の読み直し
  fetch_series が S6 全体の 52% (12.19 秒中 6.40 秒)
```

`detectors/base.py` に**スレッドローカルのキャッシュ**を置き、
`cli.detect` のループの向きを「検知器ごと」から「**系列ごと**」に変えた
(CR-007 と一体の変更である)。

| 対象 | 変更 |
| --- | --- |
| `fetch_series` | 同一系列の 2 回目以降はキャッシュを返す |
| `fetch_segments`(新設) | `group_by_segment` の結果もキャッシュする(1,092 回 / 1.7 秒) |
| `seasonal_diffs` | **epoch を先に一括で作る。** 内側のループで `datetime.timestamp()` を 1,600 万回呼んでいた |

### 2.2 実装したが採らなかった対策 — 系列単位の SQL 窓関数

**ALG-A1 を SQL(窓関数)へ移す実装を完成させ、出力が完全一致することを確認したうえで
差し戻した。**

```sql
WINDOW w AS (PARTITION BY segment ORDER BY ts
             RANGE BETWEEN to_microseconds(?) PRECEDING AND CURRENT ROW)
```

* **正しさは確認できた。** 30 日規模の全 18 ファイルが、「実行日時」の 1 行を除いて
  バイト単位で一致した(検知点 6,673 点も一致)。浮動小数点の差も出なかった。
* **しかし 4.6 秒 → 8.9 秒と約 1.9 倍遅くなった。**

**原因は問い合わせの粒度である。**

| 方式 | 156 系列 × 8,640 点の所要 |
| --- | --- |
| **系列ごとに SQL(156 クエリ)** | RANGE 7.59s / ROWS 5.31s |
| 純 Python の逐次走査 | **1.54s** |
| **全系列を 1 クエリ**(`PARTITION BY series_id, metric, segment`) | **0.88s** |

**1 系列 8,640 点では、DuckDB の 1 クエリあたりの固定費が窓計算そのものより大きい。**
SQL が有利になるのは全系列を 1 クエリで処理する形だけである。

### 2.3 SQL 化しない個別の理由(CR の要求どおり記録する)

| アルゴリズム | 理由 |
| --- | --- |
| ALG-A1 / B1 | 時刻範囲の窓。**SQL でも書けるが 2.2 のとおり遅くなる** |
| ALG-A2 | 移動中央値 + MAD。**MAD は 2 段階の中央値**であり窓関数 1 回では書けない |
| ALG-A4 | EWMA は**前の値に依存する再帰**。窓関数で表現できない |
| ALG-B2 | Mann-Kendall の全ペア符号和は **O(n²)** |
| ALG-B3 | バケット最小値。`GROUP BY` で書けるが所要 0.4 秒で利得が無い |
| ALG-B4 | CUSUM の累積和は**再帰**。ADR-013 の二分探索が既に効いている |

**ALG-A3 / A5 / B5 / C1 は従来どおり SQL 実装のままである。**

## 4. 残した課題(次のCRの候補)

**全系列を 1 クエリで処理する方式へ移せば、さらに速くなる余地がある**(2.2 の実測で
純 Python の 1.75 倍)。ただしこれは検知器の実行方式を

```
系列ごとに全検知器を適用する
  → 検知器ごとに全系列を一括で前処理し、そのあと系列ごとに判定する
```

へ変える設計変更であり、**CR-007(系列ごとのスレッド並列)と真正面から衝突する。**
また全系列分の中間結果を保持するためメモリ要求が増え、**過去に S8 で OOM(終了コード 6)を
起こした経緯がある**以上、90 日規模での実測なしには入れられない。

★ACCEPTED★ **本CRの範囲では行わない。** 検討したが、
(a) 現状 90 日で 178 秒 / 目標 600 秒と余裕が大きい、
(b) CR-007 と設計が衝突し、両方を同時に変えると切り分けが困難になる、
(c) メモリ影響の実測が別途要る、の 3 点による。
残存リスクは「系列数が桁で増えた場合に再検討が要る」ことであり、
`docs/P302-deliver.md` 10章へ申し送る。

## 7. P905(ADR 判定)の記録

**新規 ADR とした(ADR-017)。** 「SQL 窓関数へ移さない」は、**後任が必ず再検討する類の決定**である。
CR の起票文にも「SQL 化すれば速くなる」と書いてあり、実測を知らなければ同じ道を辿る。
**実装して測ったうえで棄却したという事実と数値**を残す価値が高い。
