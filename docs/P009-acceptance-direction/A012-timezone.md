# A012 — タイムゾーンの疎通確認(※CR-008)

* 対象CR: [CR-008](../P901-cr-direction/CR-008.md)
* 実装: `app/tests/acceptance/test_a012_timezone.py`
* 対応する要件: **FR-120〜FR-125**(`docs/P001-requirement.md` 13.1)

---

## 1. 試験の範囲 — **意図的に狭くしてある**

**2026-09-06 に依頼者が範囲を明示した。**

> 性能やバリエーション、エラー系のテストなどは、入力 UTC、レポート UTC のみで構いません。
> その他に {入力JST、レポートUTC} および {入力UTC、レポートJST} の場合の疎通確認をお願いします。
> 繰り返しますが、タイムゾーンが指定されていた場合は疎通テストのみで良いです。
> あと、当面 sar は分析対象にならないので、sar が無い場合の疎通テストもしてください。

**根拠**: 本アプリが使われることが想定されているシステムは**すべて UTC** である。
非 UTC の構成は「設定できる」ことに意味があるのであって、**その構成で運用されるわけではない。**
組み合わせを網羅しても、確かめているのは実際には使われない経路である。

| 区分 | 構成 | どこで試験するか |
| --- | --- | --- |
| 性能 | 入力 UTC / レポート UTC | **A006**(本書では行わない) |
| エラー系・バリエーション | 入力 UTC / レポート UTC | **A002 / A009 ほか**(本書では行わない) |
| 変換規則そのものの正しさ | — | **単体テスト** `tests/unit/test_timezone.py` |
| **疎通** | **入力 JST / レポート UTC** | **本書 3.1** |
| **疎通** | **入力 UTC / レポート JST** | **本書 3.2** |
| **疎通** | **sar が無い場合** | **本書 3.3** |

★ACCEPTED★ **非 UTC 構成を深追いしない。** 検討したのは、主要なタイムゾーンの
組み合わせ表を作って総当たりする案。**採らなかった理由**: 依頼者の明示の指示であり、
かつ想定システムが UTC のみであるため費用対効果が見合わない。
**残存リスク**: 非 UTC 構成に固有の不具合(DST 境界など)は検出できない。
DST については `README.md` 4.4 の ★ACCEPTED★ に別途記載がある。

## 2. 事前準備

ベースラインのテストデータ(14 日分)を用いる。**A006 のような大規模データは使わない。**
疎通の確認に規模は要らない。

設定は `H.make_dist()` で複製した配布物の `settings.properties` を差し替えて与える
(**`settings.properties` は `s_anomaly.py` と同じディレクトリから読まれる**ため、
作業ディレクトリに置いても効かない)。

## 3. 試験項目

### 3.1 入力 JST / レポート UTC

```ini
[timezone]
storage = UTC
db_connection = Asia/Tokyo
jvm_gc = Asia/Tokyo
lsf_queue = Asia/Tokyo
```

| # | 確かめること | 期待 |
| --- | --- | --- |
| 1 | 完走する | 終了コード 0。サマリが出力される |
| 2 | 変換した旨が進捗に出る | `投入時にタイムゾーンを変換します` |
| 3 | **時刻が 9 時間 戻る** | 対象期間の開始が `2026-06-01 00:00:00` → **`2026-05-31 15:00:00`** |
| 4 | 併記は `(UTC)` | 格納タイムゾーンが併記される |

### 3.2 入力 UTC / レポート JST

```ini
[timezone]
storage = Asia/Tokyo
db_connection = UTC
jvm_gc = UTC
lsf_queue = UTC
```

| # | 確かめること | 期待 |
| --- | --- | --- |
| 1 | 完走する | 終了コード 0 |
| 2 | **時刻が 9 時間 進む** | 対象期間の開始が **`2026-06-01 09:00:00`** |
| 3 | 併記は `(Asia/Tokyo)` | **格納タイムゾーンが併記される**(入力側ではない) |

### 3.3 sar が無い場合

**sar は当面 分析対象にならない。** したがって「無くても支障が無いこと」を確かめる。

| # | 状況 | 期待 |
| --- | --- | --- |
| 1 | sar のファイルも設定も無い(通常の構成) | 終了コード 0。完走する |
| 2 | **`sa-*.csv` が置いてある** | **無視され、結果が変わらない**(置いていない場合と一致) |
| 3 | `[timezone]` に `sar = UTC` と書いた | **未知のキーとして警告し、無視する。** 停止しない |
| 4 | 設定に sar が無い | タイムゾーンの検証は通る。`変換は行いません` が出る |

**#2 が重要である。** 利用者は sar 対応より前から `sa-*.csv` を貯めはじめる
(`README.md` 1.5)。**そのファイルが現行版の解析結果を変えてはならない。**

### 3.4 全構成に共通

| # | 確かめること |
| --- | --- |
| 1 | **レポートの全ての時刻欄にタイムゾーンが併記されている。** 1 箇所でも欠けたら失敗 |
| 2 | 既定(全 UTC)では `変換は行いません` が出て、変換の進捗行が出ない |
