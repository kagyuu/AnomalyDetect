### ★#3〜#6 の原因 — アプリではなく `report_parser.py` の欠陥である★

**レポートには 3 件とも正しく出力されていた**(手で確認済み)。
突き合わせ側が読み取れていなかった。**原因は 3 つある。**

| # | 原因 | 詳細 |
| --- | --- | --- |
| a | `series_id()` に `sar` の分岐が無い | 系列キーから `sar/{host}/{activity}/{device}` を復元できず、照合が必ず外れる。**レポートは device が占位子 `-` のとき `device=` を書かない**ため、復元時に補う必要がある |
| b | `_ALG` が `ALG-[AB]\d` である | **ALG-C1 を拾わない。** ALG-C1 を期待する INJ-011 の照合が必ず外れる。**これは CR-005(ALG-C1 新設)以来の積み残しであり、CR-010 で初めて顕在化した** |
| c | `_DATA` が和名の括弧を扱えない | 「データ」欄は `{metric} ({和名})` の形である。`\([^)]*\)` で和名を読み飛ばしていたため、**和名に括弧を含むメトリクス**(`受信 (KB/秒)` `スワップアウト(ページ/秒)` など)で照合が外れた |

- テスト指示との矛盾の疑い: なし。`docs/ArchitectureHandbook.md` 9.1 #9 が

- 次工程への申し送り: **P203 で `report_parser.py` を修正する。**

### 初回に失敗した 1 件と、その対処

**#5(8 活動すべてが現れる)が `swapping` で失敗した。**

* **原因はアプリではない。** `pswpin/s` / `pswpout/s` のベースラインが 0.1 前後と小さく、
  `effective_sigma` の下限(`sigma_floor_abs = 0.5`。ADR-003)に埋もれて
  検知点が 1 つも出なかった。**レポートは「イベント」しか載せない**ため、
  系列は存在するのにテストからは見えなかった。
* **対処**: テストデータ側に **INJ-012**(host02 のスワップアウトが
  6/10 12:00 以降に 0.1 → 30〜70 へ跳ね上がる)を追加した。
  **INJ-011(同じ host02 のメモリ張り付き)の帰結として自然な形**であり、
  作為的なデータではない。
* **★スパイクではなく水準そのものを上げた。★** 値が小さい系列では
  スパイクを入れても `effective_sigma` の下限に埋もれる。これは ADR-003 の
  意図した挙動であり、テストデータ側で形を選ぶべき事項である。
