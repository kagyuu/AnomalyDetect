## 2. 実装中に発見し、その場で是正した欠陥

### 2.1 **重ね合わせが構造的に一度も描かれなかった** — 本CRで最も重要

最初の実装では対象イベントを**脅威度の高い順だけ**で選び、既定を
`min_severity = SEVERE` とした。**15 枚のチャートが出力され、エラーも警告も
出ないまま、全ての図で折れ線が 1 本しか無かった。**

原因は設計上の衝突である。

| 事実 | 出典 |
| --- | --- |
| **`SEVERE` は定義上「観点2 の検知」である** | `README.md` 5 章 / DS-09-04 |
| **観点2 のイベントには同時アノマリーが付かない** | CR-002 / DS-11-08 |

**依頼者の要求の半分(重ね合わせ)が、エラーなしに消えていた。**

**是正**: 選別の枠を 2 つに分け(DS-15-03)、既定を `FATAL` に変えた。

```
枠1: 脅威度の高い順                        … max_per_host 件/ホスト
枠2: 同時アノマリーを持つイベントの脅威度順  … max_overlay_per_host 件/ホスト
```

**回帰試験**: `test_overlay_quota_is_separate`(単体)/
`test_05_overlay_charts_are_actually_produced`(A013)。

**この型の欠陥は 2 度目である。** CR-002 でも「原因候補ルールが無言で発火しなくなった」
という同じ形(設定の既定値が別の機能の前提と噛み合わない)で起きている。

### 2.2 採取間隔の違いで横軸がずれた

重ねる相手は採取間隔が違うため、そのまま並べると横軸が合わない。
**本体の時刻列に合わせ、同じ時刻の点が無ければ直前の値を保持する**(階段状)ようにした。

### 2.3 A011 が落ちた

作業ディレクトリの生成物を `report_*` と `tmp/` に限っていたため、`charts/` が
「想定外の生成物」と判定された。**期待値に加えた。**

### 2.4 追加の指示への対応(2026-09-06)

**実装後に依頼者から追加の指示があり、同じ回で対応した。**

| 指示 | 対応 |
| --- | --- |
| チャートが無いと「ツールの不備」と誤解される。`[NO CHART]` の画像を出す | `charts/no-chart.svg` を **1 つだけ**作り、全イベントから参照 |
| 理由は書かない(4K トークンの制限に抵触しうる) | 画像は `[NO CHART]` の文字のみ(311 バイト) |
| `MIN_POINTS` が原因の場合は生データを表で出す | `[NO CHART]` に続けて `\| 時刻 \| 値 \|` の表 |
| README に `MAX_POINTS` / `MIN_POINTS` を記載 | README 4.5 に節を追加 |

**判断が必要だった点**: **チャート機能が無効(`enabled = false`)のときは画像も出さない。**
誰も図を期待しない状況で `[NO CHART]` を 7,000 件並べる意味がないためである。
A013 `test_15_disabled_shows_no_placeholder_either` が確かめている。

**副作用**: `reporter.set_chart_placeholder()` はモジュール変数であり、
**同一プロセスで続けて実行すると前回の設定が残る。** 無効時に明示的に `None` を
渡すことで防いでいる(テストが同一プロセスで複数回実行するため実害がありえた)。

## 3. 本番規模での確認(A006)

| 項目 | 30 日規模 |
| --- | --- |
| **チャートの枚数** | **2,430 枚** |
| **チャートの合計サイズ** | **17.8MB** |
| 1 枚あたり | 約 7KB |

**上限(`max_per_host` + `max_overlay_per_host` = 100 + 100)が効いている。**
上限が無ければイベント約 7,200 件ぶんが出力される。

### 上限の既定値による違い(実測)

**依頼者の指示により既定を 10 + 10 から 100 + 100 に変更した。**

| 設定 | 枚数 | 合計サイズ | 30 日の実行時間 |
| --- | --- | --- | --- |
| 10 + 10 | 340 枚 | 3.7MB | 55.3s |
| **100 + 100(既定)** | **2,430 枚** | **17.8MB** | **95.3s** |

### 性能への影響

| ケース | 0.4.0 | **0.5.0(1 回目)** | **0.5.0(2 回目)** |
| --- | --- | --- | --- |
| 通常 30 日 | 53.1s | **95.3s** | **96.0s** |
| 大規模 90 日 | 162.8s | **302.4s** | **280.5s** |

**チャートの生成が所要時間を大きく押し上げている**(30 日で +80%、90 日で +75%)。
2,430 枚ぶんの `metrics` 問い合わせと SVG の書き出しである。
**NFR-002(600 秒)には収まっている**(90 日で 302 秒 / 余裕 50%)が、
**上限を上げるほど余裕が減る。**

### 4K トークンの目標(CR-004)は維持されている

**サマリにチャートは入らない。** A013 が
「`enabled = true` と `false` でサマリが完全一致すること」
「各サマリが 4,000 バイト以下であること」を確かめている。
