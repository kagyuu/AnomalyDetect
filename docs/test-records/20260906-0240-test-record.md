## 2. 試験の範囲 — **依頼者が明示的に狭めた**

> 性能やバリエーション、エラー系のテストなどは、入力 UTC、レポート UTC のみで構いません。
> その他に {入力JST、レポートUTC} および {入力UTC、レポートJST} の場合の疎通確認をお願いします。
> 繰り返しますが、タイムゾーンが指定されていた場合は疎通テストのみで良いです。
> あと、当面 sar は分析対象にならないので、sar が無い場合の疎通テストもしてください。
> (2026-09-06)

**根拠**: 想定システムはすべて UTC であり、非 UTC 構成は「設定できる」ことに意味が
あるのであって、その構成で運用されるわけではない。

| 区分 | 構成 | 実施箇所 |
| --- | --- | --- |
| 性能 | 入力 UTC / レポート UTC | A006 |
| エラー系・バリエーション | 入力 UTC / レポート UTC | A002 / A009 ほか |
| 変換規則そのもの | — | 単体 `test_timezone.py` |
| **疎通** | 入力 JST / レポート UTC | **A012** |
| **疎通** | 入力 UTC / レポート JST | **A012** |
| **疎通** | sar が無い場合 | **A012** |

## 3. A012 の疎通確認の結果

| 構成 | 確認できたこと |
| --- | --- |
| 入力 JST / レポート UTC | 完走。対象期間の開始が `2026-06-01 00:00:00` → **`2026-05-31 15:00:00`**(9 時間 戻る)。併記は `(UTC)` |
| 入力 UTC / レポート JST | 完走。開始が **`2026-06-01 09:00:00`**(9 時間 進む)。併記は `(Asia/Tokyo)` |
| **sar が無い場合** | 完走。**`sa-*.csv` を置いても無視され、結果が変わらない** |
| `[timezone] sar = UTC` と書いた場合 | **未知のキーとして警告し、無視する。** 停止しない |
| 既定(全 UTC) | `変換は行いません` が出て、**変換の SQL が発行されない** |

**不正な設定値**(単体テストで確認。いずれも終了コード 3)

| 値 | 結果 |
| --- | --- |
| `+09:00` | 停止。**固定オフセットは DuckDB が解釈できない** |
| `utc` | 停止。**大文字小文字を区別する** |
| `Asia/Nowhere` | 停止 |
| 複数の誤り | **まとめて全件報告する**(他の設定値の検証と同じ) |

## 4. 性能(既定の `max_memory = 4GB`)

**タイムゾーンの追加による性能への影響は無い。**
既定はすべて UTC であり、**変換の SQL が一度も発行されない**ためである。

| ケース | 0.3.0 | **0.4.0(1 回目)** | **0.4.0(2 回目)** |
| --- | --- | --- | --- |
| 通常 30 日(950,400 行) | 55.1s | **53.1s** | **51.9s** |
| 大規模 90 日(2,851,200 行) | 173.6s | **162.8s** | **161.1s** |
| うち S6(30 日) | 23.9s | 23.0s | 22.1s |

**4K トークンの達成状況(90 日規模)** — **時刻にタイムゾーンを併記しても上限内に収まる。**

| 出力 | 0.3.0 | **0.4.0** | 目安 4,000 バイト |
| --- | --- | --- | --- |
| `report_summary_202606.md` | 3,873 | **3,891** | ○ |
| `report_summary_202607.md` | — | **3,874** | ○ |
| `report_summary_202608.md` | — | **3,854** | ○ |

**併記により 1 時刻あたり 6 バイト増えるが、サマリの表は行数上限で抑えられている**
ため、増分は限定的である(+18 バイト)。

## 5. 実装中に発見し、その場で是正した欠陥

| # | 発見した欠陥 | 是正 |
| --- | --- | --- |
| 1 | **結合テストの `report_parser._parse_ts` が併記に対応しておらず 2 件が失敗した** | 併記を落として時刻だけを読むようにした。**ADR-009 が予告していた依存がまた現実化した** |
| 2 | **単体テストで進捗の出力が拾えなかった。** `load_cfg` が内部で `progress` を作り直し、出力先が差し替わっていた | cfg を先に作ってから `make_progress()` を呼ぶ順序に変えた |
| 3 | **`固定オフセット +09:00` が DuckDB で使えない**(起票前の実測)。想定より影響が大きかった | 設定を IANA の名前付きタイムゾーンに限り、`pg_timezone_names()` で検証する仕組みを入れた |
| 4 | **タイムゾーン名の検証を S2 で行えない。** 設定読み込みの時点では DuckDB の接続がまだ無い | **接続を開いた直後(S3)で検証する**構成にした。利用者から見た振る舞い(終了コード 3・全件報告)は他の設定値と同じ |
